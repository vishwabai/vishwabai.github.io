OPEN

Every request can fail. What do you do about it?

Not “if” — when. A network blips, a disk fills, a dependency slows down. Resilience engineering is the set of patterns for what happens in that moment.

This deck builds every idea the same way: teach it, recap it in one line, then expose the gap it leaves — which the next pattern fills. By the end you'll have all 31 patterns wired into one mental map.

OPEN

One slow service can take down a system that has nothing wrong with it

Watch Service C — nothing crashes, it just gets slow. No timeouts, no isolation, no limits anywhere else in the chain.

So far: an unhandled slow dependency cascades into a total outage, even though every machine is technically “up.” But we're still missing something — at what point do we just stop waiting?

TIME & RETRY

Timeout: stop waiting after a fixed budget

A timeout is a promise you make to your own caller — “I will respond within T, even if that means responding with failure.”

So far: a timeout converts an unknown wait into a bounded one. But it doesn't fix anything — it just fails faster and fails cleanly. What do you do the instant a call is abandoned?

TIME & RETRY

Retry: try again, because most failures are temporary

Packet loss, a momentary GC pause, a pod restarting — these resolve in milliseconds. Retrying converts a transient blip into a non-event.

So far: retrying trades a little latency for a lot of reliability, when failures are independent. But if 10,000 clients all retry the instant they fail — what happens to the service they're retrying against?

TIME & RETRY

Exponential backoff: space retries further apart each time

Instead of retrying immediately, wait longer after each failure — giving the struggling service room to actually recover.

So far: backoff turns a retry storm into a retry taper. But every client computes the same delay from the same formula — so what happens when they all started failing at the exact same moment?

TIME & RETRY

Jitter: add randomness so clients don't retry in lock-step

Same backoff formula, but each client picks a random point inside the window instead of the same fixed instant.

So far: jitter spreads synchronized clients across time, turning one sharp spike into a gentle ramp. But backoff still assumes the service will recover — what if it's already so overloaded that even spread-out retries keep it down?

PROTECT & ISOLATE

Circuit breaker: stop calling a service that's clearly down

Three states — Closed (calling normally), Open (failing instantly, no calls sent), Half-Open (a few test calls to check recovery).

So far: a breaker protects the caller from wasting time on a doomed call, and protects the callee from a pile-on while it recovers. But it only guards one dependency — what if a slow dependency ties up resources shared by everything else?

PROTECT & ISOLATE

Bulkhead: give each dependency its own resource pool

Named after ship compartments — flooding in one doesn't sink the vessel. Here it's thread pools, connection pools, or queues, kept separate per dependency.

So far: isolating resource pools contains a failure to the dependency that caused it. But a breaker and bulkhead only react to traffic that's already inside the system — what controls how much traffic gets in, in the first place?

PROTECT & ISOLATE

Rate limiter: cap how much traffic gets through at all

Every consumer (or API key, or IP) gets a maximum request rate. Traffic above that is rejected before it ever reaches business logic.

So far: a rate limit protects capacity by refusing excess demand up front. But a limiter enforces a policy — it doesn't help when the whole system is already past capacity despite the policy. What do you do with the traffic you already let in?

PROTECT & ISOLATE

Load shedding: when overloaded, drop the least important work first

Not every request matters equally. Under pressure, reject low-priority traffic (background jobs, analytics pings) so high-priority traffic (checkout) still gets served.

So far: shedding trades total throughput for guaranteed service to what matters most. But shedding is the server unilaterally dropping work — what if producers could be told to slow down before they even send it?

PROTECT & ISOLATE

Backpressure: let the consumer tell the producer to slow down

Instead of silently dropping or endlessly queuing, the consumer signals its real capacity, and the producer throttles itself to match.

So far: backpressure turns overload into a two-way conversation instead of one side silently failing. That covers a system staying alive under load — but what happens when a whole node just dies?

STAY UP

Failover: automatically switch to a healthy replica

When the primary is detected as dead — not slow, dead — traffic is rerouted to a standby that's ready to take over.

So far: failover converts a dead node into a brief blip, bounded by how fast you can detect death and reroute. But detection takes time — what do you do in the instant you already know something is broken?

STAY UP

Fail-fast: reject bad requests immediately, don't limp toward failure

Check the cheap things first — auth, input shape, breaker state — and reject in milliseconds instead of discovering failure after 3 seconds of real work.

So far: fail-fast makes failure cheap by detecting it as early as possible. But an immediate rejection still means the user gets nothing — is there a version of “failure” the user barely notices?

STAY UP

Graceful degradation: serve a smaller, still-useful response

If recommendations are down, show a generic “popular items” shelf instead of nothing. The page still works — just less personalized.

So far: degrading gracefully preserves the core experience by sacrificing a non-essential feature. That's about full failures — but most user pain comes from the slow tail, not total outages. What do you do about the one unlucky slow reply out of a thousand?

STAY UP

Hedged requests: fire a backup call before the first one is even late

If the primary hasn't answered by, say, the 95th-percentile latency, send the same request to a second replica — and take whichever answers first.

So far: hedging trims the slow tail at the cost of a small amount of duplicate load. That's the caller managing its own risk. Zooming out — how does anything even know a node is unhealthy in the first place?

SIGNS OF LIFE

Health checks: ask an instance “are you okay?” on a schedule

A load balancer polls each instance — liveness (“restart me if this fails”) and readiness (“don't send me traffic yet”) are two different questions with two different answers.

So far: health checks let infrastructure pull status on a schedule and route around what fails it. But polling has a detection delay built in — what if a node needs to announce its own death the instant it happens?

SIGNS OF LIFE

Heartbeats: nodes push “I'm alive” instead of waiting to be asked

Each node emits a signal on a fixed interval. Miss enough of them in a row, and the cluster declares that node dead — without ever having to ask.

So far: heartbeats flip health checking from pull to push, which is how clusters detect failure fast enough to trigger leader election or failover. That covers detecting a dead worker — but what happens to the work that node was in the middle of?

SIGNS OF LIFE

Dead-letter queue: quarantine the message that keeps failing

A message that fails processing after N retries doesn't get lost, and doesn't get to jam the queue for everyone behind it — it's routed sideways for a human to inspect.

So far: a DLQ keeps one poison message from blocking the whole pipeline, and keeps a record so nothing silently vanishes. But if that message eventually gets replayed — what stops it from being processed twice?

SIGNS OF LIFE

Idempotency: make repeating an action safe

Attach a unique key to the request. If the server has already seen that key succeed, it returns the original result instead of doing the work again.

So far: idempotency is what makes every retry, hedge, and DLQ replay in this deck actually safe to perform — without it, every one of those patterns risks charging a card twice.

RECAP

17 patterns, one request's journey

Every pattern so far answers a question about a specific point in a request's life — before it's sent, while it's in flight, or after it fails.

That's the full core toolkit for keeping a system up. Next: the precise algorithms behind just one of these boxes — the rate limiter — because “cap the rate” hides a surprisingly deep question.

RATE LIMIT ALGORITHMS

“Limit to 100 requests per minute” is harder to implement than it sounds

The honest question underneath it: how do you cheaply and fairly count “requests in the last N seconds,” for millions of keys, without keeping a full history?

So far: every rate-limiting algorithm is a different trade-off between memory, precision, and burst tolerance — none of them is free. What's the simplest possible answer, and where does it break?

RATE LIMIT ALGORITHMS

Fixed window: count requests in the current clock-aligned bucket

Limit = 100 req / 60s window. One counter, reset to zero the instant the clock crosses a minute boundary. Cheap: one integer per key.

So far: fixed window is a single counter — trivial to build, trivial to reason about. But nothing stops 100 requests at 11:00:59 and another 100 at 11:01:00 — 200 requests in two real seconds, under a “100 per minute” limit. How do you fix the boundary?

RATE LIMIT ALGORITHMS

Sliding window counter: blend the current and previous window

estimate = current_count + previous_count × overlap. Example: previous window had 100 requests, we're 25% into the new window → estimate = 30 + 100 × 0.75… weighted by how much of the old window still “overlaps” the lookback.

So far: weighting the previous window smooths the boundary burst to roughly the true rate, using just two counters instead of a full log. It's an estimate, not exact — what if you need the count to be exactly right?

RATE LIMIT ALGORITHMS

Sliding log: store every timestamp, count exactly what's in the window

On each request: drop timestamps older than (now − window), then count what's left. Perfectly precise — because it isn't estimating anything.

So far: a sliding log is exact, at the cost of storing one entry per request — 1,000 req/s over a 60s window is 60,000 stored timestamps, per key. That's the accuracy end of the spectrum. Is there a version that's cheap and handles bursts on purpose?

RATE LIMIT ALGORITHMS

Token bucket: refill steadily, spend freely, allow bursts up to a cap

tokens = min(capacity, tokens + rate × elapsed). Each request costs 1 token (or more, for expensive calls); reject if not enough remain. Example: rate = 10 tokens/s, capacity = 20 → an idle client can burst 20 requests instantly, then settle to 10/s.

So far: token bucket is the industry default — cheap (two numbers per key), and it deliberately allows short bursts instead of fighting them. But sometimes a burst downstream is exactly what you can't afford — what if you need output smoothed to a constant rate, no exceptions?

RATE LIMIT ALGORITHMS

Leaky bucket: requests queue up, and drain at one fixed rate

Incoming requests fill a queue; the queue drains at a constant rate r, no matter how bursty the input was. Queue full → new requests are rejected outright.

So far: leaky bucket guarantees a smooth, constant output rate — the mirror image of token bucket, which guarantees flexible bursts. Both algorithms so far assume one server holding the counter — what happens the moment you have five?

RATE LIMIT ALGORITHMS

Distributed rate limiting: five servers must share one limit, not enforce five

If each of 5 app servers enforces “100/min” independently, the real ceiling is 500/min. The fix: a shared store (Redis INCR + EXPIRE, or a Lua-scripted token bucket) that every server checks against.

So far: distributed limiting needs one source of truth, reachable by every node — usually costing a network round-trip per check, which is the price of correctness at scale.

RECAP

Six algorithms, one spectrum

From “cheap and approximate” to “exact and expensive,” and from “smooth output” to “bursty but efficient.” Pick based on which trade-off you can afford.

Rate limiting protects one box in the request's journey. Now: what protects the infrastructure itself — whole nodes, zones, and regions — when they're the thing that fails?

TOPOLOGY & AVAILABILITY

Active-active vs. active-passive: two ways to keep a spare copy

Both are redundancy — more than one copy that could serve traffic. Active-active: both serve live traffic right now, splitting load. Active-passive: the standby sits idle until failover, simpler but slower to kick in.

So far: active-active gives faster failover and better hardware use; active-passive gives simpler consistency, since only one side is ever writing. Either way, something has to decide who leads writes — how do multiple copies of the same data stay in sync?

TOPOLOGY & AVAILABILITY

Leader-follower: one node writes, the rest replicate and can serve reads

All writes go to the leader; it streams changes to followers. Followers can serve reads — but there's a replication lag, so a follower might briefly answer with stale data.

So far: leader-follower scales reads and gives you standbys for free, at the cost of replication lag on followers. That's about a handful of machines — what protects you when the whole rack, or the whole data center, loses power?

TOPOLOGY & AVAILABILITY

Multi-zone deployment: spread instances across independent failure domains

A region is made of multiple Availability Zones — separate power, network, and physical buildings. Deploy N instances split across 3 zones; lose one zone, lose roughly a third of capacity, not all of it.

So far: multi-zone deployment contains a zone-level outage to a fraction of capacity instead of a total loss. But a zone outage is still local to one metro area — what protects you from an event that takes out an entire region?

TOPOLOGY & AVAILABILITY

Multi-region deployment: full copies across geography

Deploy in, say, us-east and eu-west. Survives a whole-region outage — but replicating data between them now costs real time: a round trip across the Atlantic is roughly 70–100ms, not zero.

So far: multi-region buys survival against a disaster that multi-zone can't, in exchange for real cross-region latency and harder consistency. All of this protects hardware failure — what protects you from a mistake a human makes on purpose?

TOPOLOGY & AVAILABILITY

Disaster recovery: replication protects hardware, backup protects mistakes

Run DELETE FROM orders without a WHERE clause, and replication faithfully copies that deletion to every follower in milliseconds. A separate, offline backup — a point-in-time copy — is the only thing that still has the data.

So far: replication and backup solve two different failure classes — replication for “a machine died,” backup for “someone broke the data itself.” A backup by itself only gives you fixed snapshots — what if the mistake happened at 2:17pm and your last backup was at midnight?

TOPOLOGY & AVAILABILITY

Point-in-time recovery: restore to the exact second before the mistake

A periodic base backup, plus a continuous transaction log (a WAL), lets you replay every change up to any timestamp. Restore point = latest base backup + replay log up to 14:32:07 — one minute before the bad deploy.

So far: PITR turns “we lost everything since midnight” into “we lost one minute.” That's how much data you can lose — which is exactly what one of the next metrics measures on purpose.

METRICS

SLI → SLO → SLA: measurement, target, and promise

SLI: what you actually measure — “99.94% of requests succeeded, last 30 days.” SLO: your internal goal — “99.9%.” SLA: the external, often contractual promise — “99.5%,” usually looser, with a financial penalty if missed.

So far: the SLA is deliberately looser than the SLO, so you breach your own internal target long before you breach a customer contract. But “99.9%” means nothing until you convert it into actual minutes — how much downtime does that number actually buy you?

METRICS

Error budget: your SLO, converted into minutes you're allowed to fail

budget = (1 − SLO) × total time. Example: SLO = 99.9% over a 30-day month (43,200 minutes) → you're allowed 43.2 minutes of downtime, total, all month.

So far: the error budget turns an abstract percentage into a spendable resource — once it's gone, teams slow down and stabilize instead of shipping. That's a policy for the whole month — what does the failure pattern look like for one single machine, one incident at a time?

METRICS

MTBF & MTTR: how often it breaks, and how fast you fix it

MTBF (Mean Time Between Failures) is the average healthy stretch. MTTR (Mean Time To Recovery) is the average repair time. Availability = MTBF / (MTBF + MTTR). Example: MTBF = 720h, MTTR = 2h → availability = 720 / 722 ≈ 99.72%.

So far: you can hit the same availability by failing rarely or by fixing fast — the formula doesn't care which lever you pull. Both of those measure the machine. Two more metrics measure something else entirely — your data, during that repair window.

METRICS

RPO & RTO: how much data you can lose, and how long you can be down

RPO (Recovery Point Objective): the maximum data loss, measured backward in time from the incident — set by your backup frequency. RTO (Recovery Time Objective): the maximum downtime, measured forward — set by how fast your recovery process actually runs.

So far: RPO is a promise about the past, RTO is a promise about the future, and every pattern in this deck exists to make one or both of those numbers smaller.
