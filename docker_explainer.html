Why Docker? Basics

The classic problem: "It works on my machine." Different OS versions, library versions, and configs mean an app that runs perfectly for you might break for a teammate or in production.

Docker's fix: package the app + all its dependencies + config into one portable unit called a container, which runs identically everywhere.

  • Consistency — same environment on your laptop, CI server, and production.
  • Isolation — each app runs in its own sandboxed environment with its own dependencies.
  • Portability — build once, run on any machine that has Docker installed.
  • Efficiency — containers share the host OS kernel, so they're far lighter than virtual machines.

VM vs Container Basics

A Virtual Machine virtualizes the entire hardware stack, including a full guest OS for every app. A container virtualizes only at the OS level — all containers share the host's kernel.

Virtual Machines
  • Each VM has its own full guest OS (gigabytes in size)
  • Boots in minutes
  • Strong isolation via a hypervisor
Containers
  • Share the host kernel — just app + libraries (megabytes)
  • Starts in milliseconds-seconds
  • Process-level isolation via kernel namespaces/cgroups

Docker Architecture Basics

The docker command isn't itself running your containers — it's a client talking to a background service over an API.

  • Docker CLI — the docker command you type; just a thin client.
  • Docker daemon (dockerd) — the background process that actually builds images, manages containers, networks, and volumes.
  • containerd — a lower-level runtime daemon (CNCF project) that dockerd delegates real container lifecycle work to.
  • runc — the low-level OCI tool that actually spawns the container process using kernel primitives.
  • The CLI and daemon talk over a REST API (a Unix socket locally, or TCP for a remote Docker host) — this is also what tools like Docker Compose and the VS Code Docker extension use.

Namespaces & Cgroups Intermediate

Containers aren't a special kernel feature — they're regular Linux processes wrapped in two existing kernel mechanisms that create the illusion of isolation.

# see it yourself: a container's main process is just a PID on the host
docker inspect -f '{{.State.Pid}}' my_container
ps aux | grep <that pid>
  • Namespaces control what a process can see — separate PID, network, mount, UTS (hostname), IPC, and user namespaces give each container its own isolated view.
  • Cgroups (control groups) control what a process can use — CPU, memory, disk I/O — this is the actual mechanism behind --memory and --cpus.
  • A "container" is really just: a host process, put in its own namespaces, with cgroup limits applied, running from an image's filesystem layers.
  • This is also why containers boot near-instantly — there's no VM to boot, just a process to fork with different kernel bookkeeping.

Images & Layers Basics

A Docker image is a read-only template built from a stack of layers. Each instruction in a Dockerfile (FROM, RUN, COPY...) creates one cached, reusable layer.

  • Layers are cached — if a layer hasn't changed, Docker reuses it on the next build (faster builds).
  • When a container runs, Docker adds one thin writable layer on top of the read-only image layers.
  • Multiple containers can share the same underlying image layers, saving disk space.

Image → Container Lifecycle Basics

The core commands every Docker workflow revolves around:

# Build an image from a Dockerfile
docker build -t myapp:1.0 .

# Run a container from that image
docker run -d -p 8080:80 --name myapp_c myapp:1.0

# List / stop / remove
docker ps
docker stop myapp_c
docker rm myapp_c
  • build turns a Dockerfile into an image.
  • run creates and starts a container from an image.
  • ps, stop, rm manage the container's lifecycle (running → stopped → removed).
  • Images live in a registry (like Docker Hub) — docker push/pull move them in and out.

Container Lifecycle States Basics

A container moves through a small set of states. Knowing them makes docker ps -a output and exit codes much easier to reason about.

docker create myapp   # → Created
docker start  <id>    # → Running
docker pause  <id>    # → Paused
docker stop   <id>    # → Stopped (Exited)
docker rm     <id>    # → Removed
  • docker run is really create + start combined.
  • A stopped container still exists on disk (writable layer intact) until rm deletes it.
  • Exit code 0 = clean exit; non-zero = the main process errored or was killed.

PID 1 & Zombie Processes Intermediate

The first process a container starts becomes PID 1 inside its own process namespace. PID 1 has special Linux responsibilities most app frameworks were never built to handle.

# Without an init system: signals may not propagate, zombies pile up
CMD ["node", "server.js"]

# With a tiny init process as PID 1 instead
ENTRYPOINT ["tini", "--"]
CMD ["node", "server.js"]
  • PID 1 must reap zombie processes (finished child processes) — most apps don't do this, so zombies accumulate.
  • PID 1 also needs to forward signals like SIGTERM to child processes — many runtimes ignore signals when running as PID 1.
  • Fix: use a minimal init system like tini (or docker run --init) as PID 1, which handles reaping and signal forwarding correctly.

Anatomy of a Dockerfile Basics

A Dockerfile is a recipe — a sequential list of instructions Docker executes to build an image, top to bottom.

ENTRYPOINT vs CMD Basics

Both define what runs when a container starts, but they combine differently — this trips up almost everyone at first.

ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8000"]

# docker run myapp           → python app.py --port 8000
# docker run myapp --port 9000 → python app.py --port 9000
  • ENTRYPOINT is the fixed command — hard to override (needs --entrypoint flag).
  • CMD supplies default arguments — easily overridden by anything passed after the image name in docker run.
  • CMD alone (no ENTRYPOINT) = the whole thing is replaceable; ENTRYPOINT + CMD = fixed binary, swappable arguments.

.dockerignore & Image Size Basics

Without a .dockerignore file, COPY . . sends everything in your project — including node_modules, .git, and local secrets — into the build context.

# .dockerignore
node_modules
.git
*.log
.env
dist
__pycache__
  • Smaller build context → faster builds (less to send to the Docker daemon).
  • Keeps secrets and local junk out of the image entirely — not just hidden, genuinely excluded.
  • Combine with a slim base image (alpine, distroless) and multi-stage builds for the smallest practical image.

Tagging Strategy Basics

Tags are how you version images. A sloppy tagging strategy (everything as :latest) makes rollbacks and debugging painful.

docker build -t myapp:1.4.2 -t myapp:1.4 -t myapp:latest .
docker build -t myapp:$(git rev-parse --short HEAD) .
  • Semantic version tags (1.4.2) let consumers pin to exact, reproducible builds.
  • Git SHA tags tie an image directly back to the exact commit that produced it — invaluable for debugging.
  • latest is just a movable label, not a guarantee of "newest" — avoid relying on it in production.
  • One image can carry multiple tags simultaneously, pointing at the identical layers.

Inspecting Images Intermediate

Before trusting an image — yours or a third party's — these commands let you see exactly what's inside it and how big each piece is.

docker history myapp:1.0        # every layer + the command that created it
docker image inspect myapp:1.0  # full JSON: env, entrypoint, layers, size
docker diff my_container        # files changed vs the image (A/C/D)
docker images --digests         # see content-addressable digests, not just tags
  • docker history shows which instruction created each layer and how much size it added — the fastest way to find what's bloating an image.
  • docker diff shows what a running container has Added, Changed, or Deleted relative to its image — useful for catching unexpected writes (like an app writing logs into its own filesystem instead of stdout).
  • docker image inspect dumps the full manifest: layer digests, exposed ports, default env, entrypoint/cmd — everything baked into the image.

Registries & Docker Hub Basics

A registry is a storage/distribution system for images. Docker Hub is the default public registry, but private registries (ECR, GCR, GitLab, self-hosted) work the same way.

# Tag an image for your registry namespace
docker tag myapp:1.0 myuser/myapp:1.0

# Push it up
docker push myuser/myapp:1.0

# Pull it down anywhere else
docker pull myuser/myapp:1.0
  • Image names follow [registry/]namespace/repository:tag — no registry prefix defaults to Docker Hub.
  • Tags version an image (:1.0, :latest); latest is just a convention, not "the newest" automatically.
  • Pulling reuses any layers you already have locally — only new/changed layers are downloaded.

Container Networking Intermediate

Containers get their own virtual network interface. Docker creates virtual networks (bridges) so containers can talk to each other and the outside world.

  • bridge (default) — an isolated private network on the host; containers on it can reach each other by name.
  • Port mapping (-p 8080:80) exposes a container's internal port to the host machine.
  • host network — container shares the host's network stack directly (no isolation, no mapping needed).
  • none — container gets no network access at all.

Network Drivers Compared Intermediate

Beyond the default bridge, Docker supports several network drivers — each suited to a different deployment shape.

docker network create --driver bridge my-net
docker network create --driver overlay --attachable my-swarm-net
docker run --network host myapp
docker run --network none myapp
  • bridge — single host, isolated, the everyday default.
  • host — no isolation, shares the host's network stack directly; fastest but least safe.
  • overlay — spans multiple Docker hosts, used by Swarm/Kubernetes for cross-node container communication.
  • macvlan — gives a container its own MAC address, appearing as a physical device on the network.
  • none — fully isolated, no networking at all.

Volumes & Persistence Intermediate

Containers are ephemeral — delete the container and its writable layer (and any data in it) is gone. Volumes solve this by storing data outside the container's lifecycle.

  • Named volumes — managed by Docker, stored under /var/lib/docker/volumes, the recommended approach.
  • Bind mounts — map a specific host folder/file directly into the container.
  • Data in a volume survives docker rm — only deleted explicitly with docker volume rm.

Bind Mounts vs Named Volumes Intermediate

Both persist data outside the container, but they're managed very differently and fit different use cases.

# bind mount: exact host path, great for local dev hot-reload
docker run -v $(pwd)/src:/app/src myapp

# named volume: Docker-managed, portable, great for databases
docker run -v db_data:/var/lib/postgresql/data postgres
Bind Mounts
  • Points at an exact host path you choose
  • Great for local development — edit on host, see changes instantly in container
  • Tied to that machine's filesystem layout
Named Volumes
  • Docker picks and manages the storage location
  • Portable across machines, easy to back up/migrate
  • The recommended choice for production data like databases

Environment Variables & Secrets Intermediate

Config that changes between environments (DB URLs, API keys, feature flags) shouldn't be hardcoded into an image — it should be injected at runtime.

# pass individual values
docker run -e DB_HOST=db.prod.internal myapp

# load many at once from a file (not baked into the image)
docker run --env-file .env.production myapp
  • ENV in a Dockerfile sets a default — fine for non-sensitive config, baked into the image layer.
  • -e / --env-file inject values at run time — same image, different config per environment.
  • For real secrets, prefer a secrets manager or Docker/Swarm secrets over plain env vars, since env vars are visible via docker inspect.

Docker Compose Intermediate

Real apps need multiple containers (web server + database + cache). Compose defines them all in one YAML file and brings the whole stack up with a single command.

services:
  web:
    build: .
    ports: ["8080:80"]
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["dbdata:/var/lib/postgresql/data"]
volumes:
  dbdata:

docker compose up -d starts everything; Compose auto-creates a shared network so web can reach db just by its service name.

Build Cache Optimization Advanced

Docker caches each layer and reuses it if nothing changed. Instruction order matters — put things that change rarely (dependencies) before things that change often (source code).

❌ Cache-unfriendly 
COPY . .
RUN npm install

Any source change invalidates the install layer — full reinstall every build.

✅ Cache-friendly 
COPY package*.json .
RUN npm install
COPY . .

Dependencies only reinstall when package.json actually changes.

Multi-Stage Builds Advanced

Compilers, build tools, and source code bloat an image unnecessarily. Multi-stage builds use multiple FROM stages — only the final, lean stage ships in the image.

# Stage 1: build
FROM node:20 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

# Stage 2: run (only the output is copied over)
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
  • Final image excludes the Node toolchain, source files, and dev dependencies — only the build output remains.
  • Result: smaller, more secure production images with a reduced attack surface.

Health Checks & Restart Policies Advanced

Docker can periodically check whether a container is actually working, not just running, and automatically restart it on failure.

HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost/health || exit 1

# restart automatically unless manually stopped
docker run --restart unless-stopped myapp:1.0
  • HEALTHCHECK runs a command on an interval; container status becomes healthy/unhealthy in docker ps.
  • Restart policies: no (default), on-failure, always, unless-stopped.
  • Orchestrators (Kubernetes/Swarm) use health status to decide when to reroute traffic or replace a container.

Resource Limits Advanced

By default a container can use as much CPU/memory as the host allows. In production you cap this with cgroups-backed limits so one container can't starve the others.

docker run -d --memory="512m" --cpus="1.5" myapp:1.0
  • --memory caps RAM; the kernel OOM-kills the container's process if it's exceeded.
  • --cpus caps CPU as a fraction of cores (e.g. 1.5 = one and a half cores).
  • Setting limits is essential on shared hosts and in any orchestrated cluster (it's how the scheduler packs nodes).

Security Best Practices Advanced

A few habits dramatically shrink a container's attack surface.

  • Don't run as root — add USER appuser in the Dockerfile so a container breakout has limited privileges.
  • Use minimal base images — alpine or distroless images have far fewer packages, so fewer vulnerabilities.
  • Pin versions — avoid :latest in production; pin exact tags/digests for reproducible, auditable builds.
  • Scan images — tools like docker scout or Trivy catch known CVEs in your layers before deploy.
  • Don't bake secrets into images — use build secrets, env injection, or a secrets manager instead of COPYing credentials.

Logs & Debugging Advanced

When something's wrong inside a container, you have three main windows into it: logs, an interactive shell, and inspect metadata.

docker logs -f <container>        # stream stdout/stderr
docker exec -it <container> sh    # shell into a running container
docker inspect <container>        # full JSON metadata
docker stats                       # live CPU/memory usage
  • logs captures whatever the container's main process writes to stdout/stderr — that's the standard logging convention in Docker.
  • exec opens a live shell inside an already-running container, separate from its main process.
  • inspect dumps every detail — IP address, mounts, env vars, restart count — as JSON, great for scripting.

When a Container Won't Start Advanced

A container that exits immediately can't be exec'd into — the usual debugging tools don't apply yet. Here's the actual triage order.

docker ps -a                          # find it — check STATUS / Exited(code)
docker logs <container>               # #1: read the actual crash output
docker inspect <container>            # check mounts, env, command actually run
docker run -it --entrypoint sh image  # override entrypoint, poke around manually
  • Check the exit code first — 137 usually means OOM-killed (hit a memory limit); 1/2 are typically application errors; 126/127 mean the command itself couldn't run.
  • Read the logs before anything else — most "container won't start" issues are just an uncaught exception on the first line of stdout/stderr.
  • Override the entrypoint to get a shell instead of running the app — this lets you poke around the filesystem and try the start command manually to see the real error.
  • If it crashes instantly with no logs at all, suspect a missing file, wrong working directory, or a binary built for the wrong CPU architecture.

Common Gotchas Advanced

Mistakes that work fine until they quietly don't — the ones that catch almost everyone at least once.

  • localhost inside a container ≠ localhost on your machine — it refers to the container itself; reach the host via host.docker.internal (Docker Desktop) or the bridge gateway IP on Linux.
  • Bind-mounting over a build artifact hides what was baked into the image — e.g. mounting your source over /app can shadow a compiled node_modules that only exists inside the image.
  • File permission mismatches — files created by a container running as root land on the host owned by root too, common with bind mounts on Linux.
  • Forgetting EXPOSE isn't publishing — it's documentation only; you still need -p to actually map a port to the host.
  • Build context bloat — running docker build . from the wrong directory can silently send gigabytes to the daemon if there's no .dockerignore.
  • Caching a stale apt-get update — splitting it from the following install across cached layers can install outdated packages; chain them in one RUN.

CI/CD Integration Advanced

In a real pipeline, Docker images are built, tested, and pushed automatically on every commit — turning your Dockerfile into the deployable artifact.

# typical CI pipeline steps
docker build -t myapp:$GIT_SHA .
docker run myapp:$GIT_SHA npm test
docker push myregistry/myapp:$GIT_SHA
# deploy step pulls that exact tag to staging/production
  • Build once, promote everywhere — the same image moves from staging to production unchanged, eliminating "works in staging" drift.
  • CI runners build the image, run the test suite inside a container from that image, then push only if tests pass.
  • Tagging with the Git SHA ties every deployed image back to an exact, traceable commit.

Orchestration at Scale Advanced

Running one container is easy. Running hundreds across many machines, with auto-restart, scaling, and load balancing, needs an orchestrator — Kubernetes or Docker Swarm.

  • Scheduling — places containers across a cluster of machines (nodes) automatically.
  • Self-healing — restarts or reschedules containers that crash or fail health checks.
  • Scaling — spins up more replicas of a container under load, removes them when idle.
  • Load balancing — distributes incoming traffic across all healthy replicas.
  • Docker is the container runtime; Kubernetes/Swarm is the layer that manages many containers across many machines.

Docker Swarm vs Kubernetes Advanced

Two popular ways to run that orchestration layer. Swarm is built into the Docker CLI; Kubernetes is a separate, more powerful (and more complex) system that's become the industry default.

Docker Swarm
  • Built into the Docker CLI — docker swarm init and you're running
  • Simple, minimal learning curve
  • Smaller ecosystem, fewer advanced features
Kubernetes
  • Separate system with its own CLI (kubectl) and YAML model
  • Steeper learning curve, far more configurable
  • Huge ecosystem (Helm, operators, service meshes); the de facto industry standard

Production Checklist Advanced

Pulling every concept together — the things worth double-checking before a container goes live.

  • Multi-stage build, minimal base image, .dockerignore in place
  • Non-root USER, pinned image tags/digests, image scanned for CVEs
  • HEALTHCHECK defined, sensible --restart policy set
  • --memory / --cpus limits configured
  • Secrets injected at runtime, never baked into the image
  • Logs going to stdout/stderr, named volumes for any persistent state
  • Image built and pushed by CI with a traceable tag (Git SHA)
