Part 1
We start at the bottom: what actually moves when a program reads or writes.
A file is data at rest. A stream is data in motion
A file is where bytes live. A stream is the sequential, time-ordered path they travel through — you never need the whole file loaded at once.
Buffers: batch the expensive trips

Practical: Java's BufferedReader, Python's default buffered file objects, and OS page cache all exist to turn thousands of tiny I/O calls into a few big ones.

System calls are expensive — a buffer collects data in memory and writes it out in large batches instead of one byte at a time.
Same value, two ways to write it

Binary I/O

01000001

the raw bits of the integer 65, exactly as they sit in memory — no translation

imagesaudioexecutablesprotobuf

Text I/O

'A'

the same 65, run through a character encoding (ASCII/UTF-8) into something a human — or another program — can read

.txt.csv.jsonsource code

Text I/O is binary I/O plus a character-encoding contract (ASCII, UTF-8...) — that contract is what makes the bytes legible.
So far…

We can now move raw bytes reliably: files, streams, buffers, binary or text.

But a running program doesn't hold bytes.

It holds objects — nested, linked, typed.

How does an object in memory become a flat sequence of bytes — and back again?

That gap has a name: serialization.
Serialization: object graph → byte line, and back
Serialization flattens an object graph into bytes; deserialization walks those bytes back into the same shape — different process, different machine, same object.
JSON — text, nested, ubiquitous
{ "id": 1, "name": "Ana", "active": true }

≈ 42 bytes

Why it won

Human-readable, maps directly onto objects/dicts, native to JavaScript, parsers everywhere.

Cost

Field names repeat on every record; no schema — typos and shape drift aren't caught until runtime.

Practical: REST APIs, config, browser↔server payloads.

JSON trades bytes for readability — every key name is spelled out, every single time.
XML — the same data, more scaffolding
<user> <id>1</id> <name>Ana</name> <active>true</active> </user>

≈ 78 bytes — nearly 2× the JSON

Why the overhead exists

Every tag opens and closes — but that same structure lets XML carry schemas (XSD), namespaces, and attributes that JSON doesn't have.

Practical: SOAP web services, enterprise document exchange, config with strict validation (Ant, Maven, Android layouts).

Verbose by design — the closing tags are what let XML self-validate against a formal schema.
YAML — structure from indentation, not punctuation
id: 1 name: Ana active: true

≈ 27 bytes — the leanest text format

Trade-off

No braces or closing tags — whitespace is the syntax, which is compact for humans but fragile: one wrong indent silently changes meaning.

Practical: Kubernetes manifests, GitHub Actions / CI pipelines, Docker Compose, application config.

YAML is JSON's data model with the punctuation removed — great for hand-written config, riskier for machine-generated data.
CSV — a table flattened to text
id,name 1,Ana 2,Ravi

What's missing

No nesting, no types (everything is text until parsed), commas inside a value need escaping/quoting, and there's no standard for encoding.

Practical: spreadsheets, data exports/imports, bulk-loading databases — flat, tabular data only.

CSV is the simplest serialization there is: one row of text per row of the table, commas as the only structure.
So far…

Text formats (JSON, XML, YAML, CSV) are readable, portable, and easy to debug.

But readability isn't free — spelled-out field names and punctuation cost bytes and parse time.

What if a system needs to move a billion messages a second, between services that already agree on the shape?

Drop the labels, keep only what a pre-shared schema can't infer — that's binary serialization.
Protocol Buffers: a schema replaces the field names
message User { int32 id = 1; string name = 2; }

Both sides compile this .proto file. Field numbers (1, 2) travel on the wire — never the names "id"/"name".

08 01 12 03 41 6E 61

≈ 11 bytes

Encoding trick: tag+type in one byte, then varint — small numbers use fewer bytes than a fixed 4/8-byte int.

Practical: gRPC, cross-language RPC at large scale (Google-style microservices).

JSON needed ≈42 bytes for this record; Protobuf needs ≈11 — because the schema already knows the field names.
MessagePack — binary JSON, no schema required

Like JSON

Self-describing — a MessagePack file can be decoded with no shared schema, same data model as JSON (objects, arrays, strings, numbers).

Like Protobuf

Compact binary encoding — type markers replace punctuation, short strings/ints packed tightly instead of spelled out as text.

Practical: caches (Redis payloads), fast inter-service messages where you still want schema flexibility.
Avro: the schema travels with the data

Why bundle the schema?

Rows carry no field names at all (max compactness) — but the schema rides along in the file, so any reader can self-describe the data years later.

Practical: Hadoop, Kafka topics, big-data pipelines that must stay readable as schemas change over time.

Protobuf assumes both sides already have the schema; Avro ships the schema with the data — built for long-lived data lakes.
Thrift: serialization bundled with RPC

Protobuf + gRPC

Two separate projects: Protocol Buffers defines the bytes, gRPC (a separate layer) defines how services call each other.

Thrift

One IDL file defines both the data types and the service methods — serialization and RPC framework ship together, originally built at Facebook.

Practical: polyglot back-ends (many languages, one service contract) — historically big at Facebook, still used across large-scale distributed systems.
Schema evolution: change the shape without breaking readers

Old reader opens v2 data: ignores the unknown "email" field it doesn't recognize. Still works.

New reader opens v1 data: "email" is missing, so it falls back to the declared default. Still works.

Rule of thumb: adding an optional field with a default is safe; removing or renaming a required field breaks old readers.
Compression: shrink the redundancy, not the meaning

The trade-off

Smaller payload = less disk/network, but compressing and decompressing costs CPU time.

gzip / Brotli — higher compression ratio, slower.

Snappy / LZ4 — lower ratio, built for speed (used inside Kafka, Parquet).

Practical: gzip on HTTP responses; Snappy inside high-throughput data pipelines.

Compression ratio = original size ÷ compressed size — the right algorithm depends on whether you're optimizing for size or for speed.
Encryption: readable bytes become useless without the key

In transit: TLS encrypts the serialized bytes between client and server.

At rest: databases and disks encrypt stored files so a stolen drive reveals nothing readable.

Encryption is the last step of the pipeline — it protects bytes that are already correctly serialized, compressed, and ready to move.

Part 2
Same starting point — bytes on disk — but now shaped into rows, guarded by rules, and made searchable at scale.
A table is a grid of rows and columns
A relational table is formally a "relation": an unordered set of rows, each with the same typed columns.
Primary key: the column that names each row

Rule: unique across every row, never null, exactly one per table — the value every other table points back to.

The primary key is the row's permanent address — everything else in the schema can change; this shouldn't.
Foreign key: a promise that the row you point to exists
Orders.user_id references Users.user_id — the database refuses to insert an order for a user_id that doesn't exist. That guarantee is referential integrity.
Constraints: rules the database enforces for you

NOT NULL

this column can never be empty

UNIQUE

no two rows may share this value

CHECK

value must satisfy a condition (age >= 0)

DEFAULT

value used when none is given

Constraints turn "please don't insert bad data" from a hope into a guarantee, checked on every write.
So far…

Tables store rows, primary keys identify them, foreign keys relate tables, constraints keep values honest.

But nothing stops the same fact — a city, a product name — from being copied into hundreds of rows.

What happens when that duplicated fact needs to change?

One update becomes a thousand updates, and if even one is missed, the data contradicts itself. Normalization is the fix.
1NF: every cell holds one atomic value

1NF: one row per fact, one value per cell. Split the multi-valued cell into its own row per item.

First normal form is the entry ticket — no cell may hold a list; every intersection of row and column is a single value.
2NF: no fact depends on only part of the key

2NF = 1NF + every non-key column depends on the whole composite key, not just part of it.

Only matters when the primary key has more than one column — pull out anything that only needs part of that key.
3NF: no fact depends on another non-key fact

3NF = 2NF + no non-key column determines another non-key column.

If X → Y and Y → Z, then X transitively determines Z — 3NF pulls that chain apart into its own table.
BCNF: every determinant must be a candidate key

Rule of this school: each course has exactly one instructor. So course → instructor holds — but course alone isn't a candidate key (the key is student+course).

Fix

Split into Enrollment(student, course) and CourseInstructor(course★, instructor) — now every determinant is a full candidate key.

BCNF is a stricter 3NF for the rare case where a non-key column still determines part of the key — most real schemas that hit 3NF are already in BCNF.
So far…

Normalization (1NF → BCNF) splits tables until every fact is stored exactly once.

But now a single "show me this order" reads pulls from three or four separate tables, every time.

What happens when a dashboard needs that answer 10,000 times a second?

Sometimes correctness-by-decomposition is the wrong trade for speed — that's denormalization.
Denormalization: trade redundancy for speed

Normalized read

Orders → join Users (name) → join Products (price, name) — 3 tables touched for one page render.

3 joinsalways consistent

Denormalized read

Orders row already stores user_name and product_name directly — one table, one read.

0 joinsmust update in 2 places

Practical: read-heavy dashboards, reporting tables, caches — you accept extra write complexity to make the common read instant.
So far…

We can now shape data for correctness or for speed, on purpose.

But a bank transfer needs two writes: debit account A, credit account B.

What happens if the server crashes after the debit, before the credit?

Money vanishes. Unless the database guarantees both writes happen together, or neither does — a transaction.
A transaction, and the four promises it makes

Atomicity

all steps happen, or none do — no half-finished transfer

Consistency

every commit moves the DB from one valid state to another (constraints hold)

Isolation

concurrent transactions don't see each other's half-finished work

Durability

once committed, survives a crash — written to durable storage

ACID is the contract: Atomicity, Consistency, Isolation, Durability — every serious relational database is built to keep it.
Isolation is a dial, not a switch

allows: dirty reads, non-repeatable reads, phantoms

fixes dirty reads only

fixes non-repeatable reads too

fixes phantom reads too — full serial-like behavior

Dirty read = seeing another txn's uncommitted change. Non-repeatable = a value changes between two reads in the same txn. Phantom = a new row appears in a repeated range query.
Locks: shared for reading, exclusive for writing

Shared (S) lock

Many transactions can hold a shared lock on the same row at once — readers never block other readers.

Txn1 reads ✓Txn2 reads ✓Txn3 reads ✓

Exclusive (X) lock

Only one transaction may hold an exclusive lock — a writer blocks every other reader and writer on that row until it commits.

Txn1 writes ✓Txn2 waits…

Practical: this is what a `SELECT ... FOR UPDATE` (exclusive) vs a plain `SELECT` (shared, under most isolation levels) asks the engine for.
Deadlock: a cycle of waiting that never resolves

Resolution: the database detects the cycle and aborts one transaction (the "victim") — its work rolls back, breaking the deadlock.

Txn1 holds A, wants B. Txn2 holds B, wants A. Neither can ever proceed — a circular wait.
MVCC: readers never wait on writers
Multi-Version Concurrency Control: instead of locking a row for reads, the engine keeps old versions around so a reader sees a consistent snapshot while a writer builds the next version.
So far…

Transactions, ACID, isolation levels, locks and MVCC keep concurrent writes safe and consistent.

But every one of those queries still has to find the right rows first.

If that means scanning every row, one by one, how does this stay fast at a billion rows?

It doesn't — not without a shortcut. That shortcut is an index.
An index is a book's table of contents, for rows
An index is extra, sorted storage that maps a column's values to their row locations — costs disk space and slows writes slightly, to make matching reads far faster.
B-tree: a balanced, sorted lookup structure

N rows, branching factor m (children per node) → height h. With m in the hundreds, a billion rows need only ~4 levels to reach.

Every node keeps sorted keys; the tree stays balanced as it grows, so lookup, insert, and delete all cost O(log n).
B+tree: all data at the leaves, linked in order

Why databases prefer B+trees over plain B-trees: internal nodes hold only keys (more fit per disk page → shallower tree), and range queries (WHERE age BETWEEN 20 AND 30) become a fast leaf-to-leaf walk instead of repeated tree descents.

This is the actual structure behind PostgreSQL and MySQL InnoDB's default indexes — a B-tree variant, not a plain B-tree.
Hash index: instant equality, no sense of order

Great for

WHERE email = 'ana@x.com' — average O(1) lookup

Useless for

WHERE age BETWEEN 20 AND 30 — hashing destroys ordering, so no range scan is possible

A hash index trades away everything B+trees give you for range queries, in exchange for the fastest possible equality lookup.
Composite index: order of columns is the whole game

✓ fast: WHERE last_name='Rao' and WHERE last_name='Rao' AND first_name='Ana' — both use the "leftmost prefix"

✗ slow: WHERE first_name='Ana' alone can't use this index — first_name isn't the leftmost column

The leftmost-prefix rule: an index on (A, B) speeds up queries filtering on A, or A+B — never B alone.
Covering index: the answer lives in the index itself
Add the columns a query selects into the index itself, and the engine performs an "index-only scan" — no second trip to the table.
The optimizer picks the cheapest plan, not the first one

Costs are estimated from table statistics (row counts, value distribution) kept up to date by the engine — this is why running ANALYZE after a big data change matters.

Run EXPLAIN on a query to see exactly which plan the optimizer chose, and why.
Nested loop join: for every outer row, scan the inner

Cheap to start, expensive to scale — good when the outer table is small or the inner side is indexed on the join key.

The simplest join strategy — and the slowest one when both tables are large and unindexed.
Hash join: build once, probe fast

Great for large, unsorted equality joins — needs the hash table to fit in memory.

Build a hash table from the smaller side once, then stream the larger side through it — linear instead of quadratic.
Merge join: zip two sorted lists together

If neither side is already sorted, add O(n log n + m log m) to sort first — merge join wins big when the data (or an index) is already ordered.

Because both inputs are sorted on the join key, a single synchronized pass finds every match — no repeated scanning, no hash table.
GROUP BY collapses rows; OVER keeps them all

Aggregation — GROUP BY

SELECT dept, SUM(salary)
FROM emp GROUP BY dept

10 employee rows in → 3 department rows out. One number replaces the whole group.

rows: 10 → 3

Window function — OVER()

SELECT name, salary,
SUM(salary) OVER(PARTITION BY dept)
FROM emp

Still 10 rows out — each one now also carries its department's running total alongside its own data.

rows: 10 → 10

Practical: window functions power running totals, rankings (RANK, ROW_NUMBER), and moving averages without collapsing the detail rows.
Three ways to save a piece of SQL logic

Stored procedure

Reusable logic that runs inside the database server — can take parameters, loop, branch, and perform writes.

Practical: batch jobs, complex multi-step business logic close to the data.

View

A saved query, not saved data — every time you select from it, the underlying SQL runs fresh.

Practical: hide join complexity, restrict which columns users can see.

Materialized view

A view's result, physically stored on disk, refreshed on a schedule or on demand.

Practical: expensive aggregations for dashboards — instant reads, data can be slightly stale.

A view costs nothing to store but pays the query cost every time; a materialized view pays once, up front, then serves reads for free until refreshed.
Replication: copies of the same data, for safety and scale

Sync: the leader waits for the follower to confirm the write — safer (no data loss on leader crash), but slower per write.

Async: the leader commits immediately and replicates in the background — faster, but a crash can lose the last few writes.

Practical: read replicas scale read traffic; a standby replica is what gets promoted to leader during failover.
Partitioning splits a table; sharding splits the machine

Partitioning — same server

One logical table, physically split into pieces (e.g. by date range: orders_2024, orders_2025) — the engine picks the right piece automatically.

Partitioning helps one server manage a huge table; sharding is how you scale past what any single server can hold at all — each shard is its own independent database.

Part 3
We treated I/O as a black box in Part 1. Now we open it — how the OS actually moves those bytes, at scale.
Blocking: your thread waits. Non-blocking: it asks and moves on

Blocking

read() doesn't return until data is ready — your thread is frozen, doing nothing, for however long the disk or network takes.

Cost: one thread per connection just to survive waiting.

Non-blocking

read() returns immediately — with data if it's ready, or an "EWOULDBLOCK" signal if it isn't. The thread is free to do other work.

Cost: now you need a way to know when to check again.

This is about whether the call itself waits — a separate question from whether the work happens synchronously or asynchronously.
Sync vs async: who does the waiting, and who gets notified
Most real systems mix them: non-blocking, asynchronous I/O — never wait, get notified — is what lets one thread serve tens of thousands of connections.
select / poll: ask the OS "which of these are ready?"
Simple and portable, but every call re-checks every socket — with 10,000 mostly-idle connections, that's 10,000 wasted checks per poll.
epoll: the kernel tells you what changed, not what to check
Practical: this is the mechanism under Nginx, Node.js, and every high-concurrency server — handling 100,000 connections on a handful of threads.
io_uring: skip the system call, share a ring buffer instead

Both sides read/write shared memory rings — no per-operation system-call trip into the kernel at all. Built for extreme I/O throughput (modern databases, storage engines).

epoll still needs a syscall per readiness check; io_uring batches submission and completion through shared memory, cutting that overhead close to zero.
So far…

select/poll, epoll, and io_uring all answer "how do I wait on many I/O sources efficiently?"

But every read still copies data: disk → kernel buffer → your app's buffer.

What if you just want to look at a giant file without ever fully loading it?

Skip the copy entirely — map the file straight into your address space.
mmap: treat a file on disk like an array in memory
Practical: mmap is how databases like SQLite and LMDB, and tools like grep on huge log files, avoid ever loading more than what's actually touched.
Zero-copy: stop routing data through your app just to forward it
Practical: this is how Kafka and Nginx serve files/messages at line rate — the kernel moves bytes disk-to-network directly, no wasted CPU copies.
A file descriptor: one handle, many kinds of "file"
Unix's core idea: "everything is a file" — the same read()/write() calls work whether the number on the other end is a disk file, a TCP connection, or a terminal.
TCP: reliable and ordered. UDP: fast and unordered

TCP

Handshake to connect, acknowledgements for every segment, automatic retransmission and re-ordering — the application always sees a clean, in-order byte stream.

Practical: HTTP, database connections, anything where losing or reordering data is unacceptable.

UDP

Fire-and-forget datagrams — no handshake, no guaranteed delivery, no ordering. Lower latency, less overhead.

Practical: video/voice calls, DNS lookups, game state updates — where a late retransmit is worse than a dropped packet.

Reliability isn't free — TCP trades latency and complexity for a guarantee; UDP hands that guarantee back to the application, or drops it entirely.
UTF-8: a variable-length encoding for every character on earth

Why variable-length: ASCII text (English) stays 1 byte per character — fully backward compatible — while the same encoding can still represent over a million code points by using more bytes when needed.

Code point vs byte: a "character" is a code point (a number); UTF-8 is one specific way to turn that number into bytes on the wire.

This is why "string length" is ambiguous in code — byte length, code-point count, and displayed-character count can all differ for the same string.
Endianness: which end of a number comes first

Why it matters: network protocols standardize on big-endian ("network byte order") so machines with different native endianness still agree on the wire.

Get this wrong across a network boundary and 0x12345678 silently becomes 0x78563412 — a classic, hard-to-spot serialization bug.
Recap — Part 3

Advanced I/O

Blocking vs non-blocking (does the call wait?) is a different axis from sync vs async (who gets notified?).

select/poll → epoll → io_uring is the story of the OS doing less repeated work per I/O event.

mmap and zero-copy both chase the same goal from a different angle: touch the data as few times as possible.

Everything ultimately rides on file descriptors, TCP/UDP, and a byte-level agreement on encoding and byte order.

One machine's I/O is fast now. But most real systems span many machines — and that's a very different set of problems.
Part 4
One server, one disk, one clock — Parts 1-3 quietly assumed all of that. Now we take it away.
Why anything other than a relational table?

Scale

spread data across many cheap machines instead of buying one bigger one

Flexible shape

not every dataset fits neatly into rigid rows and columns

Specialized access

graphs, time series, and full-text search all want different structures

NoSQL isn't "better" than relational — it's a different point on the trade-off curve, usually giving up some consistency or query power for scale or flexibility.
Key-value store: the simplest possible database

No schema, no joins, no query language beyond get/put/delete by key — in exchange, lookups are extremely fast and trivially shardable.

Practical: Redis (cache, sessions), DynamoDB (high-scale key-based lookups), etcd (config/coordination).
Document store: a whole nested object, in one record
{ "_id": "u101", "name": "Ana", "address": { "city": "Pune", "zip": "411001" }, "orders": [ { "item": "pen", "qty": 3 }, { "item": "book", "qty": 1 } ] }

Why it's different from 1NF

This entire nested structure lives in one document — no join needed to fetch a user with their address and orders together.

Trade-off: updating one order inside one user still means rewriting (or carefully patching) the whole document.

Practical: MongoDB, Couchbase — content catalogs, user profiles, anything naturally tree-shaped.

Document stores optimize for "give me this whole entity in one read" — the opposite instinct from normalization.
Column-family store: rows that don't all share the same columns

Sparse by design: each row can have wildly different columns — no wasted space storing NULLs for columns a row doesn't use.

Wide-column layout: data for the same column across many rows is stored together on disk, which makes scanning one column across millions of rows very fast.

Practical: Cassandra, HBase, Bigtable — huge write volumes, time-series and event data, sensor logs.

Not "a table with fewer columns" — a fundamentally different physical layout, optimized for massive, uneven, high-write datasets.
Graph database: relationships are first-class, not a join

Traversing "friends of friends who live in the same city" is a fast pointer-walk here, but a chain of expensive self-joins in a relational table.

Practical: Neo4j, Amazon Neptune — social networks, recommendation engines, fraud-ring detection, knowledge graphs.
So far…

Key-value, document, column-family, and graph stores each shape data for a different access pattern.

But all of them now run on many machines — and networks fail.

When two machines can't talk to each other, what should the database do: keep answering, or refuse until it's sure the answer is right?

That's not a bug to fix — it's a fundamental trade-off with a name: the CAP theorem.
CAP: pick two, during a network partition

Networks do partition — so P isn't optional. The real choice, when a partition hits, is CP (refuse rather than risk a stale answer) vs AP (answer, possibly stale).

Practical: traditional RDBMS clusters and etcd lean CP; DynamoDB and Cassandra default to AP — configurable per use case.
PACELC: the trade-off CAP doesn't mention

Even on a perfectly healthy network, waiting to confirm a write on every replica (consistency) costs latency versus acknowledging locally and replicating after (speed).

This is why "AP vs CP" isn't the whole story — a system still has to choose fast-but-maybe-stale vs slow-but-certain even when nothing has failed.
Strong consistency: every reader sees the same, latest value
The safest guarantee, and the most expensive — every read may have to wait on a slow or distant replica.
Eventual consistency: replicas agree — eventually
Practical: DNS, most CDN caches, DynamoDB's default mode — great when a brief stale read is harmless, wrong when it isn't (a bank balance, a stock ticker).
Causal consistency: cause always arrives before effect

Causal consistency guarantees this can't happen: if event B was caused by event A, every node that sees B has already seen A. Concurrent, unrelated writes can still be seen in different orders.

A middle ground between strong and eventual — cheaper than strong consistency, but keeps cause-and-effect from looking scrambled.
Quorums: how many replicas must agree?

N = total replicas, W = replicas that must confirm a write, R = replicas a read must consult. If W+R>N, every read is guaranteed to overlap the latest write on at least one replica.

Example: N=3, W=2, R=2 — write to any 2, read from any 2, and they must share at least one up-to-date replica.

Tuning W and R is tuning the CAP trade-off directly: higher W+R leans consistent and slower; lower leans available and faster.
Vector clocks: ordering events without a shared clock
Each node keeps a counter per node it knows about; comparing vectors tells you if one write happened-before another, or if they were truly concurrent and need reconciling.
So far…

CAP, consistency models, quorums and vector clocks all cope with an unreliable network for a single write.

But what about a transaction that must update two different databases — atomically — like Part 2's transactions promised, except now they're on different machines?

A single-machine COMMIT doesn't work across a network — you need an explicit protocol.
Two-Phase Commit: ask everyone, then tell everyone

Weakness: if the coordinator crashes after phase 1, participants are stuck holding locks, unsure whether to commit or abort.

Strongly consistent, but blocking — every participant must wait for the coordinator's final word before releasing its locks.
Saga: no global lock — just a plan to undo what went wrong
Each step commits locally and immediately; if a later step fails, the saga runs compensating actions backward instead of relying on a global lock.
So far…

2PC and Sagas both coordinate a transaction across multiple databases.

But a replicated database needs a more basic agreement first: which replica is the leader, right now, that everyone accepts?

If two replicas both think they're the leader, whose writes win?

That's the consensus problem — getting a group of unreliable machines to agree on one fact.
Paxos: the original proof that consensus is even possible

Once a majority agrees, the decision is safe even if the remaining minority is slow, offline, or lying — this is the core guarantee every practical consensus system builds on.

Famously correct, notoriously hard to implement and explain — which is exactly the gap Raft was designed to close.
Raft: Paxos's ideas, made understandable

Only the leader accepts writes; it appends to its log and replicates to followers, committing once a majority acknowledge. If the leader disappears, followers time out and hold a new election.

Practical: etcd (Kubernetes' backing store), Consul, CockroachDB — Raft is the "how" behind "who is the current leader" in most modern distributed systems.
Gossip: spread the news the way a rumor spreads
Practical: cluster membership and failure detection in Cassandra, DynamoDB, and Consul — no central coordinator, and it keeps working even as nodes join, leave, or fail.
Idempotency: why "exactly once" is really "at-least-once, done safely"

At-most-once

Send, don't retry. Simple, but a lost message is just... lost.

At-least-once

Retry until acknowledged. Guarantees delivery, but the same message may arrive twice.

Exactly-once (effectively)

At-least-once delivery + an idempotent receiver — applying the same message twice has the same effect as once.

Practical trick: attach a unique request ID; the receiver checks "have I already processed this ID?" before applying it.

True exactly-once delivery across a network is provably impossible — what real systems build instead is at-least-once delivery paired with idempotent processing.
Change Data Capture: turn every write into a stream of events

Downstream consumers (search index, cache, another database, analytics pipeline) subscribe to that stream instead of polling the database directly — they stay in sync without adding load to it.

Practical: Debezium + Kafka is the standard combo — sync a search index or a cache from a relational database without changing the application code.
Event sourcing & CQRS: store what happened, not just the result

Event sourcing

Instead of storing "balance = 300", store the full history: Deposited 500, Withdrew 200. The current state is just the replay of every event.

Gain: a full audit trail, and the ability to answer "what did the state look like last Tuesday?"

CQRS

Command Query Responsibility Segregation: use one model optimized for writes (append events) and a separate, differently-shaped model optimized for reads (a fast, denormalized view).

Practical: the two often pair up — events are the write model, materialized views are the read model.

Not free: replaying history to get current state costs compute, which is exactly why CQRS's separate read model usually accompanies it.
Recap — Part 4

Distributed Data & NoSQL

Different stores (key-value, document, column-family, graph) shape data for different access patterns, not "better" or "worse" than relational.

CAP/PACELC explain why consistency, availability, and latency trade off — never assume you can maximize all three.

Quorums and vector clocks are the mechanics of tuning that trade-off; 2PC and Sagas coordinate transactions across machines; Raft/Paxos get a cluster to agree on one truth.

Idempotency, CDC, and event sourcing/CQRS are the practical patterns that make all of this survivable in production.

Distributed systems are safe now. One question left: what actually happens inside a single database engine to make reads and writes fast?
Part 5
Back to one machine — but now we go under the query planner, into the storage engine itself.
Write-ahead log: log the intent before touching the real data

If the server crashes before the data page is updated: on restart, the engine replays the WAL from the last checkpoint — nothing acknowledged is ever lost.

This is what makes the "D" in ACID (Durability) possible without fsyncing the entire data file on every single write.
Checkpointing: bound how much log you'd ever have to replay
Without checkpoints, crash recovery would mean replaying the log all the way back to the beginning of time — checkpoints give recovery a recent, known-good starting point.
Buffer pool: keep the hot pages in memory
A cache miss here means an actual disk read — this is why database performance tuning so often comes down to "does the working set fit in the buffer pool?"
So far…

WAL, checkpoints, and the buffer pool all assume B+tree-style storage: update pages in place, on disk.

But updating a page in place means a random disk write — and random writes are far slower than sequential ones.

What if a storage engine's workload is almost all writes — can we avoid random writes entirely?

Yes — by never updating in place at all. That's the idea behind the LSM tree.
LSM tree: always append, never overwrite
Practical: Cassandra, RocksDB, LevelLB, and HBase all use LSM trees — the trade-off is reads that may need to check several SSTables instead of one B+tree descent.
Compaction: merge SSTables, reclaim space, keep reads fast

Without compaction, an ever-growing pile of SSTables would make every read slower (checking more files) and waste disk on stale, overwritten values.

A background trade: compaction spends I/O now so that both storage size and future read speed stay bounded.
Bloom filter: "definitely not here" in one cheap check

If any bit is 0

the key is definitely not in the set — skip the disk read entirely.

If all bits are 1

the key is probably present — a small false-positive rate is possible, so you still check.

Practical: every LSM-based engine keeps one bloom filter per SSTable, skipping the disk entirely for the vast majority of "key doesn't exist here" checks.
Connection pooling: don't pay setup cost on every query
Practical: PgBouncer, HikariCP — essential once an app serves enough traffic that "open a fresh connection per request" becomes the bottleneck itself.
Query caching: skip re-computing an answer you already know

The hard part isn't caching — it's invalidation: the cached result must be thrown out the moment the underlying data changes, or reads go stale.

Practical: Redis/Memcached in front of a database, or an ORM's built-in query cache — "the two hard problems in computer science: cache invalidation, naming things, and off-by-one errors."
Full-text search: an index built from words, not row order
"Inverted" because it flips the normal doc→words direction into word→docs — practical: Elasticsearch, PostgreSQL's built-in full-text search, Lucene.
Geospatial indexes: making "near me" fast
Practical: PostGIS (R-tree-based), Redis GEO commands (geohash-based) — both turn "find everything within 5km" from a full scan into a bounded region lookup.
OLTP vs OLAP: many small transactions vs a few huge scans

OLTP — transactional

"Update this one order's status." Many short, concurrent read/write transactions touching few rows.

row-oriented storageindexes for point lookups

Practical: the app database behind checkout, banking, booking.

OLAP — analytical

"What was total revenue by region, last quarter?" Few, heavy read-only queries scanning millions of rows.

column-oriented storageaggregation-optimized

Practical: Snowflake, BigQuery, Redshift — dashboards, reports, ML feature pipelines.

Column-oriented storage wins for OLAP because summing one column across 10 million rows only has to read that one column, not the whole row.
Star schema: one fact table, surrounded by dimensions
Deliberately denormalized dimensions make "revenue by product category by quarter" one simple join, not a five-table chain — this is warehousing's answer to Part 2's normalization.
ETL vs ELT: where does the transformation happen?
Modern warehouses (Snowflake, BigQuery) are fast and cheap enough to transform after loading — ELT lets raw data land immediately and be reshaped as many times as needed later.
Recap — Part 5

DB Internals & Modern Workloads

WAL + checkpointing + buffer pool make one engine both durable and fast; LSM trees, compaction, and bloom filters are the write-optimized alternative to updating B+tree pages in place.

Connection pooling and query caching remove overhead that has nothing to do with the actual query.

Full-text and geospatial indexes are B-tree/hash ideas specialized for words and coordinates.

OLTP and OLAP are different problems on purpose — star schemas and ETL/ELT exist to serve the analytical side well.
