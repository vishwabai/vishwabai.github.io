Design Patterns
23 named solutions to problems object-oriented programmers keep re-solving — grouped by what they control: creation, structure, or behavior.
A pattern is a name for a shape you already know
Two teams, two unrelated codebases, the same underlying shape — that's what earns a pattern its name. It's vocabulary, not code to copy-paste.
Part One — Creational Patterns
Five patterns that control how objects come into existence — so the rest of your code never has to say "new" and know too much.
Creational
Singleton — exactly one instance, guaranteed
Every caller asks for "the instance"; the class itself guards a private constructor and always hands back the same object.
Creational
Factory Method — let subclasses decide what to build
The base class calls an abstract "make" method; each subclass overrides it to produce its own concrete product.
Creational
Abstract Factory — build a whole matching family at once
One factory call returns a whole consistent set — a light button and light panel, or a dark button and dark panel, never a mismatched mix.
Creational
Builder — assemble something complex, one step at a time
Each call configures one piece; the same builder, driven in a different order, produces a different final object.
Creational
Prototype — clone an existing object instead of rebuilding it
Copying a live, already-set-up object is cheaper and safer than re-running a long, expensive construction process.
Bridge
RECAP → GAP: creational patterns get objects born. But once they exist, how do mismatched or tangled objects work together?
FILL: structural patterns — recipes for composing objects into larger, cleaner structures.
Part Two — Structural Patterns
Seven patterns that compose classes and objects into larger structures, while keeping those structures flexible and cheap to change.
Structural
Adapter — translate one interface into another
The adapter wraps the square plug and exposes a round-socket interface — neither original class changes a single line.
Structural
Bridge — split "what it is" from "how it's drawn"
Shape-type and render-style vary independently along two separate axes; a thin bridge connects one of each instead of multiplying subclasses.
Structural
Composite — treat one leaf and a whole tree the same way
Call render() on the root and it quietly cascades to every child — folders and files answer to the exact same method.
Structural
Decorator — wrap an object to add behavior, layer by layer
Each wrapper implements the same interface as the core and forwards to it — so any number of decorators stack invisibly.
Structural
Facade — one simple door in front of a messy subsystem
One clean call like start() hides a dozen coordinated subsystem calls the client no longer needs to know about.
Structural
Flyweight — share the expensive part, keep only what differs
A thousand trees on screen, one texture in memory — every instance stores only its own position, and points back at the shared core.
Structural
Proxy — a stand-in that guards the real thing
Same interface as the real object, but the proxy can check access, cache results, or delay creation before ever forwarding the call.
Bridge
RECAP → GAP: structure is composed. But how do objects talk, decide, and change their behavior at runtime?
FILL: behavioral patterns — recipes for communication, delegation, and responsibility between objects.
Part Three — Behavioral Patterns
Eleven patterns governing how objects interact, delegate work, and adapt their behavior without hard-wiring every detail.
Behavioral
Strategy — swap the algorithm, keep the caller unchanged
The context holds a reference to an interchangeable strategy object; changing which one is plugged in changes behavior with zero edits to the caller.
Behavioral
Observer — one change, broadcast to everyone watching
The subject doesn't know who's listening — it just calls notify(); every registered observer reacts independently.
Behavioral
Command — turn a request into an object you can queue or undo
The button never touches the receiver directly — it hands off a self-contained command object that can wait in a queue, log itself, or undo.
Behavioral
State — behavior changes because the internal state changed
Instead of one giant if/else on a status flag, each state is its own object — the light just delegates to whichever state object it currently holds.
Behavioral
Chain of Responsibility — pass it along until someone can handle it
Each handler decides: handle it and stop, or pass it to the next link. The sender never needs to know which one will respond.
Behavioral
Template Method — fix the skeleton, let subclasses fill one step
Steps 1, 3, and 4 are shared and final; step 2 is abstract — every subclass runs the same overall recipe but customizes one ingredient.
Behavioral
Iterator — walk a sequence without exposing how it's stored
The iterator carries the position; the collection could be an array, a tree, or a linked list underneath — the walking code never needs to know.
Behavioral
Mediator — replace a tangle of wires with one hub
N objects wired directly to each other is O(n²) connections; route every message through one mediator and it drops to O(n).
Behavioral
Memento — snapshot the state now, restore it later
The object hands its own state to a memento without exposing internals; later, that same memento can hand it right back — undo, made safe.
Behavioral
Visitor — add a new operation without touching the elements
Each element accepts the visitor and calls back the operation matching its own type — new operations arrive as new visitors, not edits to old classes.
Behavioral
Interpreter — represent a grammar as a tree of objects
Each grammar rule becomes a class; evaluating the sentence means walking the tree bottom-up, letting every node interpret only its own piece.
Twenty-three patterns, three questions
Creational asks "how is it born?" Structural asks "how does it fit with others?" Behavioral asks "how does it act and communicate?" Every pattern here is just a well-worn answer to one of those three.
