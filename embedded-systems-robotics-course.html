Embedded Systems in Robotics
⏱ ~2 hrs to mastery · full M.Tech syllabus scope

A robot's body needs

Embedded systems are the microcontrollers, protocols, and real-time code that sit between a robot's sensors and its motors — reading the world in microseconds and reacting before it's too late. This course covers the full two-year M.Tech arc: from registers to a working robot control stack.

01Foundations

A microcontroller isn't a tiny laptop. It's a tiny factory floor.

What you think

A microcontroller is basically a miniature computer — it boots an OS, and your code is one of several programs it juggles, like apps on a phone.

What's actually true

Most robotics microcontrollers (STM32, AVR, ESP32 in bare-metal mode) run no OS by default. Your code is the only program, starting the instant power turns on, with direct read/write access to hardware registers — the actual on/off switches for every pin and peripheral.

A microcontroller (MCU) packs a CPU core, a small amount of RAM, flash memory for your program, and a set of peripherals — timers, ADCs, communication interfaces — onto one chip. Unlike your laptop's CPU, which reads instructions and data from the same enormous pool of RAM, most MCUs use a Harvard architecture: separate paths for fetching instructions (from flash) and reading/writing data (from RAM), which is part of why they can execute so predictably.

Feynman analogy #1 — the factory floor

Think of a factory floor with a fixed set of levers bolted to the wall — one lever per machine. Pulling lever #14 always turns on the same conveyor belt; there's no ambiguity, no "which app is this lever for right now." A microcontroller's registers are those levers: each memory address is wired directly to a specific piece of hardware, and writing a 1 or 0 to it has an immediate physical effect.

Feynman analogy #2 — a chef with one recipe

Your laptop's OS is like a restaurant kitchen running dozens of orders at once, switching between them. A bare-metal MCU is a chef who received exactly one recipe and does nothing else, in the same order, every single time power is applied — which is precisely why it can guarantee "the motor will stop within 2 microseconds of this sensor triggering."

hover a memory region to see what lives there
Reveal the why — why "memory-mapped" I/O?
Rather than giving peripherals a separate instruction set, MCU designers assign each peripheral's control registers a specific address inside the same address space the CPU already uses for RAM. That means turning on an LED is literally just "write the value 1 to address 0x40020014" — the same kind of instruction the CPU uses to store any other variable. It keeps the instruction set small and lets a C pointer directly control hardware.
⚡ Common sticking point

Students coming from application programming expect digitalWrite(pin, HIGH) to be "how it works." That function is a convenience wrapper — underneath, it's setting one specific bit in one specific hardware register. When something misbehaves at the register level (a misconfigured clock, a wrong bit mask), high-level wrapper functions can't explain the bug; you have to drop down to the datasheet and the register map.

✍️ explain it back

In your own words: why can't you just treat a microcontroller like a small version of your laptop's CPU?

A laptop CPU runs an OS that schedules many programs and abstracts hardware behind drivers, at the cost of unpredictable timing. A bare-metal MCU runs one program with direct register access to hardware — no scheduler, no abstraction layer — which sacrifices flexibility for deterministic, guaranteed-timing control, exactly what a robot's real-time control loop needs.
✅ did you get it?
Key takeaway
  • Most robotics MCUs run bare-metal — your code is the only program, with direct register access.
  • Memory-mapped I/O means hardware control is just reading/writing specific memory addresses.
  • This directness is what makes deterministic, real-time control possible.
02Foundations

The real world is a wave. Your MCU only understands steps.

What you think

A sensor "sends a number" to the microcontroller, and an output pin can smoothly vary its voltage to drive a motor at any speed.

What's actually true

Sensors output continuously varying voltage, which an ADC chops into discrete numeric steps. And most MCU pins can only be fully on or fully off — "analog-like" output is faked by switching on and off very fast (PWM), not by producing in-between voltages.

An ADC (analog-to-digital converter) samples a voltage at regular intervals and rounds it to the nearest step out of, say, 4096 possible values (12-bit resolution) — coarser than reality, but good enough. Going the other direction, PWM (pulse-width modulation) switches a pin on and off rapidly; the fraction of time it's on (the duty cycle) determines the effective average voltage a motor or LED "feels," even though the pin itself never leaves 0V or 5V.

Feynman analogy #1 — a staircase approximating a ramp

A ramp rises smoothly; a staircase built next to it only rises in fixed steps. An ADC replaces the smooth ramp of real-world voltage with a staircase of discrete numbers — more steps (higher bit-depth) makes the staircase feel smoother, but it's never truly continuous.

Feynman analogy #2 — flickering a light to fake dimming

Wave a flashlight on and off faster than your eye can track, and it looks dimmer the less time it's on — even though each flash is at full brightness. PWM does exactly this to a motor: full voltage, rapidly pulsed, at whatever fraction of "on" time gives the effective average speed you want.

Reveal the why — why does higher ADC resolution matter for robotics?
A 10-bit ADC (1024 steps) reading a 3.3V sensor range can only distinguish voltage changes of about 3.2mV. If your sensor's meaningful signal — say, a subtle joint-torque change — is smaller than that step size, the ADC simply can't see it; it gets rounded away. Higher resolution (12-bit, 16-bit) narrows the step size, letting the system detect finer real-world changes, at the cost of more data to process per sample.
⚡ Common sticking point

People assume a higher PWM frequency is always better. Too low, and a motor audibly whines or visibly flickers (an LED). Too high, and switching losses in the driver transistor waste energy as heat, and some motor drivers simply can't switch that fast cleanly. Real designs pick a PWM frequency matched to the actuator — often 20kHz+ for motors (above human hearing) but much lower for some other loads.

✍️ explain it back

In your own words: how can a pin that's only ever fully on or fully off make a motor spin at half speed?

By switching the pin on and off very rapidly and controlling what fraction of each cycle it spends on (the duty cycle). The motor's own electrical and mechanical inertia smooths the rapid pulses into an effective average voltage — a 50% duty cycle behaves like a steady half-voltage supply, even though the pin itself is never at half voltage.
✅ did you get it?
Key takeaway
  • ADCs quantize continuous voltage into discrete numeric steps — resolution determines how fine that quantization is.
  • PWM fakes analog output by rapidly switching a digital pin; duty cycle sets the effective average voltage.
  • Both are approximations of the real, continuous physical world — and the approximation's coarseness has real design consequences.
03Intermediate

Chips don't just need wires. They need shared rules.

What you think

Connecting two chips is mostly a wiring problem — get the pins physically hooked up and data flows.

What's actually true

Without an agreed protocol, two chips wired together produce noise, not data. A protocol defines timing (when to read a bit), framing (where a message starts/ends), and often addressing (which of many devices on the same wires should respond) — the wiring is the easy part.

Four protocols cover most robotics wiring: UART (simple point-to-point, two wires, no shared clock — both sides must agree on speed in advance), SPI (fast, one controller + multiple devices, uses a shared clock line so timing is never ambiguous), I2C (only two wires total for many devices, using addresses instead of separate wires per device), and CAN (built for electrical noise and multi-node robustness — the standard for multi-controller robots and automotive systems).

Feynman analogy #1 — Morse code vs a phone call

UART is like two people agreeing in advance "we'll each tap out letters at exactly 1 tap per second" — no live signal tells you when a letter starts, you just have to count precisely. SPI is like a phone call with a metronome playing on a shared line — every tick, both sides know exactly when the next bit is meant to be read, which removes the timing-drift problem entirely.

Feynman analogy #2 — a classroom vs a hallway PA system

I2C is like a hallway PA system: one shared line where the announcer calls a specific room number ("attention, Room 42B") before speaking — every room hears everything, but only the addressed room acts. CAN is more like a classroom where anyone can raise a hand mid-lecture and the loudest, most urgent message automatically wins the floor (built-in priority arbitration) — critical for robots where multiple controllers need to talk without stepping on each other during a safety event.

click a protocol tab to see its wiring and timing style
Reveal the why — why does I2C need addresses but SPI doesn't?
SPI gives each device its own dedicated "chip select" wire — the controller physically activates only one device at a time, so there's never ambiguity about who's being spoken to, at the cost of needing more wires as you add devices. I2C instead puts every device on the same two shared wires and asks each one to listen for its own address embedded in the message — fewer wires, but it means every device needs a unique address and some silicon logic to recognize it.
⚡ Common sticking point

Students often ask "which protocol is best?" as if one wins outright. Each is a different tradeoff: UART is simplest but point-to-point only; SPI is fastest but needs more pins per device; I2C uses the fewest pins but is slower and needs addressing; CAN is the most robust to electrical noise and supports many nodes, but has the most protocol overhead. Real robots typically use all four for different subsystems — an IMU over I2C, a motor driver over SPI, a debug console over UART, and inter-board communication over CAN.

🔀 match the protocol to its defining trait
✍️ explain it back

In your own words: why can't two chips just be wired together and start exchanging data with no agreed protocol?

Without a shared protocol, neither chip knows when a bit starts or ends, how many bits make up one piece of data, or — if multiple devices share the same wires — who a given message is meant for. A protocol supplies the timing and framing rules both sides agree to follow, turning raw electrical pulses into structured, interpretable data.
✅ did you get it?
Key takeaway
  • A protocol defines timing, framing, and (often) addressing — not just wiring.
  • UART, SPI, I2C, and CAN each trade off pin count, speed, complexity, and noise robustness differently.
  • Real robots mix protocols, matching each to the subsystem's specific needs.
04Intermediate

"Real-time" doesn't mean fast. It means punctual.

What you think

A "real-time" system is just a very fast system — the more operations per second, the more "real-time" it is.

What's actually true

Real-time means deterministic: a guarantee that a task will finish within a fixed deadline, every single time — even if that means being slower on average. A blazing-fast system that occasionally misses a deadline by 50ms is not real-time; a modest system that always meets its 10ms deadline is.

An RTOS (Real-Time Operating System, e.g. FreeRTOS) lets a robot run several tasks that appear to happen "at once" — reading a sensor every 1ms, running a control loop every 5ms, updating a display every 100ms — by rapidly switching between them (preemptive scheduling), always giving priority to the most urgent task. Interrupts sit above even the RTOS scheduler: hardware events (like an emergency-stop button) that immediately pause whatever's running to handle something time-critical.

Feynman analogy #1 — an ER, not a queue at a bank

A bank teller serves customers first-come-first-served — fair, but not "real-time." An emergency room doesn't work that way: a patient with a heart attack is seen before someone with a splinter, no matter who arrived first. An RTOS scheduler works like the ER — it constantly re-evaluates who's most urgent right now and runs that task next, interrupting less urgent work if needed.

Feynman analogy #2 — a fire alarm during a meeting

No matter how important your meeting is, a fire alarm interrupts it instantly — you don't finish your sentence first. A hardware interrupt works the same way: even the highest-priority RTOS task gets paused the instant a flagged hardware event (a button press, a sensor threshold) fires, because some things genuinely cannot wait for the next scheduling decision.

step through a scheduling timeline — watch a high-priority task preempt a running one
Reveal the why — what is "priority inversion" and why do robotics engineers fear it?
Priority inversion happens when a high-priority task is stuck waiting for a resource (like a shared data buffer) currently locked by a low-priority task — and that low-priority task itself gets stuck behind a medium-priority task that has no reason to yield. The high-priority task effectively waits behind a lower-priority one, inverting the intended order. This has caused real spacecraft failures (famously, Mars Pathfinder) and is why RTOS designs include mechanisms like priority inheritance, where a low-priority task temporarily "borrows" high priority while it holds a resource a more urgent task needs.
⚡ Common sticking point

People assume "the highest priority task always runs" is the whole story, and are then confused when a system still misses deadlines. Task priority controls scheduling order among ready tasks — it says nothing about a task that's blocked waiting on a mutex, a peripheral, or another resource. Deadline misses are often about blocking and contention, not raw priority assignment.

✍️ explain it back

In your own words: what's the difference between "fast" and "real-time"?

"Fast" describes average or peak throughput — how many operations happen per second. "Real-time" describes a guarantee about worst-case timing — that a specific task will always complete within its deadline, no matter what else is happening. A system can be fast on average yet not real-time if it occasionally misses a deadline; a system can be real-time without being especially fast, as long as it's fast enough to always meet its guarantees.
✅ did you get it?
Key takeaway
  • Real-time = deterministic worst-case timing guarantees, not raw speed.
  • RTOS schedulers use priority to decide which ready task runs next; interrupts preempt even the scheduler for time-critical hardware events.
  • Priority inversion (a high-priority task blocked behind a lower one) is a real, historically documented robotics/spacecraft failure mode.
05Advanced

You cannot plug a motor into a microcontroller pin.

What you think

Since a GPIO pin can output PWM, you can drive a motor directly from that pin the same way you'd drive an LED.

What's actually true

An MCU pin can typically source only a few tens of milliamps. A small motor can draw hundreds of milliamps to amps, and switching it off generates a voltage spike (back-EMF) that can destroy the pin. Motors always go through a driver circuit — never directly to a GPIO pin.

A motor driver (commonly an H-bridge for DC motors) sits between the MCU and the motor: the MCU sends a low-current logic signal, and the driver switches high-current power from a separate supply to the motor. An H-bridge's four switches let current flow through the motor in either direction — forward, reverse, brake (short both terminals), or coast (disconnect) — controlled by which switches are closed.

Feynman analogy #1 — a light switch vs the power station

Flipping a household light switch doesn't send electricity from your finger — it closes a small, low-power circuit that tells a much larger power system to deliver current. A motor driver is that same relationship: the MCU pin is the light switch, the driver + separate power supply is the power station, and the motor is the load that actually needs the current.

Feynman analogy #2 — four gates on a canal

Picture a motor as water flowing through a canal with four gates arranged in an H shape. Opening the top-left and bottom-right gates lets water flow one direction; opening top-right and bottom-left reverses it; closing all four stops flow entirely. That's exactly the H-bridge: four switches (usually transistors) that route current through the motor in either direction, or stop it.

click a mode to see which H-bridge switches close
Reveal the why — why do servos and steppers not need an H-bridge the same way?
A hobby servo has its own small driver circuit and gearbox built in — it accepts a PWM signal that encodes a target angle, not raw motor power, so the MCU only needs to generate that timing signal directly. A stepper motor moves in discrete steps by energizing coil pairs in sequence; it typically uses a dedicated stepper driver IC that translates simple step/direction signals into the correct multi-coil switching pattern — different from an H-bridge's continuous-rotation forward/reverse control, but the same underlying principle: keep high current away from the MCU pins.
⚡ Common sticking point

Students forget that "brake" (both terminals shorted) and "coast" (both terminals disconnected) are physically very different, even though a motor looks "stopped" in both. Braking dissipates the motor's remaining kinetic energy quickly through electrical resistance, stopping it fast; coasting lets it spin down freely under friction alone. Choosing the wrong one in a real robot can mean the difference between a controlled stop and an arm swinging past its target.

✍️ explain it back

In your own words: why does a motor need a separate driver circuit instead of connecting straight to a GPIO pin?

A GPIO pin can only safely supply a small amount of current, far less than most motors draw, and switching a motor off can generate a damaging voltage spike. A driver circuit isolates the low-power MCU signal from the high-power motor circuit, using the MCU's signal only to control switches that route current from a separate, more capable power supply.
✅ did you get it?
Key takeaway
  • MCU pins output low-current logic signals; motors need high-current drivers between the pin and the motor.
  • An H-bridge's four switches select forward, reverse, brake, or coast for a DC motor.
  • Servos and steppers use their own dedicated drivers/logic, but the "keep high current off the MCU pin" principle is universal.
06Advanced

Telling a motor "go to 90°" isn't a command. It's a negotiation.

What you think

To move a robot arm to a target angle, you calculate the needed motor power once and apply it — the arm arrives and that's that.

What's actually true

Friction, load, and motor quirks mean a single calculated power rarely lands exactly on target. Real control is a continuous loop: measure the error, correct, measure again, correct again — dozens to thousands of times per second.

A PID controller computes motor output from three terms added together: Proportional (react to how far off you are right now), Integral (react to how long and how much you've been off, to kill persistent small errors), and Derivative (react to how fast the error is changing, to avoid overshooting). Tuning the three gains — Kp, Ki, Kd — is the art of balancing speed of response against stability.

Feynman analogy #1 — driving toward a stop sign

Proportional is like pressing the brake harder the closer you are to the stop sign — big error, big correction. Derivative is like easing off the brake as your speed drops fast, so you don't jerk to a stop. Integral is like noticing you've been creeping 2cm past every stop sign for the last mile and nudging your braking point slightly earlier to fix that persistent bias.

Feynman analogy #2 — adjusting shower temperature

Too little correction (low P) and you barely react to being cold, staying uncomfortable a long time. Overreact (high P with no D) and you swing from freezing to scalding, overshooting every time. A small constant offset that never seems to go away — always slightly too cold no matter what — is exactly what the I term is built to eliminate.

Reveal the why — why does too much Kp cause oscillation?
A high Kp means a large correction for even a small error. As the arm approaches the target, it's still being pushed hard, so it overshoots past the target — now the error flips sign, and the same high Kp pushes it hard back the other way. Without a derivative term to "see" the fast approach and ease off early, this can repeat indefinitely, growing or sustaining oscillation instead of settling.
⚡ Common sticking point

Students often add the integral term first because "it sounds like it fixes everything." In practice, Ki set too high causes a slow-building oscillation of its own (integral windup) — the accumulated error term keeps growing while the system is still catching up, then overshoots wildly once it finally moves. The conventional tuning order is P first (get roughly there), then D (damp the overshoot), then a small I only if a persistent steady-state error remains.

✍️ explain it back

In your own words: what job does each of the P, I, and D terms do?

P reacts to the current error's size — bigger error, bigger correction. D reacts to how fast the error is changing, easing off as the system approaches target to prevent overshoot. I accumulates error over time, correcting small persistent biases that P and D alone never fully eliminate.
✅ did you get it?
Key takeaway
  • Real control is a continuous measure-correct loop, not a one-time calculation.
  • P reacts to current error, D reacts to the rate of change (damping overshoot), I eliminates persistent steady-state error.
  • Tuning is a balance — too much P or I without enough D typically causes oscillation.
07Advanced

Two noisy sensors, combined well, beat one perfect sensor you don't have.

What you think

To combine readings from two different sensors (say, an accelerometer and a gyroscope estimating tilt), you just average their two estimates.

What's actually true

Different sensors have different, changing amounts of trustworthiness — a gyroscope is very accurate over short timescales but drifts over long ones; an accelerometer is noisy instant-to-instant but doesn't drift. Good fusion weights each sensor by how much to trust it right now, not a flat 50/50 average.

A Kalman filter is the standard tool for this: at every timestep, it predicts the next state from the system's known behavior, then corrects that prediction using a new sensor reading — weighted by how confident the filter currently is in its prediction versus the new measurement. That confidence (the "gain") is continuously recalculated, so the filter automatically leans more on whichever source is currently more trustworthy.

Feynman analogy #1 — two witnesses, one confident and one shaky

If one witness has given reliable testimony all day and another has been contradicting themselves, a good detective weighs the confident witness's account more heavily — not automatically 50/50. A Kalman filter does the same: it tracks each sensor's recent reliability and weights new information accordingly, rather than blindly averaging.

Feynman analogy #2 — a ship's dead reckoning, corrected by lighthouses

An old ship's navigator tracks position by dead reckoning (speed × time) — accurate moment to moment, but small errors accumulate into serious drift over hours. Spotting a lighthouse gives one noisy but drift-free position fix to correct that accumulated error. The Kalman filter's predict step is dead reckoning; its correct step is the lighthouse sighting — neither alone is as good as combining both.

watch the fused estimate (bold) track closer to true angle than either noisy sensor alone
Reveal the why — why not just use the gyroscope alone, since it's more precise moment to moment?
A gyroscope measures rate of rotation, not absolute angle — so estimating angle from it means continuously integrating (summing) that rate over time. Any tiny bias in the sensor accumulates with every summation step, and over seconds to minutes the estimated angle "drifts" further and further from the true value, even with a perfectly stationary sensor. The accelerometer, despite being noisy sample-to-sample, measures gravity's direction directly and has no long-term drift — fusing the two gets the gyroscope's short-term smoothness with the accelerometer's long-term stability.
⚡ Common sticking point

Students expect a "correct" fused value to appear immediately and stay put. In reality, a Kalman filter's confidence typically starts uncertain and narrows over the first several updates as it learns the sensor noise characteristics — the fused estimate is noisiest right after startup and settles as more measurements arrive. Judging filter quality from the very first few samples is a common and misleading mistake.

✍️ explain it back

In your own words: why is fusing two imperfect sensors usually better than trusting the "better" one alone?

Because different sensors tend to fail in different ways at different timescales — one may be noisy but drift-free, another smooth but prone to drifting over time. Combining them, weighted by how much to trust each one right now, cancels out each sensor's specific weakness using the other's specific strength, producing an estimate more reliable than either sensor alone across all timescales.
✅ did you get it?
Key takeaway
  • Sensor fusion weights sources by current trustworthiness, not fixed averaging.
  • Kalman filters alternate predicting (from known system behavior) and correcting (from new measurements).
  • Combining a drift-prone-but-smooth sensor with a noisy-but-drift-free one is a classic, powerful pairing (e.g. gyroscope + accelerometer).
08Expert synthesis

A robot isn't one chip. It's a distributed conversation.

What you think

All the embedded concepts you just learned live on one microcontroller running one program — ROS is just a fancy app layered on top.

What's actually true

A real robot is usually several MCUs and a higher-level computer talking over multiple protocols at once — a motor controller board on CAN, a sensor board on I2C, wireless telemetry over WiFi/Bluetooth, and ROS/ROS2 running on a Linux "brain" computer tying them all together as loosely-coupled communicating processes.

ROS/ROS2 (Robot Operating System) isn't an OS in the RTOS sense from Chapter 4 — it's a messaging middleware that lets independent programs ("nodes") publish and subscribe to data (sensor readings, motor commands) without needing to know about each other directly. A motor controller MCU still runs its own real-time bare-metal or RTOS code underneath — ROS typically sits at a higher level, on a more powerful onboard computer, orchestrating the overall behavior and talking down to the low-level boards over UART, CAN, or a network link.

▶ step through the sense–think–act loop
Feynman analogy — a ship's crew, not a single captain

A ship doesn't run on one person doing everything — a helmsman steers, a lookout watches, an engineer manages power, and the captain integrates their reports into decisions, each communicating over agreed channels (shouted orders, signal flags, intercom). A robot's distributed embedded system works the same way: specialized boards handle specialized real-time jobs, and a higher-level computer running ROS integrates their reports into overall behavior — no single point does everything, and each link uses whichever "channel" (protocol) fits that job.

Reveal the why — why not just run everything on one powerful MCU?
Splitting the system protects real-time guarantees. A motor's control loop (Chapter 6) needs a hard, predictable deadline every few milliseconds; running that on the same processor as heavier tasks like path planning or computer vision risks an occasional slow task blocking the time-critical loop (recall Chapter 4's priority inversion). Distributing work across dedicated boards, each running lean real-time code for its one job, keeps the safety-critical loops predictable while letting the "smart but sometimes slow" computation happen elsewhere without risking a stalled motor.
⚡ Common sticking point

Teams debugging "the robot behaves erratically" often start by tweaking the ROS-level planning code, when the fault is frequently upstream in the embedded layer — a dropped CAN message, an under-tuned PID loop oscillating, an I2C sensor occasionally timing out. Before touching high-level logic, check what the low-level boards actually reported: log raw sensor values, controller output, and communication error rates. Most "AI behaved weird" complaints in robotics are embedded-layer problems wearing a software-layer costume.

🌐 the unified mental model
✍️ explain it back

In your own words: walk through what happens, end to end, when a mobile robot's obstacle sensor detects something close and the robot needs to stop.

A distance sensor's analog or digital reading is sampled by its local MCU (via ADC or a protocol like I2C), which runs a real-time task or RTOS thread checking it against a threshold. If it's close enough to matter urgently, this can trigger a hardware interrupt or a high-priority task that directly commands the motor driver to brake — deliberately bypassing the slower ROS/planning layer for the safety-critical reaction. The event is also published as a message so the higher-level ROS system can log it, replan a path, or update its map, but the actual stop happens at the fast, deterministic embedded layer, exactly because that layer offers the timing guarantee a safety stop requires.
✅ final check
Key takeaway
  • Real robots are distributed systems: several MCUs plus a higher-level computer, communicating over multiple protocols.
  • ROS/ROS2 is messaging middleware at the planning/coordination layer — it doesn't replace real-time embedded code on individual boards.
  • Safety-critical reactions belong at the fastest, most deterministic layer available — usually embedded, not the high-level planner.

Embedded Systems in Robotics — Cheat Sheet

• Bare-metal MCU: one program, direct register/memory-mapped I/O access, no OS scheduler.
• ADC: quantizes continuous voltage into discrete numeric steps; resolution = step fineness.
• PWM: fakes analog output via rapid on/off switching; duty cycle = average effective voltage.
• UART/SPI/I2C/CAN: protocols trading off pin count, speed, addressing, and noise robustness.
• RTOS: preemptive task scheduling by priority; real-time = deterministic deadlines, not raw speed.
• H-bridge: four switches routing current through a DC motor — forward/reverse/brake/coast.
• PID control: P (current error), I (accumulated error), D (rate of change) — continuous correction loop.
• Kalman filter: predict from known dynamics, correct from new measurements, weighted by trust.
• ROS/ROS2: pub/sub messaging middleware coordinating distributed nodes, sitting above the real-time embedded layer.
• Debugging rule of thumb: an erratic robot is usually an embedded-layer problem first, a planning-layer problem second.
