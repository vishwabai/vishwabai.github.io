Security Architecture a Feynman walkthrough
Every secure system
answers four questions.
Twenty terms — OAuth, JWT, RBAC, TLS, zero trust — are really just answers to a small set of plain-language problems. Learn the problems, and the terms stop being jargon.
Q1

Who are you?

Authentication — proving identity.

Q2

What can you do?

Q3

Can it be read in transit?

Architecture — assuming breach.

We'll build the whole picture one gap at a time — starting with the oldest security system there is: a door.
Foundations Authentication vs. Authorization
Two different questions, one bouncer.
Notice these are independent checks. Your ID can be 100% real (authenticated) while you're still not on the list (unauthorized) — and a fake ID can occasionally slip past checkpoint 1 entirely. Systems keep these two checks separate for the same reason: one answers "is this really you", the other answers "what did we agree you're allowed to do."
RECAP — security architecture is mostly the discipline of answering "who" and "what" correctly, every single time.
GAP — but how does checkpoint 1 actually verify an ID is real and not forged? What makes proof, proof?
Authentication Proving who you are
FILLS: what makes proof, proof
Three kinds of evidence — and why one usually isn't enough.
🧠

Something you know

Password, PIN, security question. Cheap to deploy — but it can be guessed, phished, or reused across sites.

📱

Something you have

Phone, hardware key, one-time code (OTP). Stealing it requires physical access, not just a database leak.

👁️

Something you are

Fingerprint, face, iris. Hardest to fake at a distance — but can't be rotated if it's ever compromised.

MFA Multi-Factor Authentication = combine two different categories.

Password (know) + OTP from your phone (have) means an attacker needs both your leaked password and your physical phone. Two factors from the same category — two passwords — don't count; they fail together, from the same one breach.

Practical use: banking apps require know+have (password + SMS/OTP). High-security systems add have+are (hardware key + biometric unlock on the key itself). This is the theory of authentication — now, how does a website actually remember you passed this check, for every page you click afterward?
RECAP — authentication factors are evidence categories; combining different categories is what makes MFA strong.
GAP — you only log in once. So how does the server remember it's still you on request #2, #3, #4000? Why doesn't it ask again?
Authentication Staying logged in
FILLS: why it doesn't ask again
Session authentication: the server keeps a receipt.

The trade-off: the server must hold state for every logged-in user (a session table that grows with traffic), and that cookie is tied to one domain — it doesn't travel to a mobile app or a different company's API. Fine for one website. Awkward once "the client" isn't a browser at all.

RECAP — session auth swaps "ask for a password every time" for "remember a random ID, server-side, and check a cookie."
GAP — what about a mobile app or another server calling your API — no cookie jar, no browser. What proves who's calling then?
Authentication Machine-to-machine
FILLS: proof without a cookie jar
API keys: a long password the app carries, not a person.

Good fit for

Server-to-server calls, CLIs, webhooks, internal scripts — anywhere there's no human sitting at a login screen. Simple to issue, simple to check.

Weak points

Long-lived (leaks stay dangerous for months), usually all-or-nothing permission, and represents an app, not a specific end-user's consent.

RECAP — API keys authenticate a calling application, not a person, and grant it broad, static access.
GAP — what if a user wants a third-party app to act on their behalf — read their calendar, say — without ever handing over their password? How do you delegate, safely?
Authorization Delegated access
FILLS: delegating access safely
OAuth: a valet key, not your car key.
A valet key starts the engine and locks the glovebox. It can't open the trunk. It's a separate, limited credential — you never hand over your actual house key. That's the entire idea behind OAuth: issue apps a limited token instead of your password.
RECAP — OAuth defines four roles so an app can act with limited, revocable permission — never your actual password.
GAP — great, four roles. But what's the exact sequence of messages that gets a real app a real token? Walk through it — step by step.
Authorization OAuth 2.0 · Authorization Code Flow
FILLS: the exact sequence
Click Next to run the flow, one message at a time.

Why the detour through the browser (steps 1–3) instead of just sending a password? The password field only ever appears on the Authorization Server's own login page — the client app never sees it. And why exchange a short-lived code for a token in step 4, instead of returning the token directly in step 3? Because step 3 happens in the browser's address bar (visible in logs, browser history); step 4 happens server-to-server, over a channel that also proves the client's identity with a client_secret.

RECAP — six messages turn "user says yes" into a scoped, revocable access_token the client can use.
GAP — that access_token proves the app can read your calendar. It never says whose calendar, by name. How does the app learn who you actually are?
Identity OpenID Connect (OIDC)
FILLS: how the app learns who you are
OIDC = OAuth 2.0 + a name badge.
OAuth answers "can this app act?" — that's authorization. It was never designed to answer "who is this human?" OIDC is a thin identity layer bolted on top: add scope=openid to the same request, and the Authorization Server hands back a second token alongside the access token.
RECAP — OAuth = permission ("what the app can touch"), OIDC = identity ("who's logged in"). Different jobs, one flow.
GAP — we keep saying "token." What's actually inside one, and how does the resource server trust it without phoning the auth server every single request?
Identity / Tokens JSON Web Token (JWT)
FILLS: what's inside a token
A JWT is a fact, sealed, not stored.

Header

{ "alg":"RS256", "typ":"JWT" }

Which signing algorithm was used.

Payload (claims)

{ sub:"42", iss:"auth.co", exp:1893456 }

sub=who, iss=issuer, exp=expiry, aud=audience.

Signature

Cryptographic seal over header+payload. Change one character above, the seal breaks.

Formula signature = Sign( base64url(header) + "." + base64url(payload) , key, alg )

HS256 (shared secret both sides must hold — fast, single-service) vs RS256 (private key signs, public key verifies — many services can check a token, none can forge one).

RECAP — a JWT is a self-contained, signed fact. No session store, no database round-trip to check it — that's what "stateless" means.
GAP — stateless also means no easy way to revoke a token early, so keep it short-lived. But now: we know exactly who this is. That still hasn't decided what they're allowed to do — and checking that for every user, one by one, doesn't scale. What does?
Authorization models Role-Based Access Control
FILLS: deciding permissions at scale
RBAC: don't assign permissions to people — assign them to roles.
Rule access = grant, if
permission ∈ perms(role(user))

Practical: Admin / Manager / Employee in a company tool — easy to explain, easy to audit ("who's an Admin?"). The weak spot — "role explosion": the moment access needs a condition ("only your own documents," "only during business hours"), you either bend one role to mean two different things, or you mint a new near-duplicate role for every exception, until you have hundreds of roles that are really just if-statements wearing a role's name.

RECAP — RBAC maps user → role → permission. Simple, auditable, and static by design.
GAP — what if access should depend on context — whose document it is, what time it is, where the request is coming from? Roles alone can't express "it depends."
Authorization models Attribute-Based Access Control
FILLS: expressing "it depends"
ABAC: the answer is computed, not looked up.
Formula access = Policy( subject.attrs, resource.attrs, action, environment.attrs ) → allow | deny

RBAC

Static, coarse, cheap to audit. "Is this person an Editor?"

ABAC

Dynamic, fine-grained, harder to reason about at a glance. "Do these five facts, right now, satisfy the rule?"

RECAP — most real systems use both: RBAC for the coarse "which product area," ABAC for the fine "which specific record, right now."
GAP — we've now secured who and what. But none of it matters if the data is simply readable in transit. What stops someone from just watching the wire?
Cryptography Two different padlocks
FILLS: stopping someone reading the wire
Encrypt the pipe. Encrypt the warehouse. Two separate jobs.
🚚🔒

Encryption in transit

Protects data while it moves — browser to server, service to service. An eavesdropper on the network sees only scrambled bytes.

Mechanism: TLS (next slide)

Threat stopped: network sniffing, man-in-the-middle

Analogy: an armored truck for the drive

🏬🔒

Encryption at rest

Protects data while it's stored — on disk, in a database, in a backup. Stealing the hard drive gets you ciphertext, not the data.

Mechanism: AES-256 (symmetric cipher)

Threat stopped: stolen disks, leaked backups

Analogy: a locked warehouse once the truck arrives

Why you need both: TLS alone doesn't help if someone steals your database file directly. AES-at-rest alone doesn't help if the app decrypts data and then ships it over plain HTTP. Neither replaces the other — defense in depth, a theme we'll come back to at the very end.

RECAP — "in transit" defends the network hop, "at rest" defends the storage. Different attacker, different control.
GAP — TLS claims to build a private channel between two total strangers, over a public network, without ever sending the secret itself. How is that even possible?
Cryptography TLS — Transport Layer Security
FILLS: a secret shared, without sending the secret
The handshake: agree on a secret in public, in plain sight.

The trick (Diffie-Hellman key exchange): both sides send a public "key share" over the open network, and combine it with a private value they never send anywhere. The math works out so both land on the exact same shared number — but an eavesdropper watching both messages can't reconstruct it without one of the private values. The certificate in step 2 is what stops an impostor from just answering in the server's place: it's signed by a Certificate Authority the browser already trusts, binding "this public key" to "this domain name."

RECAP — TLS gives you confidentiality (encrypted), integrity (tamper-evident), and server identity (the certificate) — that's the padlock icon in your browser.
GAP — notice: only the server proved its identity with a certificate. In service-to-service calls, how does Service A know Service B isn't an impostor too?
Cryptography Mutual TLS (mTLS)
FILLS: proving both identities
mTLS: the handshake, but both sides show ID.

Practical use: service meshes (Istio, Linkerd) issue every internal service a short-lived certificate automatically, so microservices authenticate each other without ever sharing a static secret — no API key sitting in a config file that could leak. This is a core building block of zero trust networking (slide 17).

RECAP — regular TLS proves the server's identity. mTLS proves both. No implicit trust just because a call came "from inside the network."
GAP — even a perfectly encrypted, mutually-verified connection needs a secret somewhere — a private key, a DB password, an API key. Where do all those secrets actually live?
Operations Secrets Management
FILLS: where secrets actually live
Rule one: a secret never lives in source code.

Without a vault

Secret hardcoded in a config file → committed to git by accident → now permanently in the repo's history, visible to anyone who ever clones it.

With a vault

Every access is logged and authenticated; a leaked credential can be revoked centrally, in one place, in seconds — not hunted down across a codebase.

RECAP — secrets should be fetched at runtime, from an audited vault — never baked into code, images, or env files.
GAP — even a securely stored secret is dangerous if it never changes. If one leaks silently, it stays useful to an attacker forever. What limits that window?
Operations Key Rotation
FILLS: limiting the leak window
A secret's danger has a shelf life — shorten it on purpose.
Intuition, not a strict equation blast radius ∝ (secret lifetime) × (number of systems trusting it)

Why overlap matters: rotate instantly and every request signed with the old key fails until every service redeploys — an outage. Overlap both keys briefly instead, and rotation becomes invisible to users. Automated scheduling also removes the human habit of "rotate it later" — which in practice means never.

RECAP — shorter-lived secrets shrink the damage a leak can do, and scheduled rotation makes "shorter-lived" the default, not an emergency response.
GAP — we've now locked down identity, permissions, encryption, and secrets — but all of it quietly assumed there's still a trusted "inside" of the network. What if there isn't one?
Architecture Zero Trust
FILLS: no trusted "inside"
Never trust, always verify — even from inside the building.

Old model — castle & moat

Zero trust

Built from pieces you already know: mTLS (every hop proves identity), short-lived JWTs (every call carries fresh, checkable authorization), and least privilege, next. Zero trust isn't one new tool — it's the decision to apply all the earlier controls everywhere, not just at the edge.

RECAP — "inside the network" stops being a security boundary. Every single request re-proves identity and permission.
GAP — "verify every request" — verify against what rule? How much access should even a fully-verified request actually be handed?
Architecture Principle of Least Privilege
FILLS: how much access to grant
Grant the minimum needed for the task — nothing "just in case."

Scoped tokens

A read-only API key for a reporting dashboard, instead of the same admin key used everywhere.

Just-in-time elevation

Request admin access for 1 hour to fix an incident; it expires automatically — no standing "always-on" superuser.

Why it matters

If this credential leaks tomorrow, the attacker only gets the small green circle — not the whole red one.

RECAP — least privilege is zero trust's answer to "how much." Every credential is scoped as tightly as the task allows.
GAP — how do we even know which weaknesses to defend against with all this, before a single line of code is written?
Architecture Threat Modeling
FILLS: knowing what to defend against
Ask "what could go wrong here?" — before you build it.
STRIDE is a checklist for that question — six ways any component or data flow can fail — each one mapping straight back to a control from this deck:

Spoofing

Pretending to be someone else. → mitigated by authentication, mTLS.

Tampering

Altering data in flight or at rest. → mitigated by TLS, signatures, checksums.

Repudiation

Denying an action happened. → mitigated by audit logs, signed tokens.

Info disclosure

Data seen by the wrong party. → mitigated by encryption in transit / at rest.

Denial of service

Making the system unavailable. → mitigated by rate limits, scoped API keys.

Elevation of privilege

Gaining more access than granted. → mitigated by RBAC/ABAC, least privilege.

Practical use: before shipping a "share this document" button, walk it through all six letters as a team — design-time, on paper, cheap. Skip it, and you discover these gaps in production instead.

RECAP — threat modeling doesn't add a new control; it tells you which of the controls you already have actually apply, and where.
GAP — no single control on this list is unbreakable. If one layer fails, what stops the whole system from falling with it?
Architecture Defense in Depth
FILLS: what happens when one layer fails
No single layer has to be perfect — the stack does.
An attacker who slips past one ring — a phished password, say — still meets a next one: MFA, then scoped permissions, then a short-lived token, then an encrypted disk. Each layer assumes an earlier one might already have failed. That assumption is the whole philosophy.

The one-sentence version

Every term in this deck is one ring in this circle. Learn where each ring sits, and "security architecture" stops being twenty words to memorize — it's one picture with twenty labels.

RECAP — layers compensate for each other's blind spots; that's the entire justification for having so many controls at once.

Tying it together — Philosophy

Threat modeling tells you what to worry about. Zero trust says verify everything, everywhere, always. Least privilege says grant the smallest access that works. Defense in depth assumes every single one of those will occasionally fail anyway — and builds the next ring regardless.

The Feynman test for all of it: if you can't explain why RS256 exists instead of just HS256 everywhere, or why OAuth bothers with a redirect instead of just sending a token directly — go back one slide. Every design choice in this deck exists because of a specific gap it closes, not because it sounded secure.
You've walked the whole path: a door with two questions → proof of identity → delegated access → identity on top of that → encrypting the channel → granting the right amount of access → assuming failure anyway.
That's security architecture — not twenty things to memorize, one habit of asking "what's still missing?" applied twenty times.
