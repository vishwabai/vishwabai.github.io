Searching Algorithms

How do you find one thing inside a pile of things — fast? We'll build the answer from first principles, the way Feynman would: no magic, just the idea, and why it has to work.

Every app you use searches for something, constantly.
A phone book with a million names. A username database. A sorted log of a billion events.
How do you find one entry without reading all of them?
That single question — "how much do I have to look at?" — is the entire subject. Let's start with the dumbest possible answer, then earn our way to the smart ones.
RECAP: linear search checks every element — O(n), guaranteed correct, works on anything.
But if the data is already sorted, we know something about every element we haven't looked at yet.
Why check them one at a time — why not throw away half of them in a single comparison?
That's the entire idea behind binary search. One comparison, half the haystack gone.
WHY log n IS NOT JUST A FORMULA

Linear vs. Binary — growth, made visible

The gap doesn't just grow. It explodes. This is the entire reason binary search matters in practice.

n = 16 → linear needs up to 16 checks, binary needs 4.
RECAP: binary search finds an index where the target lives, in O(log n).
But real data has duplicates. Which occurrence did we find — the first? The last? What if the target isn't even in the array — where should it be inserted?
Binary search isn't one algorithm — it's a search strategy. Change what happens when you find a match, and you get a whole family of tools.
RECAP: binary-search patterns assume O(1) random access and a sorted array in memory.
What if the array is spread across slow, sequential storage? What if values are numeric and evenly spread out, so you could guess the position instead of guessing the middle? What if the array is unbounded — you don't even know where it ends?
Each of these constraints spawns its own specialized search. Same spirit — "throw away useless work" — different shape.
