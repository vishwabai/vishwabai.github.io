RESILIENCE PATTERNS · WHY

One Slow Service Can Kill Everything

Recap: a single slow dependency can exhaust threads upstream and take the whole system down with it. But— how do we stop a slow call from becoming an infinite wait in the first place?
RESILIENCE PATTERNS · 01

Timeout

↳ Answer: give every call a deadline. If it hasn't answered by then, stop waiting.
A timeout is a promise you make to yourself before you call anyone: "I will not wait forever." You pick a deadline; if the response hasn't arrived by then, you give up and move on — the call is cancelled, the thread is freed.
if (now - startTime) > deadline: abort(call)
Practical use
  • HTTP client: connect timeout 1s, read timeout 3s
  • DB driver: query timeout so one slow query can't freeze a pool
  • Without it: a hung dependency silently freezes your app too
Recap: a timeout stops one slow call from waiting forever. But— once you give up, do you just fail? Or try again? And if everyone retries at once...?
RESILIENCE PATTERNS · 02

Retry

↳ Answer: most failures are brief blips. Try again — a couple of times, not forever.
Networks blip. A pod restarts. A retry just repeats the same call, betting that the failure was transient. It only makes sense for operations that are safe to repeat (see: Idempotency, later) and it needs a cap — 2–3 attempts, not infinite.
for attempt in 1..maxAttempts: try: return call() except Transient: continue raise Failed
Practical use
  • Retry on: connection reset, 502/503, DB deadlock
  • Never retry on: 400 bad request, 401 unauthorized
  • Cap attempts — always pair with a timeout per attempt
Recap: retrying rides out short blips. But— if 10,000 clients all fail at once and all retry immediately, what happens to the service that's already struggling?
RESILIENCE PATTERNS · 03

Exponential Backoff

↳ Answer: don't retry instantly — wait longer after each failure, growing exponentially.
Instead of retrying every attempt at the same speed, you double the wait each time. Attempt 1 fails → wait 1s. Attempt 2 fails → wait 2s. Attempt 3 → 4s. This gives the struggling service breathing room that grows the longer it stays unhealthy.
wait = min(cap, base * 2^attempt) # base=1s → 1, 2, 4, 8, 16s...
Practical use
  • AWS SDKs, gRPC clients default to this for retries
  • Always set a cap — unbounded waits are their own bug
  • Still has a flaw: everyone's clock started at the same failure...
Recap: backoff spaces retries out exponentially. But— if every client failed at the same second, they all wait 1s, 2s, 4s... in lockstep. They still slam the server together. Now what?
RESILIENCE PATTERNS · 04

Jitter

↳ Answer: add randomness to the wait so clients spread out instead of retrying in lockstep.
Jitter breaks synchronization. Instead of waiting exactly 2^n seconds, each client picks a random value inside that window. Ten thousand clients now retry at ten thousand slightly different moments — a spread, not a spike.
wait = random(0, base * 2^attempt) # "full jitter" — AWS's recommended form
Practical use
  • This is why "thundering herd" incidents get named and studied
  • Always pair jitter with backoff — jitter alone has no growth
  • Together: retry + backoff + jitter is the standard trio
Recap: jitter spreads retries so they don't re-synchronize into another spike. But— retrying still assumes the service will recover soon. What if it's actually down hard? Do you keep hammering a corpse?
RESILIENCE PATTERNS · 05

Circuit Breaker

↳ Answer: stop calling entirely once failures cross a threshold — like a fuse tripping.
Named after the electrical fuse. The breaker watches recent call outcomes. Too many failures → it opens: calls fail instantly, no network hop wasted. After a cooldown it goes half-open — lets one test call through. Success → closes again. Failure → opens again.
failRate = fails / (fails+ok) if failRate > 0.5 over last 20 calls: state = OPEN (cooldown 30s)
Practical use
  • Netflix Hystrix, resilience4j, Envoy outlier detection
  • Protects the caller and gives the callee room to recover
  • Still leaves a hole: what protects shared resources from one bad caller?
Recap: a tripped circuit stops wasting calls on a dying service. But— if Service A calls three downstreams from one shared thread pool, and one of them is slow, can it still starve the other two?
RESILIENCE PATTERNS · 06

Bulkhead

↳ Answer: give each dependency its own isolated pool, so one flooded compartment can't sink the ship.
Named after ship design: a hull is split into watertight compartments so one puncture floods only one section. Applied to software: give each downstream call its own thread pool / connection pool / queue, sized separately, so a stuck dependency can only ever exhaust its own slice.
pool[serviceA] = 10 threads pool[serviceB] = 10 threads # A stuck ≠ B starved
Practical use
  • Separate connection pools per downstream DB / API
  • Kubernetes resource limits per pod = bulkheads at infra level
  • Now the caller is protected — but what protects the callee from too much traffic?
Recap: bulkheads isolate failure so it can't spread sideways. But— that protects against a slow dependency. What stops a flood of legitimate traffic from overwhelming a healthy service?
RESILIENCE PATTERNS · 07

Rate Limiter

↳ Answer: cap how many requests get through per unit of time — reject the rest before they do damage.
A rate limiter is a bouncer at the door: it decides in advance how many requests are allowed per second/minute, and turns away the excess — usually with a fast, cheap "429 Too Many Requests" instead of doing real work and failing later.
if requests_in_window > limit: return 429 # cheap rejection
Practical use
  • Public APIs: protect against abuse and runaway clients
  • Internal services: protect against your own retry storms
  • The exact counting method matters a lot — that's Section 2, in depth
Recap: a rate limiter caps traffic before it becomes a problem. But— what happens the moment traffic exceeds the limit anyway — do you just drop things at random?
RESILIENCE PATTERNS · 08

Load Shedding

↳ Answer: when overloaded, deliberately drop the least important work to protect the rest.
Rate limiting caps traffic at the edge; load shedding is the emergency valve inside the system when load still gets too high — e.g. CPU or queue depth crosses a red line. Instead of serving everything slowly (and risking a full collapse), you intentionally reject low-priority requests to keep high-priority ones fast.
if cpu > 90% or queueDepth > max: reject(lowPriorityRequest)
Practical use
  • Prioritize checkout over recommendations on an e-commerce site
  • Google/AWS load balancers shed based on queue depth, not just count
  • This shed decision is local — but what if the upstream keeps sending faster than we can even decide?
Recap: shedding sacrifices low-value work to save the system under load. But— shedding still means dropping requests. Could the system instead just ask the sender to slow down?
RESILIENCE PATTERNS · 09

Backpressure

↳ Answer: yes — signal upstream to slow down, instead of silently dropping or crashing.
Think of a kitchen sink: if water (requests) comes in faster than the drain (processing) can take it, the sink fills up. Backpressure is the drain telling the tap to slow down before it overflows — via a bounded queue, a "slow down" signal, or simply blocking the producer.
if queue.size >= capacity: producer.pause() # or block/reject
Practical use
  • TCP itself uses backpressure (receive window)
  • Reactive streams (RxJava, Kafka consumer lag) — bounded buffers
  • Cooperative, not adversarial — needs a producer willing to listen
Recap: backpressure pushes "slow down" upstream instead of failing downstream. But— what happens when a whole node dies, not just slows down? Nothing to signal to — the node is just gone.
RESILIENCE PATTERNS · 10

Failover

↳ Answer: when a node dies, redirect its traffic to a healthy replica automatically.
A failover is the handoff: traffic that was going to a dead or unhealthy node gets rerouted to one that's alive — a load balancer stops sending to it, a DNS record flips, or a standby gets promoted. The goal is that users barely notice.
if !healthcheck(primary): route(traffic, standby)
Practical use
  • Load balancer removes unhealthy instance from rotation
  • DB failover: standby promoted to primary on outage
  • Only as fast as your detection — which needs health checks (later)
Recap: failover reroutes traffic away from a dead node to a live one. But— should a struggling-but-not-quite-dead service keep trying to serve requests slowly, or refuse them outright?
RESILIENCE PATTERNS · 11

Fail-Fast

↳ Answer: refuse immediately when you already know you can't succeed — don't make the caller wait to find out.
If you already know a request can't be served — no DB connection available, a required field is missing, the circuit is open — reject it in microseconds. The alternative (queueing it, retrying internally, hoping) just delays an inevitable failure and wastes the caller's time and your resources.
if !preconditionsMet(): return error # now, not later
Practical use
  • Validate input before opening a DB transaction, not after
  • An open circuit breaker is a fail-fast decision
  • Fails fast on certainty — but what if success is merely unlikely, not impossible?
Recap: fail-fast rejects certain failure immediately instead of stalling. But— what about requests you can partially serve — just not fully? Do you have to choose between all or nothing?
RESILIENCE PATTERNS · 12

Graceful Degradation

↳ Answer: no — serve a smaller, simpler version of the feature instead of an all-or-nothing failure.
When a non-critical dependency is down, don't take down the whole page with it. Show the product page without "you may also like" if the recommendation service is unhealthy. Show cached prices if the live pricing service times out. The core experience survives; only the extras shrink.
try: return recommendations() except: return [] # page still renders
Practical use
  • Netflix: fallback UI when a personalization service is down
  • Serve stale cache instead of a blank error page
  • What if instead of degrading, you could hide latency entirely for critical paths?
Recap: degrade the extras, protect the core. But— for a request where tail latency truly matters, is there a way to avoid waiting on the one slow replica in the first place?
RESILIENCE PATTERNS · 13

Hedged Requests

↳ Answer: fire a second request to a different replica if the first is slow — take whichever answers first.
If a request hasn't come back after, say, the 95th-percentile latency, send the same request to a second replica. Whichever responds first wins; the other is cancelled or ignored. This trades a little extra load for a much shorter worst-case wait — it directly attacks tail latency.
wait(p95_latency) if !done: sendTo(replica2) return firstOf(r1, r2)
Practical use
  • Google's original paper: "The Tail at Scale" (2013)
  • Only send the hedge sparingly — it adds real load, use for p99 pain
  • Now — how does the caller even know a replica is worth calling at all?
Recap: hedging trades a little duplicate work for much better worst-case latency. But— how does anyone even know which replicas are alive and worth sending to?
RESILIENCE PATTERNS · 14 & 15

Health Checks & Heartbeats

↳ Answer: two ways to answer "is this node alive" — ask it, or let it tell you.
Health check = pull. Something else periodically asks "are you OK?" (an HTTP GET /health). Heartbeat = push. The node itself periodically announces "I'm still here" without being asked. Miss enough heartbeats → presumed dead.
// pull: every 5s → GET /health // push: every 5s → node emits I_AM_ALIVE // if no beat in 15s → mark dead
Practical use
  • Kubernetes liveness/readiness probes = health checks (pull)
  • Cluster membership (etcd, Consul, Cassandra gossip) = heartbeats (push)
  • Feeds directly into failover and load balancer routing decisions
Recap: liveness is detected by asking (health check) or listening (heartbeat). But— what happens to a message whose processing keeps failing, over and over, even with retries?
RESILIENCE PATTERNS · 16

Dead-Letter Queue

↳ Answer: after N failed attempts, park the message somewhere separate instead of retrying forever.
A message queue keeps retrying a failed message — but if it keeps failing (bad data, a bug, a permanently down downstream), it shouldn't block the whole queue forever. After a max-retry count, it's moved to a separate "dead-letter" queue: out of the way, but not lost, for a human to inspect later.
if attempts > maxRetries: moveTo(DLQ, message) ack(original) # unblock the queue
Practical use
  • SQS, RabbitMQ, Kafka all support DLQ configuration natively
  • Alert on DLQ depth — it's a leading indicator of a real bug
  • This assumes retrying is safe to do multiple times — is it?
Recap: a DLQ keeps one poison message from jamming the whole pipeline. But— we've been saying "just retry" for 16 slides. What if retrying the same request twice charges the customer twice?
RESILIENCE PATTERNS · 17

Idempotency

↳ Answer: design the operation so doing it twice has the exact same effect as doing it once.
"Set my balance to $50" is idempotent — run it 5 times, balance is still $50. "Add $50 to my balance" is not — run it twice by accident (e.g. a retry after a lost response) and you've charged double. The fix: attach a unique idempotency key to the request; the server remembers which keys it already processed and returns the same result without redoing the work.
if seen(idempotencyKey): return cachedResult else: result = doWork(); remember(key, result)
Practical use
  • Stripe, payment APIs: client generates a UUID per logical operation
  • PUT is idempotent by design; POST usually isn't — this is why
  • This is what makes retry, hedging, and at-least-once delivery safe
Recap: idempotency is the safety net that makes every retry, hedge, and re-delivery in this section actually safe to do. That's the resilience toolbox. One more look before we move to the next problem: how do you count requests precisely enough to rate-limit them?
RESILIENCE PATTERNS · RECAP

The Whole Toolbox, One Screen

Recap: 17 patterns, each answering a specific failure mode. But— "rate limiter" was one box above. How do you actually count requests fairly, in real time, across many servers? Time to go deep.
RATE LIMITING ALGORITHMS · 01

Fixed Window

↳ Section 2: the exact recipe for counting requests fairly.
Simplest idea: chop time into fixed blocks — e.g. every clock-minute — and count requests in a counter that resets to zero at each boundary. Cheap, easy, one integer per window. But watch the boundary: a burst right at the end of one window, plus a burst right at the start of the next, can slip 2× the limit through in a very short span.
windowKey = floor(now / windowSize) count[windowKey] += 1 allow = count[windowKey] <= limit
Practical use
  • Good enough for coarse, low-stakes limits
  • Flaw: burst of 2× the limit can cross a window boundary unblocked
  • Fix without full precision? Weight the previous window...
Recap: fixed window is cheap but leaks up to 2× the limit at the boundary. But— can we smooth that boundary spike without tracking every single request timestamp?
RATE LIMITING ALGORITHMS · 02

Sliding Window (Counter)

↳ Answer: blend the previous window's count into this one, weighted by how much it overlaps.
Instead of a hard reset, estimate the request rate over a window that "slides" continuously: take the current window's count, plus a fraction of the previous window's count proportional to how much that previous window still overlaps the trailing N seconds. It's an approximation — cheap like fixed window, but the boundary spike shrinks dramatically.
overlap = 1 - (now%windowSize)/windowSize estRate = prevCount*overlap + currCount allow = estRate <= limit
Practical use
  • Cloudflare, many API gateways use this by default
  • Two integers of state — almost as cheap as fixed window
  • Still an estimate. What if you need an exact count?
Recap: a weighted blend of two counters approximates a smooth sliding window cheaply. But— "approximately" isn't good enough for a strict contract. How do you count exactly, request by request?
RATE LIMITING ALGORITHMS · 03

Sliding Log

↳ Answer: keep the exact timestamp of every request, and count precisely within the window.
The precise version: store a timestamp for every request in a sorted log (e.g. a Redis sorted set). To check a new request, drop all timestamps older than "now minus window", then count what's left. Perfectly accurate — no boundary leak, no estimation — but memory grows with request volume, not with a fixed number of counters.
log.removeOlderThan(now - window) allow = log.size() < limit if allow: log.add(now)
Practical use
  • Exact, auditable limits — e.g. compliance-sensitive quotas
  • Cost: O(n) memory per client, not O(1) like counters
  • Precision solved. Now — what about bursts, not just averages?
Recap: sliding log is exact but memory-hungry — one entry per request. But— all three so far reject bursts outright. What if you want to allow a burst, as long as the average stays in check?
RATE LIMITING ALGORITHMS · 04

Token Bucket

↳ Answer: let requests spend saved-up "tokens" — bursts are fine as long as tokens exist.
Picture a bucket that refills with tokens at a steady rate (say, 10/second), up to a max capacity. Every request must take one token to proceed; no token, no entry. If nobody's called for a while, the bucket fills up — and the next caller can burst through many requests at once, spending saved tokens, until it's empty again.
tokens = min(capacity, tokens + elapsed*refillRate) if tokens >= 1: tokens -= 1; allow else: reject
Practical use
  • AWS API Gateway, Stripe API — the most common real-world limiter
  • Naturally allows short bursts, smooths to average rate over time
  • What if you want to forbid bursts entirely — a perfectly steady output?
Recap: token bucket allows bursts up to the saved balance, then throttles to the refill rate. But— is there an algorithm that enforces a constant output rate instead of just capping input?
RATE LIMITING ALGORITHMS · 05

Leaky Bucket

↳ Answer: yes — requests queue up and drain out at a fixed, constant rate, no matter how bursty the input.
Flip the mental model: instead of a bucket of permission-tokens, it's a bucket of water (requests) with a fixed hole in the bottom. Requests pour in at any speed; they leak out — get processed — at one constant rate. If they pour in faster than the leak rate for too long, the bucket overflows and new requests are dropped.
queue.push(request) # if not full every tick: process(queue.pop()) # constant rate
Practical use
  • Traffic shaping in networking, smoothing writes to a downstream DB
  • Token bucket = smooths permission; leaky bucket = smooths output
  • Both work per-server. What about a limit shared across 50 servers?
Recap: leaky bucket enforces a perfectly steady output rate regardless of input burstiness. But— all five algorithms so far assumed one counter on one machine. What happens with 50 API servers behind a load balancer?
RATE LIMITING ALGORITHMS · 06

Distributed Rate Limiting

↳ Answer: move the counter off each server and into a shared, fast store all servers agree on.
If each of your 50 servers keeps its own local counter, a client can get 50× the intended limit just by spreading requests across servers. The fix: store the counter centrally — usually Redis — so every server checks and increments the same count. The tradeoff is a network hop per check, and a small race window under extreme concurrency.
count = redis.INCR(key) redis.EXPIRE(key, windowSize) allow = count <= limit
Practical use
  • Redis + Lua script for atomic check-and-increment
  • API gateways (Kong, Envoy) ship this as a built-in filter
  • At extreme scale, many systems accept slight over-limit for lower latency
Recap: a shared store makes the limit real across every server, at the cost of one network hop per check. That's rate limiting solved. Next: what keeps the whole system up, not just one request?

03
Reliability &
Availability Patterns
Resilience protected one request. Rate limiting protected one service. This section zooms out to the whole system: how do you keep serving traffic when a machine dies — or a whole datacenter does?
RELIABILITY & AVAILABILITY · 01 & 02

Active-Active vs Active-Passive

↳ The first decision: should your backup node do work, or just wait?
Recap: active-active serves from every node and scales capacity; active-passive keeps a cheaper idle standby that takes over on failure, at the cost of a brief failover gap. But— if both nodes are "active" and both accept writes, what stops them from disagreeing about the data?
RELIABILITY & AVAILABILITY · 03

Leader-Follower

↳ Answer: elect one node the leader — only it accepts writes; everyone else just copies it.
One node is the leader: all writes go through it, in one agreed order. It streams those changes to followers, which apply them and can serve reads. If the leader dies, the followers (or an external coordinator) elect a new leader from among themselves. This avoids the "who's right" conflict of active-active writes.
write → leader.apply() → replicate(followers) read → leader | follower (if stale reads OK)
Practical use
  • PostgreSQL streaming replication, Kafka partition leaders, Raft/etcd
  • Reads from followers can be slightly stale — a real tradeoff to design for
  • This is one copy of the leader per machine — what if the whole machine class is redundant too?
Recap: one leader avoids write conflicts; followers give you read scaling and failover candidates. But— one leader on one machine is still one point of failure at the hardware level. How far do you spread copies?
RELIABILITY & AVAILABILITY · 04, 05 & 06

Redundancy, Zoom Out Twice

↳ Answer: redundancy is the principle — multi-zone and multi-region are how far you apply it.
Recap: redundancy = more than one copy. Multi-zone survives a datacenter outage; multi-region survives losing an entire region (fire, flood, regional outage). But— multi-region protects the running system. What protects the data itself if it gets corrupted or deleted?
RELIABILITY & AVAILABILITY · 07

Disaster Recovery

↳ Answer: DR is the overall plan for "everything is gone, now what" — not just replicas of the running system.
Multi-region keeps the live system running. Disaster recovery is the broader plan for the worse case — total data loss, ransomware, an operator deleting the wrong table. It's a documented, tested plan: what backups exist, how fast can you restore, and who executes the plan under pressure. A DR plan you haven't tested is a guess, not a plan.
DR plan = backups + replicas + runbook + practiced drills
Practical use
  • "Game days" — deliberately simulate an outage to test the runbook
  • DR strategy is measured directly by two numbers: RPO and RTO (Section 4)
  • The actual data-protection mechanisms are next — three distinct tools
Recap: DR is the tested plan for total loss, measured by how much data you'd lose and how long recovery takes. But— what are the actual mechanisms that let you restore data at all — and how are they different from each other?
RELIABILITY & AVAILABILITY · 08, 09 & 10

Backup vs Replication vs Point-in-Time Recovery

↳ Three different tools that all sound like "keep a copy" — but protect against different things.
Recap: backup = periodic snapshot (slow to restore, safe from live corruption); replication = continuous live copy (fast, but copies mistakes instantly too); PITR = replay logs to any exact moment (undo the mistake precisely). But— "fast to restore" and "recent data" — how do we put a number on that?
RELIABILITY & AVAILABILITY · RECAP

From One Machine to Every Region

Recap: reliability is redundancy applied at increasing scope — process, zone, region — backed by a tested recovery plan. But— how do you know, in hard numbers, whether any of this is actually good enough? Time for metrics.
04
Metrics
Every pattern so far was a design decision. Metrics are how you find out, in numbers, whether those decisions are actually working — and how much room you have left before they don't.
METRICS · 01

SLA, SLO, SLI

↳ Three letters, one relationship: measure it (SLI), target it (SLO), promise it (SLA).
SLI (Indicator) — the raw measurement: "99.95% of requests succeeded last month." SLO (Objective) — your internal target for that indicator: "we aim for ≥99.9% success." SLA (Agreement) — the external, often contractual promise, usually looser than the SLO, with real consequences (refunds) if missed. SLI feeds SLO; SLO is set stricter than SLA on purpose, as a buffer.
SLI = goodEvents / totalEvents SLO = internal target (e.g. 99.9%) SLA = external promise (e.g. 99.5%) + penalty
Practical use
  • Pick SLIs users actually feel: latency, error rate, availability
  • SLA should always be looser than SLO — the gap is your safety margin
  • Missing the SLO is a warning; missing the SLA costs money and trust
Recap: SLI measures, SLO targets, SLA promises — with SLO stricter than SLA as a buffer. But— if your SLO is 99.9%, exactly how much room for failure does that actually give you, in real numbers?
METRICS · 02

Error Budget

↳ Answer: 1 − SLO, turned into an actual spendable allowance.
If your SLO is 99.9% over 30 days, your error budget is the other 0.1% — about 43 minutes of downtime you're allowed to spend. Every incident spends from that budget. Spend it early? You've earned the right to slow down and stabilize instead of shipping risky changes — a genuinely useful governance tool, not just a vanity metric.
budget = (1 - SLO) * period # 0.001 * 30days = 43.2 minutes burnRate = errors_now / budget_rate
Practical use
  • Google SRE: budget exhausted → freeze risky launches until it recovers
  • "Burn rate" alerts catch fast-draining budgets before the month ends
  • Budget answers "how much room" — but how do you talk about failure frequency?
Recap: the error budget turns your SLO into a spendable number that governs release risk. But— a budget tells you how much failure is allowed — it doesn't say how often failures actually happen, or how long they last when they do.
METRICS · 03

MTBF & MTTR

↳ Answer: MTBF says how often it breaks; MTTR says how fast you fix it. Together, they set availability.
MTBF (Mean Time Between Failures) — average healthy time between incidents. Higher is better. MTTR (Mean Time To Recovery) — average time spent fixing an incident once it starts. Lower is better. Improving either one raises overall availability — and often MTTR is the cheaper lever to pull, since good tooling shortens every incident, forever.
availability = MTBF / (MTBF + MTTR) # 720hr MTBF, 2hr MTTR # = 720/722 = 99.72%
Practical use
  • Invest in monitoring/runbooks to cut MTTR — fast, cheap wins
  • Invest in redundancy/code quality to raise MTBF — slower, structural
  • These describe uptime in general — but what about the moment data is lost?
Recap: availability is a straight function of how often you break (MTBF) and how fast you recover (MTTR). But— "recovery" for a data-loss incident means something more specific: how much data did you lose, and how long until it's back?
METRICS · 04

RPO & RTO

↳ Answer: RPO is how much data you can afford to lose; RTO is how long you can afford to be down.
RPO (Recovery Point Objective) — the maximum acceptable data loss, measured in time: "we back up hourly" means an RPO of 1 hour. RTO (Recovery Time Objective) — the maximum acceptable outage duration before service is restored. These two numbers directly dictate which mechanism from Section 3 you need: backup, replication, or PITR.
RPO tight (~0) → needs replication RPO loose (~1hr)→ periodic backup OK RTO tight → hot standby, fast failover
Practical use
  • Bank ledger: RPO ≈ 0 (can't lose a transaction) → sync replication
  • Internal analytics DB: RPO of hours is often fine → nightly backup
  • These two numbers should be written down and agreed on before an incident
Recap: RPO and RTO turn "how resilient should we be" into two concrete numbers that decide your architecture. That's the full field guide. Let's connect every piece back into one picture.
