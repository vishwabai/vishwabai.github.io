FOUNDATIONS

Every system runs two different jobs at once

Deciding what should happen, and actually moving the data. They fail differently, so we build them differently.

The control plane is small, slow, and smart. The data plane is huge, fast, and dumb on purpose.
FOUNDATIONS

Formula: the data plane must survive without the control plane

Control plane pushes routes/config → data plane caches them → data plane keeps working even if control plane is down.

Practical: Kubernetes API server (control) vs kube-proxy forwarding packets (data); Istiod (control) vs Envoy sidecars (data).
RECAPA system splits decisions from data movement.
GAPBut who holds the actual data inside the data plane — and can we just copy that box to scale it?
FILLDepends if the service is stateless or stateful.
FOUNDATIONS

Stateless: clone it infinitely, nothing to synchronize

No memory between requests. Any instance can answer any request.

Throughput scales linearly: N identical instances ≈ N × capacity. Practical: stateless REST APIs, static web/CDN edges, pure functions/Lambda.
FOUNDATIONS

Stateful: the box remembers — so cloning isn't free

Each instance owns a slice of data. Route the wrong request there and it doesn't have the answer.

Needs sticky routing + replication to survive a node dying. Practical: databases, session stores, stateful stream operators (windows/aggregations).
RECAPState either lives inside the service or outside it.
GAPOnce the data is too big for one machine, how do many machines share it — CPU, disk, or memory?
FILLThree sharing models: shared-nothing, shared-disk, shared-memory.
FOUNDATIONS

Three ways to let machines share a workload

The difference is what's shared: nothing, the disk, or the memory itself.

Shared-nothing scales best (Cassandra, DynamoDB) · shared-disk keeps one copy of data (Oracle RAC) · shared-memory is fastest but caps out at one box (HPC, single big DB).
ISOLATION & BLAST RADIUS

Bulkhead: let one compartment flood without sinking the ship

Partition resources — thread pools, connections, queues — per dependency, so one slow caller can't starve the rest.

Formula: blast radius ≈ 1 / N compartments. Practical: separate thread pools per downstream API (Hystrix/Resilience4j), per-tenant connection pools.
ISOLATION & BLAST RADIUS

Cell-based: replicate the whole stack, not just a pool

Each cell = compute + queue + database, fully independent. A user is pinned to exactly one cell.

If Cell 3 fails, only its slice of users feels it — never 100% of traffic. Practical: AWS's own cell-based services, sharded SaaS backends.
RECAPBulkheads isolate resources; cells isolate whole stacks.
GAPWhat if the boundary isn't infra at all — it's which team owns which piece?
FILLIsolate at the organizational boundary: federated architecture.
ISOLATION & BLAST RADIUS

Federated: independent domains, joined by a shared contract

Each domain owns its data and deploys on its own schedule. A gateway composes them for the caller.

Practical: GraphQL Federation (each team owns a subgraph), federated identity/SSO across companies, federated learning (models trained locally, only updates shared).
GEOGRAPHIC RESILIENCE

A single region is one blast radius: the whole planet is your target

Spread the same system across regions so a data-center, power, or network failure isn't global.

Cost: cross-region replication latency (often 50–150ms) and real infrastructure spend. You buy resilience with latency and money.
GEOGRAPHIC RESILIENCE

Active-Passive: one region works, the other waits

Standby region stays warm, replicating data, until a failover promotes it.

Simple to reason about, consistent — but RTO (recovery time) is the failover duration. Practical: primary-DB + warm standby, DR sites.
GEOGRAPHIC RESILIENCE

Active-Active: both regions serve traffic, all the time

No idle standby — but now two regions can accept conflicting writes at once.

Near-zero RTO, near-zero RPO — you pay for it with conflict resolution (last-write-wins, CRDTs, vector clocks). Practical: multi-region DynamoDB global tables, CDNs.
RECAPRegions trade latency/cost for survival against total outages.
GAPInside one region, a single request also has a choice: answer fast and rough, or slow and exact — why not both?
FILLSplit the hot path from the cold path.
DATA FLOW & TIMING

Hot path = fast & approximate. Cold path = slow & exact.

Serve the user from the hot path immediately; let the cold path correct the record later.

Practical: a live view-counter shown instantly (hot) is reconciled overnight by an exact batch job (cold) for billing/analytics.
DATA FLOW & TIMING

Lambda architecture: run both paths, merge at the end

Batch layer computes the accurate view; speed layer fills the gap until batch catches up.

Formula: answer = batch_view ⊕ realtime_view at the serving layer. Trade-off: you now maintain two codebases doing the same logic.
DATA FLOW & TIMING

Kappa: delete the batch layer, replay the log instead

One stream pipeline only. To "reprocess," rewind the log and run it again with new logic.

One codebase, one mental model. Practical: Apache Kafka's long-retention log + stream processors (Kafka Streams, Flink) — proposed by Jay Kreps as Lambda's simpler sibling.
RECAPKappa treats the event log as the one source of truth.
GAPIf events are the real truth, why do most apps still model "current state" as the thing they read and write?
FILLSeparate them: CQRS and Event Sourcing.
STATE & HISTORY

CQRS: writing and reading are different jobs — stop forcing one model to do both

Commands go to a write model optimized for validation. Queries go to a read model optimized for shape and speed.

Read model is often eventually consistent — updated a moment after the write. Practical: write to normalized SQL, project into denormalized Elasticsearch/Redis for reads.
STATE & HISTORY

Event Sourcing: don't store the state — store every change

Current state is just a replay of history. Nothing is ever overwritten or lost.

Formula: state = reduce(events, apply, initial). Practical: bank ledgers, audit trails, "what was the balance last Tuesday" time-travel queries.
RECAPEvents pile up as an ever-growing, ordered history.
GAPDo we process that history the instant it arrives, or wait and process it in chunks?
FILLStream vs batch processing.
PROCESSING MODELS

Stream processing: the data never stops arriving

Each event is handled the instant it shows up — often within a sliding time window.

Latency: milliseconds. Practical: fraud detection, live dashboards, Flink/Kafka Streams windowed aggregation.
PROCESSING MODELS

Batch processing: let it pile up, then crunch it all at once

Bounded chunks, run on a schedule — trading latency for throughput and simplicity.

Latency: hours, throughput: huge. Practical: nightly billing runs, data-warehouse ETL, Spark batch jobs.
PROCESSING MODELS

MapReduce: the recipe behind most big batch jobs

Split the data, map it in parallel, shuffle by key, reduce each key's group.

Formula: map(k1,v1)→list(k2,v2) then reduce(k2,list(v2))→v3. Practical: classic word-count, log aggregation, Hadoop/Spark jobs.
RECAPMapReduce splits one big job into parallel pieces.
GAPBeyond one framework — how does any request or event actually fan out to many workers and come back together?
FILLScatter-gather, fan-out/fan-in, work stealing, and the scheduler that assigns it all.
WORK DISTRIBUTION

Scatter-Gather: one request in, one merged answer out

A coordinator scatters the same query to many workers, then gathers and combines their partial results.

Latency = slowest worker (the "straggler" problem). Practical: search engines querying many shards, price-comparison aggregators.
WORK DISTRIBUTION

Fan-out feeds many; fan-in collects from many

Fan-out: one event copied to every interested consumer. Fan-in: many producers write into one stream.

Practical: fan-out = pub/sub topic to many services (order placed → email, inventory, analytics); fan-in = many microservices logging into one Kafka topic.
WORK DISTRIBUTION

Work Stealing: idle workers steal from busy ones

Each worker has its own queue. An empty worker steals a task off the tail of someone else's queue instead of sitting idle.

Self-balancing — no central coordinator needed. Practical: Java's ForkJoinPool, Go runtime scheduler, Rust's Tokio executor.
WORK DISTRIBUTION

Distributed Scheduler: someone still has to place the work

Matches pending jobs to nodes based on capacity, constraints, and priority — before any stealing or scattering can happen.

Practical: Kubernetes scheduler (bin-packs pods onto nodes by CPU/memory requests), YARN, Mesos, Borg (Google's original inspiration for Kubernetes).
RECAPActive-active needed every region to accept writes — with conflict resolution.
GAPWhat if there isn't even a "leader" node to coordinate those writes in the first place?
FILLLeaderless architecture — any replica can accept a write.
TOPOLOGY

Leaderless: no single node decides — quorums do

Any replica accepts reads and writes. Correctness comes from overlapping quorums, not from asking one boss.

Formula: R + W > N guarantees a read overlaps a prior write. Practical: Amazon Dynamo, Cassandra, Riak — the engine behind true active-active.
RECAP

Every pattern answers one of four questions

Twenty-five names, four underlying axes.

Isolation → bulkhead/cell/federated · Geography → multi-region/active-active/passive · Timing → hot-cold/lambda/kappa/stream/batch · Coordination → CQRS/ES/scatter-gather/fan-out-in/work-stealing/scheduler/leaderless.
