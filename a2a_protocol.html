OPEN PROTOCOL · GOOGLE / LINUX FOUNDATION
Agent2Agent
How independent AI agents discover each other, hand off work, and get it done — without ever seeing inside one another.
THE PROBLEM
Every agent lives on its own island
No shared way to say "here's what I can do", or "here's a task, go do it."
THE INSIGHT
The web solved this once already
A2A is not a new invention — it's HTTP, JSON-RPC and SSE, arranged into a contract that agents agree to follow.
TWO DIFFERENT WIRES
A2A is horizontal. MCP is vertical.
both, layered together.
DEFINITION
A2A in one sentence
An open, vendor-neutral protocol that lets independent agents discover each other's capabilities, delegate tasks, and exchange results — while staying completely opaque about how they work internally.
SIMPLE
Reuses the web
HTTP, JSON-RPC 2.0, SSE — no new transport layer to invent or debug.
ASYNC-FIRST
Built for long tasks
A task can take seconds or days, and may need a human in the loop.
OPAQUE
No shared internals
Agents exchange declared capabilities and results — never prompts, memory, or tools.
MODALITY AGNOSTIC
Any content type
Text, files, structured data, even embedded UI — all as typed "Parts".
ENTERPRISE READY
Auth built in
TLS, OAuth2, JWT and tracing are first-class, not an afterthought.
GOVERNANCE
Linux Foundation
Apache 2.0, vendor-neutral, backed by 150+ organizations.
THE VOCABULARY
Five nouns. That's the whole protocol.
BUILDING BLOCK 1
The Agent Card: a business card for robots
No handshake, no SDK lock-in — just a plain JSON document fetched over HTTPS. That's the whole discovery step.
ANATOMY
What's actually inside a card
agent-card.json
{
  "name": "invoice-agent",
  "description": "Reads, validates and files invoices",
  "url": "https://agents.acme.co/invoice",
  "version": "1.0.1",
  "capabilities": { "streaming": true, "pushNotifications": true },
  "securitySchemes": { "oauth2": { "type": "oauth2" } },
  "skills": [
    { "id": "validate-invoice",
      "description": "Checks totals, tax and vendor ID",
      "inputModes": ["application/pdf"],
      "outputModes": ["application/json"] }
  ]
}
Skills are the granular list of "things I can actually do" — a router agent reads this to decide who to call.
BUILDING BLOCK 2
The Task: one unit of delegated work
A single contextId can span many related tasks — think of it as the thread a whole conversation lives in.
STATE MACHINE
Every task walks the same eight states
Only completed / failed / canceled / rejected are final. Everything else can still move.
BUILDING BLOCK 3
Messages are envelopes. Parts are the contents.
One message can mix all three — a sentence, a form, and an attached PDF, in a single turn.
BUILDING BLOCK 4
Artifacts: the thing you actually wanted
Artifacts can stream in incrementally — a report can grow chunk by chunk before the task even finishes.
THE WIRE
Under the hood: plain JSON-RPC 2.0
POST https://agents.acme.co/invoice
{
  "jsonrpc": "2.0",
  "id": "req-01",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [{ "kind": "text", "text": "Validate this invoice" }]
    }
  }
}
One HTTP endpoint, one method name, one params object. message/send, tasks/get, tasks/cancel are the core verbs.
STREAMING
message/stream: watching the task think
No polling loop needed — the agent pushes every state change and artifact chunk down one open connection.
LONG-RUNNING TASKS
When the task outlives the connection
Same idea as a webhook: register once, get called back — instead of holding a connection open for a task that runs overnight.
SECURITY
Enterprise auth, not an afterthought
TRANSPORT
TLS everywhere
HTTPS is mandatory in production. Plain HTTP is a v0.1 development convenience only.
IDENTITY
OAuth2 + JWT
The Agent Card's securitySchemes field advertises exactly which flows it accepts.
SCOPE
Per-skill authorization
A client is authorized for specific skills, not blanket access to the whole agent.
RUNTIME
auth-required state
A task can pause mid-flight and ask for a fresh credential before continuing.
TRACEABILITY
Correlated IDs
taskId and contextId flow through logs for end-to-end tracing across agent hops.
EXTENSION
Secure Passport
An official extension for propagating verified identity across a multi-agent chain.

Publish your Agent Card

  "url": "https://agents.acme.co/refund",
  "version": "1.0.0",
  "capabilities": { "streaming": true },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    { "id": "process-refund",
      "description": "Issues a refund for an order id" }
  ]
}
This one static file is what makes your agent discoverable by anyone speaking A2A.
IMPLEMENTATION · STEP 2
A minimal A2A server (Python)
server.py — using the a2a-sdk
from a2a.server import A2AServer
from a2a.types import AgentCard, AgentSkill, TaskState

skill = AgentSkill(id="process-refund", description="Issues refunds")
card  = AgentCard(name="refund-agent", skills=[skill])

class RefundExecutor:
    async def execute(self, context, event_queue):
        order_id = context.get_text_part()
        # ... do the actual refund logic here ...
        await event_queue.enqueue(TaskState.working)
        result = refund(order_id)
        await event_queue.enqueue_artifact(result)
        await event_queue.enqueue(TaskState.completed)

app = A2AServer(agent_card=card, executor=RefundExecutor())
app.run(port=8080)
IMPLEMENTATION · STEP 3
Calling it from another agent
client.py
from a2a.client import A2AClient

client = await A2AClient.get_client_from_url(
    "https://agents.acme.co/refund"  # fetches the Agent Card first
)

response = await client.send_message({
    "role": "user",
    "parts": [{ "kind": "text", "text": "Refund order #4471" }]
})

async for event in client.send_message_streaming(response.task_id):
    print(event.state, event.artifact)
The client never imported anything from the refund agent's codebase — only its Agent Card.

BEFORE YOU SHIP
The production checklist
01
Idempotent handlers
Retries will happen. The same message/send twice must not double-charge a card.
02
Token downscoping
Don't hand a delegated agent your full credential — scope it to the one skill it needs.
03
Timeouts & cancellation
Always support tasks/cancel — a runaway agent shouldn't burn compute forever.
04
Observability
Propagate taskId / contextId into your traces — multi-agent bugs live across hops.
05
Schema validation per skill
The spec doesn't standardise each skill's input shape — you must validate it yourself.
06
Rate limits & backpressure
A popular agent becomes everyone's dependency — protect it like any public API.
07
Versioned Agent Cards
Bump version and keep old skill ids alive during a migration window.
08
Human-in-the-loop UX
Design what happens when a task sits in input-required for hours, not seconds.
09
Registry / discovery strategy
There's no official global registry yet — decide how agents will find each other at scale.
HONEST LIMITATIONS
What v1.0 still leaves to you
The protocol is stable, not finished. Governance and edge-case behavior are still actively being worked out.
RECAP
A2A, end to end
Card → Task → Message/Part → Artifact. Everything else in the spec exists to make those four steps safe at enterprise scale.
