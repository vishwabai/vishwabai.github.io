FOUNDATIONS

Some questions don't need an exact answer

Has this URL been seen before? Roughly how many unique visitors today? Is this the top-selling item? None of these need a perfect record of every item — just a trustworthy estimate.

A normal set stores every item it has ever seen. Watch what happens to its memory as the count climbs — then watch what a sketch does instead.
FOUNDATIONS

You can't maximize memory, speed and certainty together

Every structure on this deck sits somewhere on this triangle. Exact structures anchor one corner. Everything we build today deliberately gives up a little certainty to win big on the other two.

That single trade — a little uncertainty for a lot of space and speed — is the one trick behind all fifteen structures. Only the details of how change.

BLOOM FILTERtrade certainty for space — answer "maybe" instead of "yes"
BLOOM FILTER

Represent a whole set with a handful of bits

A Bloom filter is just a bit array of size m, all zeros. To insert an item, run it through k independent hash functions and flip the bits they point to on.

Notice: we never stored "apple" anywhere. We only remember which bits its hashes touched. That's the entire trick.
BLOOM FILTER

Query: all-ones means "maybe", one zero means "definitely not"

To check membership, hash the query the same way and look at those k bits. If even one is still 0, the item was never inserted — guaranteed.

A Bloom filter can say "definitely not present" with 100% confidence, but can only ever say "probably present" — never a guaranteed yes.
BLOOM FILTER

False positives: two items can turn on the same bits

This is the price of compression. "apple" and "mango" together happened to set bit 9. A totally different word, "kiwi", might hash to bits that are all already on — a false positive.

P(false positive) ≈ (1 − e−kn/m)k. More bits per item (m/n) or a tuned k drives this down — it never reaches zero.
BLOOM FILTER

A filter that can never forget

In production: Chrome Safe Browsing (malicious URL check) · Cassandra/HBase (skip disk reads for missing keys) · Medium/Akamai request de-duplication · Bitcoin SPV wallets

RECAP
A Bloom filter answers membership in O(1) time using a handful of bits per item, with zero false negatives.
GAP
but bit 9 belongs to both "apple" and "mango" now — if we delete "apple" and flip that bit back to 0, what happens to "mango"?
NEXT
COUNTING BLOOM FILTERgive every bit some breathing room instead of just one
COUNTING BLOOM FILTER

Replace each bit with a small counter

Same k hash functions, same array size — but every slot is now a 4-bit counter (0–15) instead of a single bit. Insert increments; delete decrements.

Now deleting "apple" only lowers shared counters — it never wipes out "mango"'s claim on that slot.
COUNTING BLOOM FILTER

Deletion isn't free

In production: Squid web cache eviction · peer-to-peer systems tracking dynamic membership · distributed caches needing add + remove

RECAP
Counters let us delete items safely, at roughly 4× the memory of a plain Bloom filter.
GAP
but we're still burning a full counter for every slot even when most counters are 0 or 1 — can we get deletion and better space efficiency?
NEXT
CUCKOO FILTERstore a fingerprint of the item instead of touching many shared bits
CUCKOO FILTER

Store a short fingerprint in one of two buckets

Hash the item to get bucket A, and derive a small fingerprint (e.g. 8 bits). Bucket B is computed as A XOR hash(fingerprint) — so the item can always be found from either bucket.

This is the same idea behind cuckoo hashing: every item has exactly two possible homes, computed independently of each other.
CUCKOO FILTER

When both buckets are full, kick a neighbor out

If bucket A and bucket B are both full when inserting, evict a random existing fingerprint from A, and re-insert it into its own alternate bucket. Repeat until something lands.

This "cuckoo kick" is why buckets stay nearly full (95%+ load) without ever needing chaining or extra pointers — and it's also why a full table can occasionally fail to insert.
CUCKOO FILTER

A fingerprint compare beats a counter check

False positive rate depends only on fingerprint size f and bucket size b (entries per bucket): ≈ 2b / 2f. No hashing per query bit — just compare stored bytes.

For false-positive rates under about 3%, cuckoo filters use less total memory than an equivalent Bloom filter — and support deletion natively.
CUCKOO FILTER

Sometimes even 8-bit fingerprints are more than you need

In production: Network routers (packet filtering) · large-scale web crawlers (URL dedup) · RocksDB's cuckoo table storage format

RECAP
Cuckoo filters compress membership into short fingerprints with two candidate homes each, supporting deletion natively.
GAP
but bucket arrays still jump around in memory during collisions — is there a layout that keeps everything in one flat, cache-friendly array?
NEXT
QUOTIENT FILTERsplit each fingerprint into a bucket address and a remainder, stored in-place
QUOTIENT FILTER

Split the fingerprint itself into an address and a value

Take a fingerprint of q+r bits. The top q bits ("quotient") pick a home slot directly in one flat array; the bottom r bits ("remainder") are the only thing actually stored there.

No separate hash table, no pointer chasing — just one contiguous array, which is exactly what CPU caches love.
QUOTIENT FILTER

A filter that can be merged like two sorted lists

In production: Squeakr (DNA k-mer counting) · SSD/flash-optimized databases · systems needing mergeable, resizable filters

RECAP
Membership filters (Bloom, Counting Bloom, Cuckoo, Quotient) all answer "is X probably in this set?" using a fixed, tiny footprint.
GAP
but none of them can tell us how many distinct items exist, or how often each one showed up — how do you count billions of unique things in kilobytes?
NEXT
HYPERLOGLOGestimate a count from the rarest pattern you happen to observe
HYPERLOGLOG

Rare patterns reveal how many coin flips happened

Flip a fair coin until you get tails. If you happened to see 10 heads in a row before that, you probably flipped a lot — runs that long are rare unless you tried many times.

Hashing an item is exactly like flipping coins with its bits: a hash with 10 leading zeros is a rare (1-in-1024) event. If you saw one, you likely hashed roughly 210 items.
HYPERLOGLOG

One lucky guess is noisy — average many small guesses instead

A single max-leading-zeros counter swings wildly. So split incoming hashes across m buckets (using their first few bits as the bucket index), and let each bucket keep its own max.

Averaging m independent "rare event" observations with the right kind of mean cancels out most of the noise from any single unlucky or lucky hash.
HYPERLOGLOG

12 KB of memory, billions of items, ~1% error

Standard error ≈ 1.04 / √m. With m = 16,384 registers at 6 bits each (~12 KB total), HyperLogLog estimates cardinalities in the billions within about 0.8% error — with small-range and large-range bias corrections applied.

Compare that to a real HashSet of a billion 20-byte strings: roughly 20 GB. HyperLogLog gets you within 1% of the truth for 0.00006% of the memory.
HYPERLOGLOG

Counting how many is only half the question

In production: Redis PFCOUNT/PFADD · Google BigQuery APPROX_COUNT_DISTINCT · Presto/Spark distinct counting · ad-tech unique visitor dashboards

RECAP
HyperLogLog tells us how many distinct items passed through — using leading-zero runs and a handful of kilobytes.
GAP
but it can't tell us how many times each individual item showed up — like, how many times did people search for "iPhone" today?
NEXT
COUNT-MIN SKETCHa small grid of counters that never undercounts, only ever overcounts
COUNT-MIN SKETCH

A 2D grid where every row uses a different hash

Build a grid of d rows × w columns, all zero. To record an item, hash it once per row (d independent hash functions) and increment that cell in every row.

Different rows use different hash functions, so a collision in row 1 almost never repeats in row 2 — that's the whole insight we'll use next.
COUNT-MIN SKETCH

To read a count, take the minimum across rows

Query hashes the item the same way and reads all d cells — but returns the smallest value, not the sum or average.

Collisions can only add other items' counts into a cell, never subtract — so every cell value is ≥ the true count. The minimum across rows is the tightest overestimate you can trust.
COUNT-MIN SKETCH

Sizing the grid from an accuracy target

Choose width w = ⌈e/ε⌉ and depth d = ⌈ln(1/δ)⌉. Then with probability at least 1−δ, the estimate exceeds the truth by at most ε·N (N = total updates seen).

Want error under 0.1% of total traffic, 99% of the time? That's roughly w=2,719, d=5 — about 13,600 counters total, regardless of how many distinct items exist.
COUNT-MIN SKETCH

Frequency told us "how often" — not "how alike"

In production: Network heavy-hitter / DDoS detection · Twitter trending topics · database query planners estimating join cardinality

RECAP
Count-Min Sketch tracks approximate frequencies for millions of distinct keys in a small, fixed grid, always overestimating and rarely by much.
GAP
but frequency counts don't tell us whether two entire documents or sets are similar — how do you compare billions of web pages for near-duplicates without comparing them pairwise?
NEXT
MINHASHa single random hash function can estimate the overlap between two whole sets
MINHASH

Comparing every pair of documents doesn't scale

Jaccard similarity of two sets A and B is |A∩B| / |A∪B|. Computing it directly means intersecting entire word-sets — fine for two documents, impossible for a billion-page comparison matrix.

We want a short "fingerprint" per document such that comparing fingerprints approximates comparing the full sets.
MINHASH

The minimum of a random hash is a fair coin flip over the union

Apply one random hash function to every word in a set; keep only the smallest resulting value. Remarkable fact: P(min-hash of A equals min-hash of B) is exactly the Jaccard similarity of A and B.

Why? The item achieving the overall minimum hash (across A∪B) is equally likely to be any element of the union — and it produces a matching min for both sets exactly when that element lies in A∩B.
MINHASH

A signature vector turns similarity into a matching-fraction

Run k independent hash functions, keep the min of each, and stack them into a signature of length k. The fraction of positions where two signatures agree estimates the Jaccard similarity.

Estimating similarity for a billion documents now means comparing short fixed-length signatures — and Locality-Sensitive Hashing buckets similar signatures together so you never do pairwise comparisons at all.
MINHASH

We've been processing data as it flows past, once each

In production: Google's original near-duplicate web-page detection · plagiarism/code-clone detection · recommendation engines (user-item overlap) · genomic k-mer similarity

RECAP
HyperLogLog, Count-Min Sketch and MinHash all summarize a stream of data using fixed memory and one pass.
GAP
but what if the task isn't summarizing — it's picking a fair, uniformly random sample from a stream so long you'll never know its length in advance?

RESERVOIR SAMPLINGkeep a running sample that stays perfectly fair no matter how long the stream runs
RESERVOIR SAMPLING

Pick k fair winners from a line that never stops

You want 3 uniformly random items from a stream of unknown, possibly huge length — seeing each item exactly once, using only O(k) memory. You can't wait for the stream to end to count it first.

Naively: store everything, then pick at the end. That needs O(n) memory — exactly what we're trying to avoid.
RESERVOIR SAMPLING

Algorithm R: let later items fight for a seat with fair odds

Fill the reservoir with the first k items. For every item i after that (1-indexed), roll a random j between 1 and i. If j ≤ k, item i evicts reservoir slot j.

Item i's chance of entering is k/i. Once in, its chance of surviving every later round multiplies out to exactly k/N — the same as everyone else, no matter when they arrived.
RESERVOIR SAMPLING

A fair sample doesn't need the data kept in order

In production: Kafka streaming log sampling · unbiased A/B test cohort selection · SQL TABLESAMPLE on huge tables · random tweet sampling for research

RECAP
Reservoir Sampling maintains a uniformly random sample of a stream of unknown length, in O(k) memory, one pass.
GAP
but many real systems need their in-memory data sorted and searchable in O(log n) — without the rebalancing complexity of a red-black tree. What's the simplest way to get that?
NEXT
SKIP LISTstack coin flips on top of a linked list to build free "express lanes"
SKIP LIST

A plain sorted linked list forces you to check every node

Searching for 47 in a sorted linked list of 12 items means walking node by node from the start — O(n) in the worst case, even though the data is sorted.

Balanced trees fix this with O(log n) search, but need rotations on every insert/delete. Is there a simpler trick that's still probabilistically balanced?
SKIP LIST

Flip a coin per node to build express lanes above it

Every node is promoted to level 2 with probability 1/2, to level 3 with probability 1/4, and so on — pure randomness, no rebalancing logic at all.

The result looks like a highway system: a sparse top level for long jumps, denser lower levels for fine-grained steps — built entirely by coin flips at insert time.
SKIP LIST

Search top-down: go right while safe, drop down when blocked

Start at the top-left. Move right as long as the next value is still ≤ target. When the next value would overshoot, drop one level and repeat.

Each dropped level eliminates roughly half the remaining candidates — the same halving behavior as binary search, achieved with zero rebalancing.
SKIP LIST

A sorted structure that's simple, fast, and lock-friendly

In production: Redis sorted sets (ZSET) · LevelDB/RocksDB in-memory write buffers · Lucene posting-list traversal · concurrent/lock-free data structures

RECAP
Skip Lists give sorted, O(log n)-search structures without any rebalancing logic — just randomness.
GAP
in fact, that's exactly the structure databases use to buffer writes in memory before flushing to disk — but why buffer writes at all instead of writing straight to disk?

LSM TREEturn slow random disk writes into fast sequential ones
LSM TREE

Random writes are the enemy of spinning disks and even SSDs

A B-tree updates the exact page a key lives on — scattered across disk. At high write volume, this means constant random-access seeks, which are orders of magnitude slower than sequential access.

The fix: never write randomly. Buffer writes in memory, then flush them to disk as one big sequential block.
LSM TREE

Writes flow: memory buffer → immutable file → background merge

New writes land in an in-memory Memtable. When it fills up, it's flushed as a new, immutable, sorted SSTable file on disk. A background process periodically compacts (merges) SSTables together.

This is the three-part machine at the heart of Cassandra, RocksDB, LevelDB and HBase — we'll open each box on the next two slides.
LSM TREE

Compaction merges sorted files the way merge-sort merges runs

Because every SSTable is already internally sorted, merging two of them is a simple sorted-merge pass — and it's the moment overwritten or deleted keys finally get discarded for good.

Without compaction, reads would have to check an ever-growing pile of files. Compaction keeps that pile shallow, trading some background CPU/IO for consistently fast reads.
LSM TREE

Two of the boxes we just drew deserve a closer look

In production: Apache Cassandra · RocksDB / LevelDB · HBase · InfluxDB · ScyllaDB

RECAP
LSM trees turn slow random writes into fast sequential ones by buffering in a Memtable and flushing to immutable SSTables.
GAP
we glossed over the memory buffer itself — what actually happens if the process crashes before that buffer is flushed to disk?
NEXT
MEMTABLEthe volatile write buffer, backed by a durability trick
MEMTABLE

A sorted in-memory buffer with a durability safety net

The Memtable holds all recent writes sorted by key (commonly as a Skip List, for cheap sorted iteration and O(log n) inserts). But RAM is volatile — a crash would lose every unflushed write.

Every write is also appended to an on-disk Write-Ahead Log (WAL) before touching the Memtable. On restart, replaying the WAL rebuilds the Memtable exactly as it was.
MEMTABLE

One size threshold, then a clean handoff

Once the Memtable reaches its size limit (e.g. 64 MB), it's frozen as read-only, handed to a background thread to flush as a new SSTable, and a brand-new empty Memtable takes over writes immediately.

Bigger Memtables mean fewer, larger SSTables (less compaction later) but slower crash recovery and more RAM pressure — a real, frequently-tuned production trade-off.
MEMTABLE

The Memtable's job ends the moment it becomes a file

In production: RocksDB / Cassandra memtable size tuning is one of the most common production performance knobs

RECAP
The Memtable is the volatile, sorted write buffer, protected by a Write-Ahead Log and flushed wholesale once full.
GAP
once flushed, that data becomes a static file on disk — what makes that file fast to search, given it can never be modified again?
NEXT
SSTABLEsorted, indexed, and paired with a Bloom filter to skip files that can't possibly help
SSTABLE

Sorted, immutable, and searchable without loading the whole file

An SSTable stores key-value pairs sorted by key in one file, plus a sparse index (e.g. every 100th key's byte offset) so a lookup can binary-search the index, then read just one small block from disk.

Immutability is the real prize: no locks for concurrent readers, trivial replication, and merging two files is just a sorted merge — exactly what we saw compaction do.
SSTABLE

A Bloom filter per file skips disk reads entirely

Every SSTable ships with a small embedded Bloom filter over its own keys. Before touching disk, the read path checks it: "definitely not here" means skip this file completely.

This is the full circle back to slide one: a data structure we treated as a toy example now sits inside every production LSM database, saving real disk IO on every read.
SSTABLE

Storage engines were about ordered keys and values

In production: Google Bigtable (origin of the format) · Cassandra data files · LevelDB/RocksDB · Kafka segment files (same append-only philosophy)

RECAP
SSTables are immutable, sorted, indexed files — the disk-resident half of every LSM-based database, paired with Bloom filters for fast negative lookups.
GAP
but plenty of systems don't store key-value pairs at all — they store yes/no flags for millions of records. What's the fastest way to combine a million such flags at once?

BITMAPone bit per record, combined at CPU speed with AND / OR / XOR
BITMAP

One bit per record, one CPU instruction per 64 of them

To track a boolean per record (is_active, is_premium, in_segment_7), use one bit per record ID. Combining two bitmaps with AND/OR/XOR processes 32 or 64 records per single CPU instruction.

This is how "premium users who were active yesterday" becomes one bitwise AND across two arrays — no loops over individual user records at all.
BITMAP

Bitmaps are blazing fast — when the data is dense

In production: Redis SETBIT/BITCOUNT/BITOP for feature flags · database bitmap indexes on low-cardinality columns · real-time analytics segment combining

RECAP
Bitmaps combine millions of boolean flags per record using native bitwise CPU instructions.
GAP
but what if only 5 out of 10 million IDs are actually set — do we really need 10 million bits of mostly zeros just to represent 5 numbers?
NEXT
ROARING BITMAPstore each chunk of the bitmap in whatever format is smallest for it
ROARING BITMAP

Split the ID space into chunks, pick the cheapest container per chunk

Divide the 32-bit key space into 65,536-value chunks. Each chunk picks its own best representation: a plain bitmap if dense, a sorted array of values if sparse, or a run-list if the values are clustered in ranges.

A single structure now adapts itself: dense regions stay compact bitmaps, sparse regions barely use any memory at all.
ROARING BITMAP

Bitwise operations run directly on the compressed containers

AND-ing two roaring bitmaps ANDs matching chunks: array×array does a merge-intersect, bitmap×bitmap does native word-AND, and mixed pairs convert only the smaller side — never decompressing the whole structure.

You get the sparse-friendly size of a hash set and the dense-friendly speed of a raw bitmap, automatically, per chunk.
ROARING BITMAP

Compressed ID sets that AND and OR at bitmap speed

In production: Apache Lucene / Elasticsearch (filtering doc-id sets) · Apache Druid · Spark · Pilosa · ClickHouse

RECAP
Roaring Bitmaps compress sparse or clustered ID sets while keeping fast native bitwise operations, chunk by chunk.
GAP
search engines run exactly this kind of set-intersection billions of times a day — but how do they get from "the word cat" to "a set of matching document IDs" in the first place?
NEXT
INVERTED INDEXflip the mapping from document → words to word → documents
INVERTED INDEX

Flip the mapping: word → documents, not document → words

A forward index stores what words are in each document — useless for search. An inverted index stores, for every word, the sorted list of document IDs that contain it: a posting list.

Now "find documents containing ‘fox’" is a single lookup into a hash map or B-tree keyed by the word — no scanning of documents required.
INVERTED INDEX

Boolean search is just posting-list intersection

"quick AND fox" merges the two posting lists like a sorted merge — matching IDs survive. Skip pointers embedded in long posting lists let this jump ahead instead of scanning every entry.

Modern engines increasingly store posting lists as Roaring Bitmaps of document IDs — turning boolean search into the same bitwise AND/OR we just built.
INVERTED INDEX

This is how every keyword search you've ever run actually works

In production: Google / Bing web search · Elasticsearch, Solr, Lucene · PostgreSQL GIN full-text indexes

RECAP
The inverted index maps words to posting lists of document IDs, letting boolean search become list intersection at scale.

SYNTHESISwatch four of these structures work together inside one real write and one real read
SYNTHESIS

Fifteen structures, one recurring trade

Every structure we covered gave up a small, well-understood amount of certainty or freshness in exchange for a large win in memory, speed, or both.

None of these are exotic research toys — every single one ships in software you have used this week.
SYNTHESIS

One write into Cassandra touches four of these structures

A single INSERT: append to the WAL, add to the Memtable (a skip list), and eventually flush into an SSTable carrying its own Bloom filter for fast future negative lookups.

None of these structures live in isolation — they're building blocks that compose into the storage engine of a real, widely-deployed database.
SYNTHESIS

A search-engine query touches a different four

Elasticsearch resolves "quick fox" → two posting lists from the Inverted Index, each stored as a Roaring Bitmap of document IDs, intersected in place; a MinHash pass elsewhere flags near-duplicate results to demote.

Same fifteen-structure toolbox, completely different assembly — that's the actual skill: recognizing which trade-off a problem needs, then reaching for the matching tool.
