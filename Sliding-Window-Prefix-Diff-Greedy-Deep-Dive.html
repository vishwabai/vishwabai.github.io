SLIDING WINDOW · WARM-UP
The idea, in one picture
Imagine looking at a train through a fixed gap in a fence — you don't re-look at the whole train each time it moves, you just drop what left your view and add what entered it.

Why this beats brute force

  • Brute force re-scans the window from scratch at every position → O(n·k) work.
  • A sliding window reuses the previous window's work: remove the piece that left, add the piece that entered.
  • That turns re-scanning into O(1) update per step → O(n) total.
  • Works whenever "window value" can be updated incrementally: a sum, a count, a max, a set of characters.
There are four flavors of this idea: fixed-size, variable-size, frequency-map, and monotonic windows. We'll meet all four, each through one worked example.
SLIDING WINDOW · 01 / 06 — FIXED-SIZE WINDOW
Max sum of any 3 consecutive elements
The window size k never changes — it just slides one step at a time. Watch the sum update without re-adding the whole window.

Formula

sum(i) = sum(i-1) − arr[i−k] + arr[i] Time : O(n) Space : O(1)
Practical uses: moving average of stock prices, k-day rainfall total, rate-limiters checking "requests in the last k seconds." But what if we don't know the right window size in advance — how do we know when to grow it, and when to shrink it?
SLIDING WINDOW · 02 / 06 — VARIABLE-SIZE + FREQUENCY-MAP WINDOW
Longest substring without repeating characters
String: "a b c a b c b b". Grow the right edge greedily; the moment a character repeats inside the window, jump the left edge past its last position. A frequency-map (last-seen index) is what makes the jump instant instead of a scan.

Two-pointer rule

while map[s[r]] exists && map[s[r]] >= l: l = map[s[r]] + 1 map[s[r]] = r maxLen = max(maxLen, r-l+1)
Character-frequency problems live right next door: "Find All Anagrams in a String" and "Permutation in String" use this exact same expand/shrink loop, but the map counts characters needed instead of last-seen index. Matching "no repeats" is easy — but what if the window must match a whole target string exactly?
SLIDING WINDOW · 03 / 06 — VARIABLE WINDOW, HARDER CONSTRAINT
Minimum Window Substring
s = "ADOBECODEBANC", t = "ABC". Grow right until the window contains every character of t (with enough copies) — then greedily shrink left while it still qualifies, recording the smallest window seen.

Formula

expand r until formed==required while formed==required: record window if smaller shrink from l, l++ Time : O(|s|+|t|) Space : O(|s|+|t|)
Real use: browser "find in page with all keywords," DNA subsequence matching, log-scanning for the shortest span containing a set of required event types. Instead of chasing "best window," what if we just want to count windows under a limit — like "at most K distinct"?
SLIDING WINDOW · 04 / 06 — AT-MOST-K CONSTRAINTS
Longest substring with at most 2 distinct characters
String: "e c e b a a a c", K = 2. Expand right always; only shrink left when distinct count exceeds K. This same "at most K" window is also the building block for counting exactly K.

The "exactly K" trick

countExactlyK(K) = atMostK(K) − atMostK(K−1)

Counting "at most" is a clean sliding window. Counting "exactly" is not — so we build it by subtracting two "at most" windows instead.

Practical uses

  • Fruit into baskets: at most 2 fruit types per basket.
  • Traffic analysis: sessions using at most K distinct IPs.
  • Autocomplete: longest query prefix touching ≤ K categories.
All four problems so far tracked a sum or a set. But what about the maximum value inside a moving window — recomputing that from scratch would cost O(k) per step. Is there a trick?
SLIDING WINDOW · 05 / 06 — MONOTONIC-WINDOW TECHNIQUE
Sliding Window Maximum (via a monotonic deque)
Keep a deque of indices whose values are strictly decreasing, front-to-back. The front is always the current window's maximum — no scanning needed.
Deque (front → back)

Why it's O(n)

  • Pop from the back any index whose value is ≤ the new value — it can never be the max again.
  • Pop from the front if it fell outside the window.
  • Each index is pushed once, popped once → amortized O(1) per step, O(n) total.
Same pattern powers min-stack, stock span, and largest rectangle in histogram — anywhere a moving max/min needs to update in O(1).
CHECKPOINT
From windows to whole ranges
RECAP — a sliding window keeps a running answer for whatever is currently inside a moving range, updating it in O(1) per step instead of rescanning.
But every window answer still only tells us about a range we already touched, one step at a time — what if someone asks for the sum of any arbitrary range, right now, with zero setup at query time?
FILL → precompute running totals once, and every range becomes one subtraction.
PREFIX / DIFFERENCE · 01 / 06 — PREFIX SUM
Answer any range-sum query in O(1)
Build prefix[i] = sum of arr[0..i-1] once. Then sum of any range [l, r] is just prefix[r+1] − prefix[l] — no matter how wide the range is.

Formula

prefix[0] = 0 prefix[i] = prefix[i-1] + arr[i-1] sum(l..r) = prefix[r+1] - prefix[l] Build : O(n) Query : O(1)
Trade-off vs. sliding window: prefix sums cost O(n) space but answer any range instantly and repeatedly — sliding windows answer only the current range, once, in a single pass.
PREFIX / DIFFERENCE · 02 / 06 — PREFIX SUM, APPLIED
Subarray Sum Equals K (prefix sum + hashmap)
arr = [1, 2, 3, -2, 5], target K = 5. Key idea: if prefix[r] − prefix[l] = K, then some earlier prefix equals prefix[r] − K. Store every prefix sum seen so far in a hashmap.

Formula

need = runningSum - K count += freq[need] freq[runningSum]++

Other prefix-sum classics

  • Equilibrium / pivot index: find i where left-sum == right-sum.
  • Range update count: "how many days had cumulative rainfall > X?"
  • Product analytics: cumulative revenue between any two dates, O(1) per query.
This "target minus running value, look it up" shape reappears everywhere — remember it, it's not just for sums.
PREFIX / DIFFERENCE · 03 / 06 — 2D PREFIX SUM
Sum of any rectangle, in O(1)
Extend the same idea to a grid: pre[i][j] = sum of everything above-left of (i, j). Any submatrix sum is 4 lookups and 3 additions/subtractions — inclusion-exclusion, just like a Venn diagram.

Formula

pre[i][j] = grid[i][j] + pre[i-1][j] + pre[i][j-1] - pre[i-1][j-1] rectSum(r1,c1,r2,c2) = pre[r2][c2] - pre[r1-1][c2] - pre[r2][c1-1] + pre[r1-1][c1-1]

Build once: O(rows·cols). Every rectangle query after that: O(1).

Real applications: image processing (box-blur / integral images use exactly this), heatmap dashboards answering "total sales in this region," matrix-based grid games. Prefix sums are great at answering — but what if the same range needs to be updated, over and over, not just read?
PREFIX / DIFFERENCE · 04 / 06 — DIFFERENCE ARRAY
Apply many range updates, cheaply
Problem: apply +3 to [1,4], +2 to [3,5], and -1 to [0,2] to an array of 7 zeros — without touching every element in every range. Mark only the two edges of each range; recover the real array with one prefix-sum pass at the end.
Formula: diff[l] += val; diff[r+1] -= val; then rebuild with a running sum. k updates, each O(1), then one O(n) rebuild — instead of O(n) per update. Uses: seat-booking calendars, "how many meetings overlap this minute," batch discount ranges on a price array.
PREFIX / DIFFERENCE · 05 / 06 — DIFFERENCE MATRIX
The same trick, in two dimensions
To add a value to every cell inside a rectangle, mark only its 4 corners in a difference matrix — then recover the grid with a 2D prefix-sum pass.

Formula

diff[r1][c1] += v diff[r1][c2+1] -= v diff[r2+1][c1] -= v diff[r2+1][c2+1] += v // then 2D-prefix-sum the diff // matrix to get final grid

Practical uses

  • Calendar / room-booking heatmaps: mark occupied rectangles of (day × room), read final load once.
  • Image editing: batch brightness adjustment over rectangular patches.
  • Game maps: apply many "area buff" rectangles, then bake the final tile grid once.
Same shape as the 1D version: mark corners → integrate once. This "mark the boundary, integrate later" idea is the deepest reusable insight in this whole section.
Same complexity win as 1D: k rectangle updates in O(k), one O(rows·cols) rebuild — instead of touching every cell of every rectangle directly.
PREFIX / DIFFERENCE · 06 / 06 — PREFIX XOR & CUMULATIVE FREQUENCY
The same running-value trick, different operators
Prefix sum isn't really about "+" — it's about any operation with an inverse. XOR is its own inverse (x ^ x = 0), so the exact same "running value, hashmap lookup" shape from Subarray-Sum-K works for XOR too.

Prefix XOR

xorPre[i] = xorPre[i-1] ^ arr[i-1] xor(l..r) = xorPre[r+1] ^ xorPre[l]

Uses: "find subarray with XOR = K," single-number / parity puzzles, checksum verification over a byte range.

Running sums & cumulative frequency

  • Running sum: prefix sum used live, e.g. account balance after each transaction.
  • Cumulative frequency: prefix sum over a count array — "how many scores ≤ X" in O(1), the backbone of percentile lookups and order statistics.
One mental model, four operators: + for totals, − to undo them, ^ for XOR ranges, and plain counts for cumulative frequency.
CHECKPOINT
From reading data to deciding with it
RECAP — prefix and difference techniques trade a little precomputation for instant, repeated answers about sums, updates, and counts over any range.
But knowing the data perfectly doesn't tell us what to do. When we have to make a sequence of choices — pick this meeting, skip that one — and we can't see the future, what rule tells us the locally best move is also the globally best one?
FILL → sometimes just being greedy — taking the best option right now — is provably optimal. Let's find out exactly when.
GREEDY · CORE CONCEPT — GREEDY CHOICE PROPERTY
Make the best move right now, never revisit it
A greedy algorithm builds a solution one decision at a time, always taking whatever looks best at this instant, and never undoing that choice later. It works only when a local best choice is guaranteed to fit inside some global best solution.

When greedy provably works

  • Coin change with {1, 5, 10, 25}: always take the biggest coin ≤ remaining amount → optimal. This is the classic "greedy works" example.
  • Greedy choice property: a locally optimal choice leads to a globally optimal solution.
  • Optimal substructure: the rest of the problem, after the choice, is a smaller version of the same problem.

When greedy quietly fails

  • Coin change with {1, 3, 4}, target 6: greedy picks 4+1+1 (3 coins) — optimal is 3+3 (2 coins). Greedy isn't always safe.
  • 0/1 Knapsack (can't take fractions): greedy-by-ratio can miss the true optimum — needs dynamic programming instead.
The honest rule: greedy is a hypothesis, not a default. You must prove it — usually with an exchange argument — before trusting it.
GREEDY · PROOF TECHNIQUE — EXCHANGE ARGUMENT
How you actually prove a greedy rule is correct
Take any optimal solution that disagrees with the greedy choice. Swap in the greedy choice instead. If the result is still valid and at least as good — the greedy choice was always safe.
Assume optimal picks B first
B (ends late)
then A
Greedy picks A first (ends earliest)
A (ends early)
then B

A ends no later than B, so swapping A into B's slot never blocks anything B could reach — the swapped solution is still valid, and no worse.

The three-step recipe

  • 1. Assume an optimal solution that differs from greedy at some point.
  • 2. Exchange that point for the greedy choice.
  • 3. Show the new solution is still feasible and no worse — so greedy could have been optimal all along.
Every greedy algorithm in this deck — interval scheduling, knapsack, Huffman, job sequencing — is provable this same way. We'll apply it, not re-derive it, from here on.
GREEDY · 01 / 08 — ACTIVITY SELECTION / INTERVAL SCHEDULING
Fit the most non-overlapping intervals
Sort by end time. Always take the next activity that starts at or after the last one you took ends. That one rule maximizes the count — proven by the exchange argument on the previous slide.
Formula: sort by end time, O(n log n); scan once, O(n). Uses: CPU/job scheduling, booking one meeting room to fit max meetings, class-timetable conflict resolution.
GREEDY · 02 / 08 — MINIMUM PLATFORMS / MEETING ROOMS
How many resources do we need at once?
Different question from before: not "which to skip" but "what's the peak overlap." Sort arrivals and departures separately; sweep both with two pointers, counting how many are simultaneously active.
sort(arrivals); sort(departures) i=j=0, platforms=0, best=0 while i < n: if arr[i] <= dep[j]: platforms++; i++ else: platforms--; j++ best = max(best, platforms)
This is exactly LeetCode's "Meeting Rooms II" and the classic "minimum train platforms" problem. Real use: how many support agents / servers / checkout counters are needed at peak load.
GREEDY · 03 / 08 — FRACTIONAL KNAPSACK
Fill the bag with the best value-per-weight first
Bag capacity = 15kg. Items can be split (fractions allowed), so simply rank by value ÷ weight and take greedily until the bag is full — the fraction of the last item makes it exactly optimal.

Formula

sort items by value/weight, descending for each item: take min(item.weight, remaining capacity) add its proportional value stop when capacity == 0
Why 0/1 Knapsack (no splitting) needs DP instead: once you can't take fractions, the greedy exchange argument breaks — a high-ratio item might not fit, forcing you to compare whole combinations. Uses: cargo loading, budget allocation across divisible investments, bandwidth allocation.
GREEDY · 04 / 08 — HUFFMAN CODING
Shorter codes for more frequent symbols
Repeatedly merge the two least-frequent nodes into one, until a single tree remains. Frequent characters end up near the root (short code); rare ones end up deep (long code) — this greedy merge order is provably optimal.

Formula & complexity

use a min-heap of (symbol, frequency) while heap.size > 1: a, b = pop two smallest push merged(a, b, freq = a.f + b.f) Time: O(n log n) — n symbols, heap ops
Real application: .zip, .gzip, JPEG, MP3 all use Huffman or a close relative for entropy coding — this exact merge-the-two-smallest rule is running inside file compressors right now.
GREEDY · 05 / 08 — JOB SEQUENCING WITH DEADLINES
Maximize profit, one job per time slot
Each job takes 1 unit of time and must finish by its deadline. Sort by profit, descending; for each job, greedily place it in the latest free slot at or before its deadline — that keeps early slots open for jobs with tighter deadlines.

Formula

sort jobs by profit, descending for each job (deadline d, profit p): for t = d down to 1: if slot[t] free: slot[t] = job; profit += p; break
Uses: single-server task scheduling with hard deadlines and per-job rewards, ad-slot allocation, exam-hall / interview-slot assignment maximizing total value.
GREEDY · 06 / 08 — GAS STATION (CIRCULAR TOUR)
Find the one starting point that completes the loop
At each station, gas[i] is what you gain and cost[i] is what it takes to reach the next station. Key insight: if your tank ever goes negative, no station you passed through could have been a valid start — so jump the candidate start to the very next station.

Formula

total=0, tank=0, start=0 for i in stations: diff = gas[i]-cost[i]; total+=diff; tank+=diff if tank < 0: start = i+1; tank = 0 answer = (total >= 0) ? start : "no solution"
One pass, O(n), O(1) space — proof is another exchange argument: any station you fail at can never be the answer, so skipping past all of them together is safe. Uses: route planning with fuel constraints, resource-cycle feasibility checks.
GREEDY · 07 / 08 — JUMP GAME
Can you reach the last index?
nums[i] is the furthest you're allowed to jump from i. Track the furthest index reachable so far as you scan left to right — you never need to try every jump combination.

Formula

reach = 0 for i in 0..n-1: if i > reach: return false // stuck, can't get here reach = max(reach, i + nums[i]) return true
Greedy works here because reachability only ever grows — tracking the single best "furthest reach" summarizes every path that could have gotten you there. Uses: network reachability with hop limits, platform-game level solvability checks.
GREEDY · 08 / 08 — WHY GREEDY WORKS AT ALL: MATROID INTUITION
The structure that makes "always pick the best" safe
A matroid is just a name for structures where the greedy rule is guaranteed correct: a family of "allowed" combinations where (1) any subset of an allowed set is also allowed, and (2) you can always grow a smaller allowed set toward a bigger one, one element at a time.

In plain terms

  • If picking fewer things is always still "valid" (like a subset of non-overlapping intervals), you have the first property.
  • If a smaller valid set can always be extended toward a larger one without breaking validity, you have the second.
  • When both hold, picking greedily by weight/value is provably optimal — this is why activity selection, minimum spanning trees, and job sequencing all admit a clean greedy proof.

Where it breaks

  • 0/1 Knapsack fails property (2): a "small valid set" can't always extend — capacity gets wasted differently by different orderings.
  • When a problem doesn't fit this shape, greedy needs a fresh, problem-specific exchange-argument proof — or it needs DP instead.
You don't need to name-drop "matroid" in an interview — but this is the deep reason the exchange argument keeps working, slide after slide, problem after problem.
FINAL RECAP
One decision framework, three tools
TechniqueUse it when…ComplexitySignature example
Sliding Window You need a running answer (sum / count / max / distinct set) over a contiguous, moving range, in one pass. O(n) time, O(1)–O(k) space Longest substring without repeats
Prefix / Difference You need repeated range queries, or many range updates, on data that doesn't change between queries. O(n) build, O(1) query/update Range-sum queries; batch calendar updates
Greedy You must commit to choices in sequence, and can prove a local-best rule never blocks a global-best outcome. Usually O(n log n) (sorting) + O(n) scan Activity selection; Huffman coding
The one thread through all three: don't recompute what you can carry forward. A window carries its sum. A prefix array carries every range. A greedy proof carries the guarantee that today's best choice never needs to be undone tomorrow.
