06 — Python on AWS

Run Your Python Code on AWS

🐍 3 Ways to Run Python on AWS

EC2 — full control, you manage the server. Best for long-running apps, ML training, custom environments.
Lambda — serverless, event-driven. Best for short tasks, APIs, scheduled jobs. No server needed.
ECS / EKS — Docker-based. Best for scalable services and microservices running continuously.

Option 1 — EC2 (Virtual Server) Basic

EC2 — SSH & run Python
# 1. Launch EC2 (free tier: t2.micro, Ubuntu 22.04)
$ aws ec2 run-instances \
--image-id ami-0f5ee92e2d63afc18 \ # Ubuntu ap-south-1
--instance-type t2.micro \
--key-name my-key # your .pem key
# 2. SSH into the server
$ ssh -i my-key.pem ubuntu@YOUR_EC2_IP
# 3. On the EC2 instance: install Python & run
ubuntu@ec2$ sudo apt update && sudo apt install python3-pip -y
ubuntu@ec2$ pip3 install -r requirements.txt
ubuntu@ec2$ python3 app.py
# 4. Keep it running after you disconnect
ubuntu@ec2$ nohup python3 app.py > out.log 2>&1 &
# OR use systemd / screen / tmux for production
# 5. Copy your code to EC2 from local
$ scp -i my-key.pem app.py ubuntu@YOUR_EC2_IP:~/

Option 2 — AWS Lambda (Serverless) Mid

Lambda — deploy Python function
# lambda_function.py — your code MUST have this handler
def lambda_handler(event, context):
name = event.get("name", "world")
return {"statusCode": 200, "body": f"Hello {name}"}
# Package with dependencies
$ pip install requests -t ./package
$ cp lambda_function.py ./package/
$ cd package && zip -r ../lambda.zip .
# Create Lambda function (first time)
$ aws lambda create-function \
--function-name myPythonFunc \
--runtime python3.12 \
--handler lambda_function.lambda_handler \
--zip-file fileb://lambda.zip \
--role arn:aws:iam::123456:role/lambda-role
# Update & invoke
$ aws lambda update-function-code --function-name myPythonFunc --zip-file fileb://lambda.zip
$ aws lambda invoke --function-name myPythonFunc --payload '{"name":"DevOps"}' out.json
$ cat out.json
{"statusCode": 200, "body": "Hello DevOps"}

Option 3 — Docker on ECS (Fargate) Advanced

ECS Fargate — run Python container at scale
# 1. Build Python app Docker image and push to ECR (see Docker → Advanced tab)
# 2. Create ECS cluster (Fargate = no EC2 to manage)
$ aws ecs create-cluster --cluster-name myapp-cluster
# 3. Register task definition (points to your ECR image)
$ aws ecs register-task-definition --cli-input-json file://task-def.json
# 4. Create & run service (3 replicas, auto-restart)
$ aws ecs create-service \
--cluster myapp-cluster \
--service-name myapp-svc \
--task-definition myapp:1 \
--desired-count 3 \
--launch-type FARGATE
# 5. Force new deployment (after pushing updated image)
$ aws ecs update-service \
--cluster myapp-cluster \
--service myapp-svc \
--force-new-deployment
✅
Use Lambda when…
Task runs under 15 min, triggered by events (HTTP, S3 upload, schedule), or you want zero server management.
🖥️
Use EC2 when…
Long-running processes, ML training, full OS control, or you need persistent state on disk.
📦
Use ECS/EKS when…
Containerized app, needs autoscaling, microservices architecture, or you already use Docker.

09 — DevSecOps

Security in DevOps

🔐 Shift Security Left

Don't bolt security on at the end. Embed it in every stage of the pipeline — linting, scanning, secrets management — so issues are caught before they reach production.

Never hardcode secrets Basic
Use environment variables or AWS Secrets Manager. Never commit API keys or passwords to Git.
IAM Least Privilege Basic
Each Lambda/EC2/service should only have the IAM permissions it actually needs — nothing more.
Scan Docker images Mid
Use docker scout or Trivy in CI to detect CVEs in your images before pushing to ECR.
SAST / Dependency Scanning Mid
Tools like Bandit (Python), Snyk, or GitHub Dependabot flag vulnerable packages automatically.
VPC & Security Groups Advanced
Run all resources in a private VPC. Open only the ports needed, to specific CIDR ranges only.
WAF + Shield Advanced
AWS Web Application Firewall blocks SQLi/XSS. Shield protects against DDoS attacks.

Advanced DevOps Concepts

🚦 Blue/Green & Canary Deployments▼
🟦🟩 Blue/Green
Run two identical environments. Route 100% traffic to Blue (live). Deploy to Green, test it, then flip the load balancer. Instant rollback = flip back.
🐦 Canary
Release to 5% of users first. Monitor error rates and latency. If healthy, gradually increase to 100%. Catch bugs before everyone is affected.

🌐 Networking: VPC, Subnets & Load Balancers▼
  • VPC (Virtual Private Cloud) — your own isolated network on AWS. All resources live inside it.
  • Public Subnet — has internet access. Put load balancers, NAT gateways here.
  • Private Subnet — no direct internet. Put databases, Lambda, EC2 app servers here.
  • Security Group — stateful firewall per resource. Think of it as a per-service firewall rule.
  • ALB (Application Load Balancer) — distributes HTTP traffic across EC2/ECS tasks. Supports path-based routing.
  • Route 53 — AWS DNS service. Maps your domain to ALB or CloudFront.

💰 Cost Optimization on AWS▼
  • Use Savings Plans / Reserved Instances — commit 1-3 years, save up to 72% vs on-demand.
  • Use Spot Instances for fault-tolerant batch/ML workloads — up to 90% cheaper.
  • Right-size EC2 — use AWS Compute Optimizer to find over-provisioned instances.
  • Set S3 lifecycle rules — move old data to S3 Glacier (archive) automatically.
  • Use Lambda for infrequent workloads — pay only when it runs, not 24/7.
  • Enable AWS Cost Anomaly Detection — alerts when spending spikes unexpectedly.
  • Tag all resources — use tags to track costs per team, project, or environment.

12 — SRE

Site Reliability Engineering

🎯
SLI — Service Level Indicator
A measurable metric. e.g. "95th percentile API latency" or "successful request rate". The thing you actually measure.
📋
SLO — Service Level Objective
A target for your SLI. e.g. "99.9% of requests succeed each month." Your internal reliability goal.
📜
SLA — Service Level Agreement
A legal contract with a customer. SLA is always weaker than your SLO — you need headroom before breaching SLA.
💰
Error Budget
If SLO = 99.9%, your error budget is 0.1% (43 min/month of allowed downtime). Burn through it → freeze deploys.

🚨 Anatomy of an Incident

T+0:00
🔴 Alert fires
PagerDuty wakes someone up. Error rate spikes above 5% — SLO alarm triggered via CloudWatch.
T+0:05
🔍 Triage begins
On-call engineer checks dashboards, reads logs, narrows scope. Slack incident channel opened. Incident Commander assigned.
T+0:20
🧩 Root cause identified
A bad deploy at T-1h introduced a null-pointer. Traces in X-Ray confirm it's the /checkout service.
T+0:28
⚡ Mitigation
Rollback triggered: kubectl rollout undo deployment/checkout. Error rate drops to 0.
T+0:35
✅ Incident resolved
All-clear posted. Error budget impact: ~6 min burned. Post-mortem scheduled for 48h later — blameless.
T+48h
📄 Post-mortem written
Timeline, impact, root cause, action items (add unit test for null case, improve deploy gates). Shared company-wide.
SRE runbook commands
# Check current error rate (last 5 min)
$ aws cloudwatch get-metric-statistics \
--namespace AWS/ApplicationELB \
--metric-name HTTPCode_Target_5XX_Count \
--period 300 --statistics Sum \
--start-time $(date -u -d '5 minutes ago' +%Y-%m-%dT%H:%M:%S) \
--end-time $(date -u +%Y-%m-%dT%H:%M:%S)
# Quickly rollback a bad deploy
$ kubectl rollout undo deployment/myapp
$ kubectl rollout status deployment/myapp # watch it go green
# Python: calculate error budget remaining
slo_target = 0.999 # 99.9%
window_mins = 43800 # 1 month in minutes
budget_mins = window_mins * (1 - slo_target) # = 43.8 min
burned_mins = 6
remaining = budget_mins - burned_mins
print(f"Budget remaining: {remaining:.1f} min ({remaining/budget_mins*100:.0f}%)")
Budget remaining: 37.8 min (86%)
13 — Helm

Helm — Kubernetes Package Manager Advanced

⛵
What is Helm?
Helm is to Kubernetes what apt is to Ubuntu. It packages Kubernetes YAML files into reusable Charts — versioned, templatable, shareable. One helm install deploys your entire app with all its services, ingress, secrets, and config.
📦 Chart (the package)
A directory of YAML templates + Chart.yaml (name, version, description) + values.yaml (defaults).
🔧 Values (your config overrides)

22 — Chaos Engineering

Chaos Engineering — Break Things on Purpose

💥
The Chaos Principle
Intentionally inject failures in a controlled way to discover weaknesses before real incidents do. Netflix invented Chaos Monkey. The philosophy: "If it hurts, do it more often." You find out your backups don't restore during a scheduled drill — not during a 3 AM incident.
🐒
Chaos Monkey
Netflix's original tool. Randomly terminates EC2 instances during business hours. Forces teams to build self-healing systems.
🌪️
AWS FIS (Fault Injection Simulator)
AWS-managed chaos. Inject CPU stress, kill ECS tasks, drop network packets, throttle APIs — with automatic blast-radius limits.
🔬
Litmus / Chaos Toolkit
Open-source K8s chaos. Run experiments as Kubernetes CRDs. GitOps-friendly, integrates with CI pipelines.

Common Chaos Scenarios to Run

💀
Kill a Random Pod
Does Kubernetes restart it automatically? Does traffic fail over without downtime? Tests auto-healing and replica redundancy.
kubectl delete pod $(kubectl get pods -l app=myapp -o name | shuf -n 1)
🐌
Inject Network Latency
Add 500ms to all outbound calls from a pod. Does the app time out gracefully or hang? Do downstream retries cause cascades?

🔥
CPU Stress on EC2
Max out CPU on an instance. Does CloudWatch fire the alarm? Does autoscaling add capacity? Does the app degrade gracefully?

🗃️

Circuit Breaker pattern in Python — survive dependency failures
import time

class CircuitBreaker:
"""OPEN = fail fast. CLOSED = normal. HALF-OPEN = test recovery."""
def __init__(self, threshold=5, timeout=60):
self.failures, self.threshold = 0, threshold
self.open_until = None

def call(self, fn, *args, **kwargs):
if self.open_until and time.time() < self.open_until:
raise RuntimeError("Circuit OPEN — service unavailable")
try:
result = fn(*args, **kwargs)
self.failures = 0 # success → reset
self.open_until = None
return result
except Exception as e:
self.failures += 1
if self.failures >= self.threshold:
self.open_until = time.time() + 60 # open for 60s
print(f"Circuit opened after {self.threshold} failures")
raise

# Usage
cb = CircuitBreaker(threshold=5)
result = cb.call(call_payment_service, order_id=42)
23 — Service Mesh

Service Mesh — Istio & Traffic Control

🕸️
What is a Service Mesh?
A dedicated infrastructure layer for service-to-service communication in microservices. A sidecar proxy (Envoy) is injected into every pod automatically. It handles retries, timeouts, mTLS encryption, circuit breaking, canary routing, and observability — all without changing your application code.
🔐
mTLS Everywhere
Mutual TLS between every service pair, automatically. Zero code changes. Istio rotates certs, enforces policies.
🔀
Traffic Splitting
Route 90% to v1, 10% to v2 of a service. Gradually shift based on header, user cohort, or percentage.
🔁
Retries & Timeouts
Declare retry policy at the mesh level. 3 retries with 5s timeout — no code changes in your Python service.
📊
Auto Observability
Every request gets latency, error rate, and traffic metrics in Prometheus automatically. No instrumentation needed.
💥
Fault Injection
Inject HTTP 503s or artificial delays into any service call — great for chaos testing without modifying code.
🛡️
Authorization Policies
Declare which services can talk to which at L7. "Only the API service may call the payments service" — enforced by the mesh.

26 — Artifact Management

Artifact Management — Versioning Every Build Output

An artifact is any output your pipeline produces — a Docker image, a Python package, a Helm chart, a Terraform module. Proper artifact management means every artifact is immutable, versioned, signed, and traceable back to the exact commit that produced it.

Container Images
Docker / ECR / GHCR
Tag with git SHA, never :latest in prod. Scan every image on push. Use digest pinning: image@sha256:abc in prod.
Python Packages
PyPI / AWS CodeArtifact
Publish internal libraries to a private registry. Pin exact versions with pip-compile. Never use >= in prod deps.
Helm Charts
Helm OCI / Artifact Hub
Push Helm charts to ECR as OCI artifacts. Version with semver. Pull in GitOps via ArgoCD with a chart version lock.
Terraform Modules
Terraform Registry / Git Tags
Share infra modules across teams via a private registry. Consume with a pinned version: source = "git::...?ref=v1.2.0".
Artifact versioning commands
# Docker: tag with git SHA + semantic version + latest
$ SHA=$(git rev-parse --short HEAD) # e.g. a3f9c21
$ VER=$(cat VERSION) # e.g. 1.5.2
$ docker build -t myapp:${SHA} -t myapp:${VER} .
$ docker push myapp:${SHA} # immutable — never changes
$ docker push myapp:${VER} # semver tag

$ pip install build twine
$ python -m build # creates dist/*.whl

27 — On-Call Engineering

On-Call Engineering — Runbooks & Incident Response

📟
On-Call is a skill, not a punishment
Good on-call means waking up to an alert and knowing exactly what to do in the first 60 seconds. The tools: a clear runbook, a single dashboard, a fast rollback command, and an escalation path. The goal: resolve in minutes, not hours.

The 60-Second Response Runbook

1
Acknowledge the alert
Ack in PagerDuty/OpsGenie so the team knows someone is on it. Don't investigate and ack later — ack first to stop escalation timers.
pd oncall ack --incident I12345
2
Check the dashboard
Open Grafana/CloudWatch. Look at error rate, latency p99, pod count, CPU/RAM. What spiked and when exactly?
aws cloudwatch get-metric-statistics --namespace AWS/ApplicationELB --metric-name HTTPCode_Target_5XX_Count ...
3
Check recent deploys
Did something deploy in the last 30 minutes? 90% of incidents are caused by recent changes. Check Git log, ECS task revision, Helm release history.
git log --oneline -10 | head && aws ecs describe-services --cluster prod --services myapp --query 'services[0].deployments'
4
Read the logs
Check CloudWatch Logs for ERROR/CRITICAL patterns around the time the alert fired. Look for stack traces, null pointers, OOM kills.
aws logs filter-log-events --log-group-name /ecs/myapp --filter-pattern "ERROR" --start-time $(date -d '30 minutes ago' +%s000)
5
Rollback if deploy-related
Don't debug in prod. If a deploy caused it, roll back first, investigate after. Time to resolve > time to debug.
kubectl rollout undo deployment/myapp # or: aws ecs update-service --force-new-deployment
6
Communicate
Post a brief status in the incident Slack channel every 15 minutes: "Still investigating, error rate 8%, rolled back v1.5.0, monitoring." Then write the post-mortem.
slack post --channel #incidents "🔴 P1 - API errors at 8%. Rollback in progress. ETA: 10 min. IC: @you"
