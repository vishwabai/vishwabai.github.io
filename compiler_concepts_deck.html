Compiler Concepts
By the end, you'll know exactly what happens between these two lines.
The Whole Pipeline, At a Glance
Source code passes through many small, honest transformations before it runs.
What Actually Happens When Code Runs?
Every line eventually becomes electrical signals a CPU can follow. Let's trace the journey.
To a Computer, Code Is Just Characters
A computer sees only a flat stream of characters. But how does it know '1' and '2' are a number, and '+' is an operator? We're missing a way to group and label them.
Grouping Characters Into Words: Lexing
Each run of characters becomes one token: a name, a number, or a symbol.
Every Token Has a Type
A token is a (type, value) pair — the atoms of syntax.
Under the Hood: Finite Automata
Lexers are literally tiny state machines — one rule: which door to take for the next character.
Tokens Have No Shape Yet
We have a flat list of typed tokens. But what stops '=' from appearing before every name? We need rules for valid structure.
Grammar: Rules for Valid Structure
Grammar defines valid patterns — and lets patterns nest inside themselves. That's recursion.
Parsing: Tokens Become a Tree
The parser matches grammar rules and builds a tree that mirrors the structure.
Why Multiplication Binds Tighter
Grammar encodes precedence directly: '*' sits deeper in the tree, so it's evaluated first.
The Parse Tree Is Too Noisy
Every node here just relays grammar bookkeeping. What's the actual meaning underneath?
AST: Keep Meaning, Drop Decoration
The AST keeps only what changes behavior — operators and operands, nothing else.
A Clean Tree Isn't Necessarily Correct
We have a clean AST. But nothing has checked whether 'ab' was ever declared. Is a valid-looking tree the same as a meaningful one?
Semantic Analysis: Does It Make Sense?
Semantic analysis tracks what each name means — its type, its scope — as the tree is walked.
Type Checking: Catching Category Errors
Type checking enforces rules like this one — mismatched types are an error, not just a style issue.
Still Tied to One Language's Shape
Semantic analysis confirms the program is internally consistent. But this AST still mirrors one language's grammar. How do we get a form any machine can target?
Intermediate Representation: One Language In Between
IR is simple, uniform, and close to hardware — but still independent of any one machine.
Static Single Assignment: Name Once, Reason Easily
SSA renames each assignment — now every use points to exactly one definition, which makes optimization straightforward.
Correct, But Wasteful
This IR is correct — but it does unnecessary work at runtime. Can the compiler do some of that work in advance?
Optimization: Do the Math Now, Not Later
Constant folding: if the compiler already knows the values, it computes the result once — not every time the program runs.
Optimization: Delete What Never Matters
If a value is computed but never used, it's dead — safe to remove entirely.
Optimization: Never Repeat Yourself
Computed the same thing twice? Reuse the first result instead of recomputing.
Still Not a Real Machine's Language
Optimization trimmed the IR to only necessary work. But a CPU only knows fixed registers and a small instruction set. How does IR become that?
Code Generation: IR to Instructions
Code generation picks concrete instructions and registers for each IR operation — this is instruction selection.
Register Allocation: Finite Slots, Infinite Values
There are far fewer registers than values — the allocator reuses a register once a value's lifetime ends.
One File Isn't the Whole Program
Code generation produced machine instructions in an object file. But our program calls functions living in other files. How do separate pieces become one program?
Linking: Stitching Files Into One
The linker resolves each reference to a real address and merges everything into one executable.
A File on Disk Isn't a Running Program
Linking produced a single executable file sitting on disk. But nothing is executing yet. How does it become a live process?
Loading: From Disk to Live Memory
The loader maps each section into memory and hands control to the entry point — execution begins.
But Not Every Language Takes This Road
Some languages compile to a made-up machine's instructions instead of the real one. Let's see why.
Bytecode: A Machine That Only Exists in Software
Bytecode is simple, compact, and machine-independent — perfect for a software-simulated machine to run anywhere.
Virtual Machines: Executing Bytecode Step by Step
The VM is a small interpreter loop: read one bytecode instruction, update the stack, repeat.
Interpreting Is Safe, But Slow
A VM interpreting bytecode is portable. But repeating the same decode-and-dispatch work every time costs real speed. Can we get both portability and native speed?
JIT: Compile the Hot Parts, While Running
The JIT watches which code runs often, compiles just that part to native instructions, then uses the fast version from then on.
Two Philosophies: Compile Ahead vs Compile Live
AOT pays the compile cost once, upfront. JIT starts immediately but pays a smaller cost later, adapting to real usage.
Real Compilers, Real Choices
Same pipeline, different trade-offs — chosen based on startup time, peak speed, and portability needs.
The Full Journey, One More Time
Characters → tokens → tree → meaning → IR → faster IR → instructions → one program → running.
