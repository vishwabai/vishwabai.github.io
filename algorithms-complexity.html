CONCEPT 1 — TIME COMPLEXITY
Time Complexity: Steps as a Function of n
T(n) = number of elementary operations
Plain version: don't time it with a stopwatch — count how many basic steps run, as the input size n grows. That count is hardware-independent.
Why not just use a stopwatch? Because wall-clock time depends on CPU speed, the programming language, even what else is running. T(n) counts operations, so it stays true on any machine.
LINEAR SEARCH — WORST CASE
RECAP — T(n) counts operations, not seconds. GAP — But real code for linear search is closer to T(n) = 3n + 5 (a check, a compare, an increment, each loop). Do those exact constants matter once n is huge?
CONCEPT 2 — BIG O (UPPER BOUND)
Big O: A Guaranteed Ceiling on Growth
f(n) = O(g(n)) if ∃ c>0, n₀>0 such that
f(n) ≤ c·g(n) for all n ≥ n₀
Plain version: from some point on (n₀), the algorithm never grows faster than c times this curve. It's a promised worst-case ceiling.
3n + 5 = O(n)
drop the constants (3, 5) — only the shape "grows like n" survives.
n² + 3n = O(n²)
the fastest-growing term wins; n² dominates 3n as n grows.
f(n) = 3n + 5 STAYS UNDER c·g(n) = 4n, AFTER n₀
RECAP — O(n) is the worst-case ceiling we just proved for linear search. GAP — O only promises we won't be slower than this. Is there a guarantee we can't be faster either — a floor?
CONCEPT 3 — BIG OMEGA (LOWER BOUND)
Big Ω: A Guaranteed Floor on Growth
f(n) = Ω(g(n)) if ∃ c>0, n₀>0 such that
f(n) ≥ c·g(n) for all n ≥ n₀
Plain version: no matter how lucky the input is, the algorithm needs at least c times this much work. It's a promised minimum.
Summing n numbers is Ω(n)
you must touch every number at least once — no shortcut skips an element.
f(n) NEVER DIPS BELOW c·g(n), AFTER n₀
RECAP — O = ceiling, Ω = floor — two separate promises about the same function. GAP — What if the ceiling and the floor turn out to be the exact same curve? Is there a name for that tight match?
CONCEPT 4 — BIG THETA (TIGHT BOUND)
Big Θ: When Floor and Ceiling Meet
f(n) = Θ(g(n)) if f(n)=O(g(n))
AND f(n)=Ω(g(n))
Plain version: f(n) is sandwiched between c₁·g(n) and c₂·g(n) forever after n₀. Θ is the algorithm's true, exact growth rate.
Linear search, worst case: Θ(n)
the ceiling and the floor are both "n" — no gap left between them.
f(n) SQUEEZED BETWEEN c₁·g(n) AND c₂·g(n)
RECAP — One algorithm now has three labels: O (ceiling), Ω (floor), Θ (exact fit). GAP — These describe one algorithm's own growth. But how do different growth-rate classes compare to each other as n gets huge — which one wins the race?

CONCEPTS 5, 6, 7 — BEST, AVERAGE, WORST CASE
Same Algorithm, Different Luck
One algorithm — linear search — run three times on the same 8-name list, only the target changes.
BEST CASE — target is first
1 step · O(1)
AVERAGE CASE — target is around the middle
~n/2 steps · O(n)
WORST CASE — target is last, or missing
n steps · O(n)
When people say "this algorithm is O(n)" with no qualifier, they almost always mean the worst case.
RECAP — Time isn't one number — it depends on which case you land in. GAP — We've spent this whole time on TIME. Algorithms also consume something else while they run — what?
CONCEPT 8 — SPACE COMPLEXITY
Space Complexity: Memory as a Function of n
S(n) = extra memory used beyond the input, as a function of n
("auxiliary space" — the input array itself usually isn't counted)
RECURSIVE factorial(5) — CALL STACK GROWS
ITERATIVE factorial(5) — ONE VARIABLE, REUSED
result = result × i
same one box, overwritten each loop → S(n) = O(1)
RECAP — Recursive elegance often costs stack space; a loop can trade that away. GAP — So far every operation cost the same each time. What if ONE step is occasionally expensive but mostly cheap — does that ruin our worst-case math?
CONCEPT 9 — AMORTIZED ANALYSIS
Amortized Analysis: Averaging the Expensive Moments
A dynamic array (Python list, JS array, Java ArrayList) doubles its capacity when full. Watch what one resize costs — and what it costs on average.
capacity: 4
COST PER INSERT — ONE SPIKE, MOSTLY FLAT
amortized cost =
total cost of n ops ÷ n
Copies happen rarely (1, 2, 4, 8…) and each one pays for the growth since the last — spread out, every insert still averages O(1).
RECAP — One expensive step, spread over many cheap ones, still averages to O(1). GAP — We've built solid tools for judging ONE algorithm. Can we ever prove no algorithm — not even one nobody has invented yet — can beat some limit?
CONCEPTS 10, 11 — UPPER & LOWER BOUNDS
Bounding the Algorithm vs. Bounding the Problem
UPPER BOUND OF AN ALGORITHM
Merge sort takes at most O(n log n) — a ceiling on this one method. That's the same O(...) from Slide 4, applied to sorting.
LOWER BOUND OF A PROBLEM
No comparison-based sort can ever beat Ω(n log n) — a floor on every possible method, proven, not just observed.
WHY: A DECISION TREE OF COMPARISONS
3 items have 3! = 6 possible orderings. Each comparison splits the possibilities in two, so you need at least log₂(6) ≈ 2.6 → 3 comparisons, minimum.
Merge sort's O(n log n) ceiling meets this Ω(n log n) floor → it's asymptotically optimal.
RECAP — When an algorithm's upper bound meets the problem's lower bound, we call it optimal. GAP — We can now measure time and space precisely. But can a system minimize both at once — or does saving one always cost the other?
CONCEPT 12 — TIME – SPACE TRADE-OFFS
Trade-offs: Spending Space to Buy Speed
Same task — look up a phone number — two honest solutions, two different bills.
SORTED ARRAY + BINARY SEARCH
TIME — O(log n)
EXTRA SPACE — O(1)
HASH TABLE
TIME — O(1) average
EXTRA SPACE — O(n)
ALSO: MEMOIZATION
Naive Fibonacci recomputes the same calls endlessly — O(2ⁿ) time, O(1) space. Cache each answer once (memoize) and it drops to O(n) time — at the cost of O(n) space to hold the cache. Same problem, opposite trade.
RECAP — Every design sits somewhere on the time–space line; there's rarely a free lunch. GAP — So where does all of this actually show up outside a classroom?
WHERE THIS SHOWS UP
Complexity Analysis in the Real World
SEARCH ENGINES
An inverted index + hashing gives near O(1)/O(log n) lookups across billions of pages instead of scanning the whole web per query.
GPS & MAPS
Dijkstra / A* graph algorithms — their complexity is exactly why a route recalculates fast even with live traffic on millions of roads.
DATABASE INDEXES
A B-tree index turns an O(n) full-table scan into an O(log n) lookup — the whole reason "add an index" fixes a slow query.
EVERYDAY ARRAYS
Python lists, JS arrays, Java ArrayList — all use the doubling trick from Slide 10, so .append() stays amortized O(1) for you, invisibly.
Four places you're already relying on Big-O reasoning, whether you knew it or not.
