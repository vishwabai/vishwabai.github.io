THE PROBLEM

Before objects, there was chaos

Say we need to track three students: their name, grade, and GPA.
GAP We need a way to bundle related data and behavior into one unit — but what does that unit look like?
FILL A class — a blueprint that defines the shape, but holds no data itself.

A class defines what every future object of this kind will have — not the values themselves.
RECAPA class is a blueprint — attributes and methods, but no real values.
GAP You can't live inside a blueprint. How do we get a real, usable thing out of it?
FILLThe object — a real instance stamped from the class, holding its own values.
CLARIFYING

Class vs. Object — the one-line test

RECAPObjects are instances stamped from a class, each with its own copy of data.
GAP They look identical in shape. So how does each object keep its OWN values without mixing them up with the others?
FILL Attributes — each object gets its own private storage slots, filled in at creation.
RECAPEach object holds its own attributes — private, independent data.
GAP Data just sits there quietly. How does an object actually DO something with it?
FILL Methods — functions that belong to an object and act on its own attributes.
WORKED EXAMPLE · PRACTICAL USE

A BankAccount object in action

This exact pattern runs real banking software, game characters, and UI widgets.
class BankAccount:
  def deposit(self, amt):
    self.balance += amt
 
  def withdraw(self, amt):
    if amt <= self.balance:
      self.balance -= amt
Real uses: bank ledgers · game player health/inventory · UI buttons holding their own state · database record wrappers
RECAPMethods act on an object's own attributes, using self/this to know which object.
GAP Manually setting every attribute right after creating each object is repetitive — what if we forget one? What if it should happen automatically, the instant the object is born?
FILL Constructor — special method that runs automatically at birth, filling in attributes.
RECAPA constructor runs automatically at birth, guaranteeing every object starts fully formed.
GAP Every object eventually dies — a function ends, a program closes. If that object was holding something real, like an open file or a connection, what cleans it up?
FILL Destructor — runs when an object is destroyed, releasing what it was holding.
Practical use: closing files, releasing DB connections and network sockets, unlocking a mutex, freeing GPU/hardware handles
COMMON MISTAKES

Where this trips people up

⚠
Mutable default attributes.
A list set as a default in the constructor can end up shared across every object instead of being fresh per instance.
⚠
Trusting destructor timing in GC languages.
Python's __del__ may run late or never in a program's lifetime — never rely on it for critical cleanup.
⚠
Confusing class attributes with instance attributes.
Changing a class attribute through one object can silently affect every other object sharing it.

DEEP DIVE

Three levels of visibility

Think of them as concentric rings — the closer to the center, the fewer places can reach in.
public — reachable from anywhere. The intended front door.
protected — reachable from the class itself and its subclasses only.
private — reachable only from inside the class itself. Nothing outside gets in.
# Python: convention, not enforced
self._balance # "protected" by convention
self.__pin # name-mangled → harder to reach
// Java / C++: enforced by the compiler
private double balance;
PRACTICAL PATTERN

Getters & setters guard the door

A setter can inspect a value before it's ever allowed to land on the object.
def set_balance(self, amt):
  if amt < 0:
    raise ValueError("no negatives")
  self._balance = amt
def get_balance(self):
  return self._balance
LANGUAGE NOTE

Python doesn't have a real "private"

It relies on convention and one small trick instead of a hard compiler wall.
"We're all consenting adults here" — Python trusts discipline over a hard wall; Java and C++ enforce it at compile time.
RECAPEncapsulation locks an object's data behind methods it chooses to expose.
GAP The data is safe now, but the world is still full of overwhelming detail — wiring, voltages, SQL syntax. How do we let someone use something complex without needing to understand all of it?
FILL Abstraction — expose a simple interface, hide the complicated machinery behind it.
Same idea as a car's accelerator pedal: press it, and the car moves — you never touch the fuel injection timing.
DEEP DIVE

Abstract classes: a blueprint with gaps left on purpose

DEEP DIVE

Interfaces: a contract with zero implementation

CLARIFYING THE CONFUSION

Encapsulation vs. Abstraction

They usually team up: an abstract interface (abstraction) sits in front of encapsulated internals (encapsulation).
WORKED EXAMPLE

One interface, two very different insides

class Shape(ABC):
  @abstractmethod
  def area(self): ...
Calling code just does shape.area() and never needs to know which one it's holding — a preview of Episode 3's polymorphism.
PRACTICAL APPLICATIONS

Where this shows up in real systems

●
Payment gateways. A PaymentProcessor interface lets you swap Stripe for PayPal without touching checkout code.
●
Database drivers. Your app calls the same abstract query methods whether it's talking to PostgreSQL or SQLite underneath.
●
Encapsulated bank accounts. Real banking software never lets external code set a balance directly — only through validated, logged methods.
●
Plugin systems. Any plugin implementing the expected interface works — the host app never needs to know its internals.
COMMON MISTAKES

Where this trips people up

⚠
Leaking a mutable reference.
A getter that returns the actual internal list lets outside code mutate it directly — return a copy instead.
⚠
Getter/setter for everything.
Wrapping every trivial field in a pass-through getter and setter adds noise without adding any real protection.
⚠
Treating abstract class and interface as the same thing.
An abstract class can hold state and real code; a pure interface (in most languages) cannot.

RECAPEpisode 2: encapsulation guards data, abstraction hides complexity behind a simple interface.
GAP Circle and Square both needed structure and repeated boilerplate. What if related classes could share code instead of rewriting it every time?
FILL Inheritance — a new class is built ON TOP of an existing one, and gets everything it has for free.
DEEP DIVE

Writing it, and calling the parent explicitly

class Dog(Animal):
  def __init__(self, name):
    super().__init__(name)
    # parent's constructor runs first
Python
class Dog extends Animal {
  Dog(String name) {
    super(name);
  }
}
Java
RECAPInheritance lets Dog and Cat reuse Animal's code and add their own on top.
GAP A dog doesn't just make "a generic animal sound" — it barks. How does a child class replace a parent's behavior with its own version, specifically for itself?
FILL Method overriding — a subclass redefines a method it inherited, using the exact same name and signature.
DEEP DIVE

How does it know WHICH version to run?

Dynamic dispatch — the decision is made at runtime, based on the object's real type.
In C++, a method must be marked virtual for this lookup to happen — otherwise it uses the declared type instead.
RECAPOverriding + dynamic dispatch: the actual object's type decides which method body runs.
GAP That solves replacing behavior for a subtype. But what if we want the same method name to accept different kinds or numbers of inputs — not to override anything?
FILL Method overloading — several methods, same name, different parameter signatures.
int add(int a, int b) {
  return a + b;
}
double add(double a, double b, double c) {
  return a + b + c;
}
Java / C++ — resolved at compile time
Python has no true overloading — a later def add() just replaces the earlier one.
CLARIFYING THE CONFUSION

Overriding vs. Overloading

RECAPOverriding changes behavior per subtype; overloading offers multiple call shapes for one name.
GAP Now Dog and Cat each override make_sound() differently. How do we treat a whole mixed group of them identically, without ever checking which one is which?
FILL Polymorphism — "many forms": one call, one interface, correct behavior for each actual object.
PRACTICAL APPLICATION

Real use: a payment processing loop

This is exactly how e-commerce checkout code stays simple no matter how many payment types exist.
for method in [card, paypal, upi]:
  method.pay(amount)
# card, paypal, upi all implement
# the same PaymentMethod interface
# checkout code never changes,
# even when a new provider is added
Same interface from Episode 2, now put to work through polymorphism.
RECAPPolymorphism lets one loop treat many different subtypes identically, through a shared interface.
GAP So far every child had exactly one parent. What if a class genuinely needs behavior from TWO unrelated parents — like an amphibious vehicle being both a Car and a Boat?
FILL Multiple inheritance — a class inherits from more than one parent at once.
Allowed in Python and C++ · disallowed for classes in Java and C# (they allow it only for interfaces)
THE CATCH

The diamond problem

What if both parents share a common ancestor — and both override the same method?
FILL Mixins & Traits — small, focused, single-purpose classes designed to be combined, not full ancestries.
class LoggingMixin:
  def log(self, msg): ...
class Car(Vehicle, LoggingMixin):
  # gets log() "for free", cleanly
Python — resolved via a clear Method Resolution Order (MRO)
A mixin never stands alone — it exists purely to be added onto another class, one small capability at a time.
Java and C# sidestep the diamond entirely: interfaces with default methods give similar reuse without ever allowing two conflicting field ancestries.
COMMON MISTAKES

Where this trips people up

⚠
Deep inheritance chains.
Five levels of "is-a" makes a change at the top ripple unpredictably — the fragile base class problem.
⚠
Forgetting super().__init__().
The parent's own setup never runs, silently leaving attributes half-initialized.
⚠
Inheriting just to reuse a little code.
If it isn't really an "is-a" relationship, composition (Episode 4) is usually the safer tool.

Java / C++
↑ "static" underlines at the same moment — same meaning, different keyword
RECAPInstance members live per-object; static members live once, shared by the whole class.
GAP Every relationship so far has been "is-a" through inheritance. But a Car isn't a kind of Engine — it just HAS one. How do objects work together without being the same kind of thing at all?
FILL Composition — a "has-a" relationship where the part is owned outright: born and destroyed together with the whole.
Practical use: a UI Window owns its Buttons — close the window, and the buttons cease to exist too.
RECAPComposition ties two objects' lifetimes together — the part dies when the whole does.
GAP A sports Team has Players — but cut the team, and the players don't vanish; they can join another team tomorrow. How do we model "has-a" when the part should outlive, or be shared beyond, the whole?
FILL Aggregation — a "has-a" relationship where the part lives independently and can outlive, or be shared beyond, the whole.
RECAPAggregation: the part is independent and can survive, or be shared, beyond the whole.
GAP A Driver drives a Car — neither owns the other, and there's no diamond of ownership at all. What's the plainest possible way to say "these two objects simply know about and use each other"?
FILL Association — two independent objects simply know about and use each other. No ownership, no diamond.
RECAPAssociation: two peer objects that simply know about and use each other, no ownership.
GAP Sometimes a class needs another object for just one single operation — never stores it, never keeps a lasting link. Is there a connection even looser than association?
FILL Dependency — the weakest link: one object borrows another only for the duration of a single call.
RECAPDependency: an object borrowed only for a single call, never stored, the loosest link of all.
GAP Episode 3 warned against inheriting just to reuse a little code. If an object wants another object's behavior without inheriting from it, how does it actually borrow that behavior?
FILL Delegation — an object forwards a request to another object it holds, instead of handling it itself.
holding one — not by inheriting from it.
WORKED EXAMPLE · PRACTICAL USE

Composition + Delegation, together

This exact pattern is how most real software prefers reuse over inheritance.
class Car:
  def __init__(self):
    self.engine = Engine() # composition
 
  def start(self):
    return self.engine.start() # delegation
"Favor composition over inheritance" — a class becomes flexible when it borrows behavior instead of being permanently bound to an ancestor.

One spectrum, from tightest to loosest

COMMON MISTAKES

Where this trips people up

⚠
Confusing aggregation with composition.
Ask: "if the whole is destroyed, does the part still make sense on its own?" If yes, it's aggregation.
⚠
Reaching for inheritance to reuse a little code.
If it isn't truly "is-a", composition + delegation is usually safer and more flexible.
⚠
Turning every dependency into a stored field.
If an object is only needed for one call, passing it in briefly keeps coupling loose — don't hoard it as a permanent field "just in case".

Composition

Aggregation
Correct! The rooms exist independently and are only referenced by House — a classic "has-a, but doesn't own" relationship.
Dependency
Not quite: dependency is a brief, single-call borrow — House keeps a lasting reference to its rooms as a field.
